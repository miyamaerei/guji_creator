- **组合规则口径**：一条含多模态 → **拆为多条规则记录共享 item_id**（不并成单条多值，避免槽位歧义）；同一机构条的职能句如可切分为多条独立规范（如"凡选，每岁有大选，有急选…"与"凡升必考满…"）→ 各建一条规则。

  - **必须 AI 逐条判定**，代码触发词引擎只作候选/提示（pitfalls.md #7；《新官轨范》204 条代码引擎被用户否决先例）。

## 6.7 员额置信度（v3 新增 —— 用户发现歧义后补）

> 用户（m00284）指出：`{"office":"左、右侍郎", "count":2, "grade":"正三品"}` —— "这个感觉是左侍郎1，右侍郎1，但是不确定，所以需要**补一个置信度**，方便之后验证"。

**源文本实测：并列职官员的员额句式分三型，语义确定性不同**

| 型 | 句式 | 实测 | 语义 | confidence |
|---|---|---|---|---|
| **P1** | `左、右X各N人`（**带"各"**） | 49（全文）/ 55（含沿革） | **N × 并列项数**（明确） | **0.95** |
| **P2** | `左、右X N人`（**不带"各"**） | 8 / 11 | **N（本身即合计）** | **0.90** |
| **P3** | `各A、B N人`（合称共享） | 107 上界 / **真歧义约 4** | 疑为共 N，亦可能各 N | **0.60 → 待核** |
| P4 | 单纯（"尚书一人"） | 1247 | 字面值 | 1.00 |

**判定优先级纪律（v3.1，必守）**：**先判并列前缀型（P1/P2），再判合称共享型（P3）**。v3 首跑曾把 `左、右侍郎各一人` 误判为 P3（先判 `、`+`各`），致用户关心的那条记录被标成低置信；修正优先级后 = **P1 / 0.95**。

**`posts[]` 元素 v3 字段族**：
```python
{"office": "左、右侍郎", "office_parts": ["左侍郎", "右侍郎"],
 "count": 2, "grade": "正三品", "grade_order": 5,
 "count_form": "P1",              # P1/P2/P3/P4/未明
 "count_confidence": 0.95,        # 员额解读置信度 0.0~1.0
 "verify_needed": False,          # count_form ∈ {P3,未明} 或 conf<0.8 时 True
 "verify_reason": "未明",          # 需复核原因
 "count_evidence": "左、右侍郎各一人",  # 判定依据原文（防歧义回溯）
 "note": "未明"}
```

- `office_parts` 由打包器按并列符 + 左右/正副/东西南北前缀自动生成；**原始层不拆**（保持原文可溯），仅在 `_views/posts_flat.csv` 按原子职官展开（`左侍郎 count=1 / 右侍郎 count=1`）。
- `count_confidence < 0.8` 的 posts 元素自动进 `_views/verify_needs_review.csv`（**人工复核入口**）。
- **实证结论**：用户直觉判断正确 —— `左、右侍郎各一人` 的"各"字给出明确依据，合计 2（左 1 + 右 1）。

  - **交付前必查 `layer_count` 分布与 0 空条目率**，不能只信 validate 绿灯（pitfalls.md #28）。
  - **收尾用缺省模式跑 `build_kg_join.py`**（PowerShell 下 `--volumes 01,02` 会被拆参致 0 回填——工厂待评审区坑），回读 JSON 抽查 `by_vol`。
- **枚举治理**：枚举单点文件 `_kg_enums.py`（含 `version`）；新增值 `registerVersion+1` 回溯存量。
- **枚举校准用「收集-报告-暂存」模式**（V3）：未匹配值入 pending 表不中断执行，收尾统一决议——pitfalls.md #15。
- **封闭枚举硬校验（阻断）**：打包前对源数据做 `value ∈ ENUM_SET` 硬校验，不在集内 → 报错并列出待决议清单，**不许静默写入**（pitfalls.md #27）；验证报告输出每层"值种数 vs schema 定义数"，比值 > 1.5 判口径漂移。
