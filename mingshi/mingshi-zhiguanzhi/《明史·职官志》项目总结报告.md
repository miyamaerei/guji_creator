## 0. 项目概述

《明史·职官志》（卷四十八～卷五十二）数字化工程，由 `book-knowledge-factory` 实例化后按用户锁定口径推进：

- **AI 逐条判定 + 代码只验缺漏**（判定与验证严格分工）
- **条粒度**（按机构条目切分，**317 条**；非按卷、非按句）
- **original 指纹注入 + 引用关联**（AI 源数据不手抄原文）
- **每卷独立 JSON + 全局归一**（先分卷产出，再归一并验证）
- **枚举顶层封闭 + 动态回填**（新增枚举值必须 `VERSION+1` 并回溯存量）
- **词典全文本内生**（用户明确否决外部词典抓取）

最终形成**底座 + 7 层知识资产 + 跨层索引**：

```
L0 底座 → L1 实体层 → L2 规则层 → L3 流程层 → L4 结构化层（ORG/RANK/LINE/EVO 四维）
       → APPT 任职层 → TME 时间沿革层 → 跨层索引
```

本实例相对工厂既有 12 个实例的**最大差异**：本书是**典志体**（正史"志"），既非笔记（《五杂俎》《水东日记》），也非政书汇编（《明会典》）。典志体的行文单元是**机构**，不是事件、不是条文，因此需要**一套全新的结构化层四维设计**（ORG/RANK/LINE/EVO）与**时间沿革层（TME）**——这两项已作为新层与"正史典志体型（zgz 型）"方案组合回写工厂层库。

## 2. 反思结论

### 反思一（触发点：用户四次结构性纠偏）
本项目用户共发起 **4 次根本性结构改造**（v2 树形数组 / v3 员额置信度 / v7 取消模板容器 / 以及卷04 三项决定），每一次都发生在"我以为已经设计好了"之后。

核心结论：
- **v2**（用户要求树形 + 数组 + 时间链）：反映了"典志体的核心对象是**可层次化、可量化的编制**"，而我初期按层库默认的 ACT/FRD/LGR/TME 四维套用，完全没抓住本书的真实对象。
- **v3**（用户发现员额歧义）：用户在**读实际数据**时发现的，我生成时没意识到 `左、右侍郎` 的语义歧义。→ 教训：**编制类数据必须显式建模歧义**，不能假装确定。
- **v7**（用户质问 templates）：我把"没有具体实例"当成了 ORG 准入判据，实际上**原文是否作为机构陈述**才是判据。→ 教训：**准入判据必须从「原文说话的方式」出发，不是从「数据完备性」出发**。
- **卷04 三项决定**：南京段品级省略是原文的**口径声明**（条1 括注），不是数据缺失。→ 教训：**异常密度差先找原文声明的共同前提**，别急着判为缺漏。

### 反思二（触发点：假 ERR 与真 ERR 的区分）
v7 首跑 120 条假 ERR（`rank_type 越界: None`），卷05 首跑 128 条 ERR 中 107 条是"树内边仅 ORG 有"。

核心结论：
- **假 ERR 指纹**：值全为 `None` 且集中在一批新记录 → 是"字段根本不存在"而非"字段值非法"，**先怀疑分派顺序**，不要逐条补字段。
- **结构一致性 ERR（树内边 vs LINE 边）**往往不是数据错误，而是**两棵树口径不一致**（如 ORG 树把京卫挂在"隶X军都督府"分组节点下，LINE 边却直指 `X军都督府`）。修正应在**其中一侧**统一口径，不是逐条修数据。
- 卷05 的 107 条缺失 LINE 边用**脚本从 ORG 树递归展开自动补齐**（而非手写），这是正确做法：**树是单一真相源，边表应可派生**。

## 3. 根因分析：为什么"重复很多次无用读取"

诚实复盘，本项目重复读取有 5 类根因，其中 3 类工程失误、2 类环境与方向成本：

1. **上下文压缩后的 schema 重读（半可控）**：8 层 schema 复杂，压缩后需重读 `references/schemas.md`。改进：schema 样例已固化进 SKILL.md 的 5 个示例块。
2. **探查-执行边界没守住（失误）**：卷02/03/04/05 各有一轮"首跑 → 发现 50~130 条 ERR → 修 → 复跑"，其中多次是本可在探查阶段发现的（如卷03 的层级同级问题、卷05 的所司互逆）。改进：**卷首探查时须实测一遍"层级枚举覆盖度"与"树内边口径"**。
3. **产物覆盖回归导致的重复验证（失误）**：v7 改造后曾误以为 structs 全量需重建，实际只需重跑 `build_struct`。改进：管线已按层拆分，重跑粒度已可控。
4. **环境噪声导致的重复跑（半可控）**：PowerShell 下 `python -c` 含中文/引号会 `InvalidArgument`、`--volumes 01,02,03` 被拆参、控制台中文乱码 → 多次白跑。改进：**中文校验一律写临时 .py 文件**；单卷重跑逐卷调用。
5. **用户多轮纠偏（方向成本，不是无用读取）**：v2/v3/v7 + 卷04 三项决定 —— 这 4 轮全部产生了**正面的结构改进**，且已回写工厂，应视为**方向对齐成本**而非浪费。

## 4. 方法论沉淀（下次遇到典志体/编制类文献的处理原则）

1. **一次探查**：开工前读完全部输入 + schema 样例 + **密度统计**（品级标注密度、机构隶属词密度）。连续两次读取不再改变计划即停止探查。
2. **异常密度差先找原文声明的共同前提**：卷04 南京段品级密度低 80 倍，根因是条1 的一句括注，不是数据缺失。
3. **准入判据从「原文说话的方式」出发**：ORG 的判据是"原文是否作为机构陈述"，不是"有没有具体实例"（v7 教训）。
4. **先锁 schema 再写数据**：字段口径、枚举、ID 规则一次性定死；打包器注入指纹/关联/校验。
5. **AI 判定与代码验证严格分工**：判定逐条人工（AI）；代码只验缺漏。
6. **歧义必须显式建模**：编制类数据的员额歧义（P3 合称共享）不能假装确定，须有 `count_confidence` + `verify_needed` + 待核清单（v3 教训）。
7. **树是单一真相源，边表应可派生**：新增 ORG 节点须三处同步（children / RANK / LINE），若不一致优先怀疑口径而非逐条补数据。
8. **所有生成器正式化**：`build_` 前缀 + 可重跑 + 幂等；修复并入生成器。
9. **验证一次到位**：校验脚本写文件输出；**假 ERR 指纹（值全 None + 集中在新记录）先查分派顺序**。
10. **交付按层聚合**：每层一组（归一汇总 + 验证清单 + 卷示例 + 跨层索引）。
11. **如实报告缺口**：哪里缺、缺什么、补什么方案，不静默降级。
12. **多行结构用 edit 删改须以完整记录为单位**（卷05 事故）。
