## 0. 项目概述

《明史·职官志》（卷四十八～卷五十二）数字化工程，由 `book-knowledge-factory` 实例化后按用户锁定口径推进：

- **AI 逐条判定 + 代码只验缺漏**（判定与验证严格分工）
- **条粒度**（按机构条目切分，**317 条**；非按卷、非按句）
- **original 指纹注入 + 引用关联**（AI 源数据不手抄原文）
- **每卷独立 JSON + 全局归一**（先分卷产出，再归一并验证）
- **枚举顶层封闭 + 动态回填**（新增枚举值必须 `VERSION+1` 并回溯存量）
- **词典全文本内生**（用户明确否决外部词典抓取）
- **交付前字段填充率体检**（v11 新增：`ERR=0` 只证明值合法，不证明有值）

最终形成**底座 + 8 层知识资产 + 跨层索引**：

```
L0 底座 → L1 实体层 → L2 规则层 → L3 流程层 → L4 结构化层（ORG/RANK/LINE/EVO 四维）
       → C15 官职层（v10）→ APPT 任职层 → TME 时间沿革层 → 跨层索引
```

本实例相对工厂既有 12 个实例的**最大差异**：本书是**典志体**（正史"志"），既非笔记（《五杂俎》《水东日记》），也非政书汇编（《明会典》）。典志体的行文单元是**机构**，不是事件、不是条文，因此需要**一套全新的结构化层四维设计**（ORG/RANK/LINE/EVO）与**时间沿革层（TME）**——这两项已作为新层与"正史典志体型（zgz 型）"方案组合回写工厂层库。

**v9–v12 的触发点都来自用户用真实查询反向验收**（而非工程指标报错），这是本项目最有价值的教训，详见 §2 反思三与 §3 第 6 条。

| 缺陷 | 根因 | 修法 |
|---|---|---|
| 子机构无 ID（446/869 无归属） | `C.assign_ids` 只作用于**顶层记录**，`children[]` 子节点从未拿到 id | 按「父 id + 子序号」派生 `ORG-505#1` |

**ID 空间坑**：`walk_org` 曾自行合成子节点 ID（`根ID#父名/子名`），**覆盖** `build_struct` 派生的 `#N` 形式 → 改为**优先沿用记录里已有的 `id`**。

**关系配对五条纪律**（宁缺毋滥）：
① **语义方向**（古汉语「A…。B佐之」中 **B 才是佐者**，主语在后 —— 首跑曾判反 180°）；
② **关系条 ≠ 编制条**（「侍郎佐之」在职掌条 `01-034`，编制在同机构前一条 `01-033` → 须沿条目序回溯 `owning_item`，**跨卷不回**）；
③ **回溯落回自身不得兜底**（严禁退化为「按名字取首个」，会随机挂到南京某部）；
④ **合称/拆名互认**（原文「侍郎」vs 节点「左侍郎/右侍郎」，须去左右前缀比对）；
⑤ **「兼领之」主语可以是人**（「命兵部尚书**于谦**兼领之」→ 标记词前 14 字内含「命/以…」施动句式即跳过）。

**实测**：1241 节点 / 有平级 278（边 203） / 官职—官职关系 **16 条**（全为副贰） / 实俸 33；3 个查询视图（`officials_flat.csv` / `official_tree.json` / `official_by_grade.json`）。

**最重要技术发现 —— 复合句静默丢数据**：
印信表覆盖率长期只有 ~57% 而**不报任何错**。根因：原文表格句是**复合句**，一句含**多组「机构清单 + 品级 + 规格」**：
```
通政司、大理寺、太常寺、詹事府、京卫、各按察司、各卫，俱正三品，
苑马寺、宣慰司，俱从三品，铜印，方二寸七分，厚六分。
```
解析器按「找**第一个**品级标记 → 之前的都算清单」，于是第二组清单出现在**第一个标记之后**，被当作规格 token 跳过。修法：数格式标记个数 ≥2 判为复合句 → **按标记切段逐段独立登记**；**首段可能无标记**须独立并入。实测归一后唯一机构名 **157 → 235**，顶层覆盖率 **57% → 81.6%**。

**接线检查法（同坑复发，教训最重）**：`_seal_backfill.py` 逻辑正确、独立可跑，但**从未被 `build_struct.py` 调用** → `seal` 填充数为 **0** 而 `ERR=0`。根因是**检查单缺失**（pitfalls #45 已首记此坑，当时只记「字段要回填」，没把「填充率体检」写进流程）。

**v11 定死**：
1. 新增字段必做**填充率体检**（逐字段统计非空节点数并出表）；
2. **排查顺序：先查是否被调用 → 再查解析覆盖面 → 最后才接受「原文没有」**；
3. **填充率表列入交付清单，与 ERR/GAP 并列** —— `ERR=0` 只证明值合法，不证明有值。

**实测**：`seal` 165（顶层 117/145 = 80.7%）/ `jurisdiction` 64 / `powers` 27 / `station` 19 / `doc_channel` 5 / `assess` 4；枚举 `_kg_enums.py` **V1.7**。

**⑦ 类「办公地点」的边界**：**无单一字段可独答** —— `station`（内廷/外朝）+ `jurisdiction`（辖域含驻地）+ **TME**（移驻沿革）三者合成。驻地**变迁**属时间序列（「三十八年令防秋日驻宣府。四十三年，移驻怀来」），不作 ORG 静态字段。

**已知可选后续增量**：道制 200+ 道名的驻点数据未建为 ORG 子节点（`道` 节点 `children` 为空），但原文有**现成结构化数据源**（`(驻省)` `(驻广信)` 类括注 79 处 + 行内 `驻` 121 处）。→ **v12 已建**。

## 2. 反思结论

### 反思一（触发点：用户四次结构性纠偏）
本项目用户共发起 **4 次根本性结构改造**（v2 树形数组 / v3 员额置信度 / v7 取消模板容器 / 以及卷04 三项决定），每一次都发生在"我以为已经设计好了"之后。

核心结论：
- **v2**（用户要求树形 + 数组 + 时间链）：反映了"典志体的核心对象是**可层次化、可量化的编制**"，而我初期按层库默认的 ACT/FRD/LGR/TME 四维套用，完全没抓住本书的真实对象。
- **v3**（用户发现员额歧义）：用户在**读实际数据**时发现的，我生成时没意识到 `左、右侍郎` 的语义歧义。→ 教训：**编制类数据必须显式建模歧义**，不能假装确定。
- **v7**（用户质问 templates）：我把"没有具体实例"当成了 ORG 准入判据，实际上**原文是否作为机构陈述**才是判据。→ 教训：**准入判据必须从「原文说话的方式」出发，不是从「数据完备性」出发**。
- **卷04 三项决定**：南京段品级省略是原文的**口径声明**（条1 括注），不是数据缺失。→ 教训：**异常密度差先找原文声明的共同前提**，别急着判为缺漏。

### 反思二（触发点：假 ERR 与真 ERR 的区分）
v7 首跑 120 条假 ERR（`rank_type 越界: None`），卷05 首跑 128 条 ERR 中 107 条是"树内边仅 ORG 有"。

核心结论：
- **假 ERR 指纹**：值全为 `None` 且集中在一批新记录 → 是"字段根本不存在"而非"字段值非法"，**先怀疑分派顺序**，不要逐条补字段。
- **结构一致性 ERR（树内边 vs LINE 边）**往往不是数据错误，而是**两棵树口径不一致**（如 ORG 树把京卫挂在"隶X军都督府"分组节点下，LINE 边却直指 `X军都督府`）。修正应在**其中一侧**统一口径，不是逐条修数据。
- 卷05 的 107 条缺失 LINE 边用**脚本从 ORG 树递归展开自动补齐**（而非手写），这是正确做法：**树是单一真相源，边表应可派生**。

### 反思三（触发点：五卷全绿之后，用户 8 问中 3 问答不了 —— 本项目最有价值的教训）

**这是本项目最重要的一次认知纠正。** 五卷全部完成时，所有工程指标都是满分的：ERR=0 / GAP=0 / 跨层索引 0 空条目 / 幂等复跑一致。但用户用 8 类真实查询验收时，**3 类核心查询（官职的上级 / 下级 / 平级）根本无解**。

根因不是任何一个 bug，而是**层设计的盲区**：把「机构」当成了唯一骨架，官职退化为机构节点上的 `posts[]` 数组元素 —— 无 ID、无父子关系。而 L1 明明已经把 1109 条 `official` 标注出来了，**标了却没有任何索引可用**。

**核心结论**：
- **工程验收维度（层内是否自洽）与用户验收维度（我能不能查到 X）可以完全脱节。** `ERR=0` 只说明「数据没写错」，不说明「数据够用」。
- **`ERR=0` 甚至不说明「有数据」** —— v9 `salary_ref` 431/431 全空、v11 `_seal_backfill.py` 未接线致 `seal` 全域为 0，**两次都没有报错**。
- 对策三层（已进坑库）：
  1. **Phase ② 就产出「目标查询问句清单」并逐问标注承载层**（#50）；标注不出的即设计缺口；
  2. **交付前用问句清单反向实查一遍**（v10 补充：光有清单不够，必须实查）；
  3. **交付前跑字段填充率体检，与 ERR/GAP 并列**（v11）。

**v9 → v10 → v11 三版全部源自这条**：v9 补全书性专表与字段回填，v10 建 C15 官职层，v11 加机构附加属性族。**没有一次是工程报错驱动的**。

## 3. 根因分析：为什么"重复很多次无用读取"

诚实复盘，本项目重复读取有 5 类根因，其中 3 类工程失误、2 类环境与方向成本：

1. **上下文压缩后的 schema 重读（半可控）**：8 层 schema 复杂，压缩后需重读 `references/schemas.md`。改进：schema 样例已固化进 SKILL.md 的 5 个示例块。
2. **探查-执行边界没守住（失误）**：卷02/03/04/05 各有一轮"首跑 → 发现 50~130 条 ERR → 修 → 复跑"，其中多次是本可在探查阶段发现的（如卷03 的层级同级问题、卷05 的所司互逆）。改进：**卷首探查时须实测一遍"层级枚举覆盖度"与"树内边口径"**。
3. **产物覆盖回归导致的重复验证（失误）**：v7 改造后曾误以为 structs 全量需重建，实际只需重跑 `build_struct`。改进：管线已按层拆分，重跑粒度已可控。
4. **环境噪声导致的重复跑（半可控）**：PowerShell 下 `python -c` 含中文/引号会 `InvalidArgument`、`--volumes 01,02,03` 被拆参、控制台中文乱码 → 多次白跑。改进：**中文校验一律写临时 .py 文件**；单卷重跑逐卷调用。
5. **用户多轮纠偏（方向成本，不是无用读取）**：v2/v3/v7 + 卷04 三项决定 —— 这 4 轮全部产生了**正面的结构改进**，且已回写工厂，应视为**方向对齐成本**而非浪费。

6. **审计视角缺位（v12 新识别的第 6 类，最根本）**：前 5 类都是「做得慢」，这一类是「**做完了但没验收对**」。项目在 v9 时工程指标已全绿（ERR=0 GAP=0 0 空条目），但用户 8 问中 3 问答不了；直到 m03393 要求「列举一般人会问的问题并检查能否回答」，才系统性暴露三个结构缺口。**根因**：验收用的是「层内自洽指标」，而不是「读者的问句」。改进：**问句清单应在 Phase ② 就产出**，它是字段设计的依据（工厂 pitfalls v8 #50 已固化此条）；执行完毕后的反向实查是**补救**，成本更高。

## 4. 方法论沉淀（下次遇到典志体/编制类文献的处理原则）

1. **一次探查**：开工前读完全部输入 + schema 样例 + **密度统计**（品级标注密度、机构隶属词密度）。连续两次读取不再改变计划即停止探查。
2. **异常密度差先找原文声明的共同前提**：卷04 南京段品级密度低 80 倍，根因是条1 的一句括注，不是数据缺失。
3. **准入判据从「原文说话的方式」出发**：ORG 的判据是"原文是否作为机构陈述"，不是"有没有具体实例"（v7 教训）。
4. **先锁 schema 再写数据**：字段口径、枚举、ID 规则一次性定死；打包器注入指纹/关联/校验。
5. **AI 判定与代码验证严格分工**：判定逐条人工（AI）；代码只验缺漏。
6. **歧义必须显式建模**：编制类数据的员额歧义（P3 合称共享）不能假装确定，须有 `count_confidence` + `verify_needed` + 待核清单（v3 教训）。
7. **树是单一真相源，边表应可派生**：新增 ORG 节点须三处同步（children / RANK / LINE），若不一致优先怀疑口径而非逐条补数据。
8. **所有生成器正式化**：`build_` 前缀 + 可重跑 + 幂等；修复并入生成器。
9. **验证一次到位**：校验脚本写文件输出；**假 ERR 指纹（值全 None + 集中在新记录）先查分派顺序**。
10. **交付按层聚合**：每层一组（归一汇总 + 验证清单 + 卷示例 + 跨层索引）。
11. **如实报告缺口**：哪里缺、缺什么、补什么方案，不静默降级。
12. **多行结构用 edit 删改须以完整记录为单位**（卷05 事故）。
13. **先问「用户要查什么」，再定字段**（v9–v11 最大教训）：Phase ② 产出目标查询问句清单 → 逐问标注承载层 → 标不出的即设计缺口。
14. **新增字段必做填充率体检**（v9/v11 两次同坑）：`ERR=0` 只证明值合法，不证明有值。排查顺序＝**先查是否被调用 → 再查解析覆盖面 → 最后才接受「原文没有」**；填充率表与 ERR/GAP 并列交付。
15. **覆盖率也是验收指标**（v11）：机构清单与字段值不一致**不会报 ERR**（印信表复合句静默丢掉一整组：苑马寺/宣慰司/招讨司/安抚司）。凡"表 → 值"的解析，都要报覆盖率并与源清单对账。
16. **用户点名的类 ≠ 必须建的类**：先量证据密度再决定。原文稀疏且已有字段可承载者，应明确指出「**已由 X 承担**」，而非新开语义重叠字段（v11 ②选任方式）。用户给了「没有就算了」的口子时，**忠实执行比凑数重要**。
17. **定量制度用「保底值 + 实际值」两层结构**：`grade_based`（按等级统一标准）+ `actual`（个别特例，**没有就不填 null**）。可复用于俸禄/赏赐/配额/赋役/驿传供给（v10）。
18. **「有原文显式表述的边」才建边，不按等级相邻自动连边**：228 个唯一官职名同品级者动辄数十，「吏部郎中 vs 户部郎中」同品级却不同机构 —— 自动连边会把组织包含关系误当官职关系（v10）。
19. **定义必须落到校验器**：「平级 = 同机构同品级」不只是文档描述，而是 `m.org_id != n.org_id or m.grade_order != n.grade_order` → ERR。**定义不可执行就等于没定义**（v10）。
20. **原文形态决定字段边界，不要强求单一字段**：v11 ⑦「办公地点」三问分属 `station` / `jurisdiction` / TME，无字段可独答 —— 如实说明承载分工，好过造一个语义模糊的字段。
