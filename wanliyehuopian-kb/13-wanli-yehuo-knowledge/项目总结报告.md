## 0. 项目概述

《万历野获编》（明·沈德符，1578–1642，万历三十四至三十五年撰成，被誉为"明代野史之冠"，
清修《明史》大量引用）数字化工程，按用户锁定口径推进：

- **AI 逐条判定 + 代码只验缺漏**（判定与验证严格分工）
- **条粒度**（按 `【标题】` 切分，共 1451 条）
- **original 指纹注入 + 引用关联**（AI 源数据不手抄原文；生成器逐字硬校验）
- **每卷独立 JSON + 全局归一**（先分卷产出，再归一并验证）
- **枚举顶层封闭 + 动态回填**（新增枚举值必须 version+1 并回溯存量）
- **词典全文本内生**（用户明确否决外部词典抓取）

最终形成**底座 + 10 层 + 跨层索引 + 6 类派生视图**：
实体层 → 规则层 → 事件层 → 任职层 → 关系层 → 引书层 → 论说层 → 纪事层 → 沿革层 → 制度层 → 跨层索引。

### 0.1 方案定型：为什么是这 12 层

用户问："如果我是一个研究万历野获编的人，产出足以覆盖明会典的问题了吗？还有哪些不够呢？"
据此按**密度信号实测**逐层决定建/不建（不是照搬层库模板）：

| 层 | 建/不建 | 数据证据 |
|---|---|---|
| L0 底座 | 建 | `【】` 天然切分，1451 个条目标记 |
| L1 实体 | 建 | 人物/机构/地名/职官极密；任职词 1120 命中 |
| L2 规则 | 建 | 规范词 767（不可/须/例/定制/著为令） |
| L3 流程 | **不建** | 本书为掌故笔记非操作手册——**"点不是线"** |
| L4 结构化 | **不建** | 非台账/编制体，无多维组织对象 |
| L5 事件 | 建 | 叙事纪事密集（国本之争/矿税/楚狱等） |
| C1 APPT | 建 | 任职词 1120 命中 |
| C3 REL | 建 | 交往/恩怨/师生/姻亲/弹劾叙事丰富 |
| C5 TRL | **不建** | 用户未要求 |
| C6 CIT | 建 | 引书 `《` 436 命中 |
| C9 OPN | 建 | "按"字议论 379 处，几乎每 4 条 1 条有议论 |
| C10 MING | 建 | 全书几乎全涉明，年号 1280 命中 |
| C14 TME | 建 | 年号 1280，制度沿革叙事丰富 |
| REG 制度 | 建 | 70%+ 内容涉典章制度 → 用**笔记掌造型 REG**（7 属性精简版，非政书 13 属性） |
| C2 LIT / C4 NAM / C7 OBJ / C8 CUS | **不建** | 整篇文献极少 / 无表格式名录 / 名物密度不足 / 风俗散见各条（归 L1 或 OPN） |

**关键设计取舍**：
- **L3/L4 明确不建** —— 这是本方案与政书型（如《明会典》）分野的根本。笔记是"点"的集合，强行拉"线"（流程）或建"面"（结构化台账）会造出原文不支持的伪结构。
- **REG 用精简 7 属性版** —— 政书型 REG 的 13 属性（编制/品级/俸禄/..）在笔记中大多无对应文本，采用 `name/category/establishment/content_summary/actual_practice/vs_official_history/tme_ids` 等笔记掌故友好字段。
- **用户否决 `category_48`** —— 理由："应该是卷名，不要额外加"。改用源文自带的 `○` 门类（48 类），不另造分类维度。

## 2. 反思结论

### 反思一（触发点：补齐卷01 时出现 21 项校验失败，修复后重跑"错误一字不变"）

**核心结论：合并器的非幂等性会把"修复无效"伪装成"修复未生效"，掩盖真实进展。**

- 现象：修好片段文件后重跑，21 项错误**完全相同**。
- 实际根因：`_merge_parts.py` 用 `src.rfind("    go()")` 定位 head 边界。**首次合并后** part2 已含全部片段，第二次合并时 `rfind` 找到的是**末尾**的 `go()`，于是"head"= 整个已合并文件，五个片段被**再追加一遍**——part2 从 256,890 字符涨到 502,032，内含两份副本。
- 为什么看起来"没生效"：校验器对同一 `item` 只是重复累积 `ERRORS`，错误文本相同。
- **教训**：**"改完没变化"不等于"改动没生效"——先验证输入是否真的变了**（此处应比对 part2 的字符数/条目块数）。定位手段：用 `# ==== 01-009` 这类**条目注释**作 head 边界，而非可变长位置锚（`go()`）。修复后加自检：合并结果条目块必须恰好 48 个。

### 反思二（触发点：去重）

**核心结论：非幂等写入器会静默产生重复记录，必须显式去重 + 校验 ID 唯一。**

- 因反思一的重复合并，写盘后各层出现 **49 条重复记录**（24 ents + 3 rules + 4 events + 5 opns + 1 cits + 4 mings + 5 tmes + 3 regs）。
- 实测确认：49 个重复 ID 的记录 `json.dumps(sort_keys=True)` **完全相同**（纯副本，无内容冲突）→ 安全去重。
- `validate_layers.py` 的 ID 唯一性检查正是为此设的最后一道网。

### 反思三（触发点：交付前核对派生视图）

**核心结论：上游一个字段污染会静默传播到所有下游，必须在上游校验。**

- 发现 `views/subcategory_index.json` 有一个 120 字符的 key，追查到 `_item_registry.json` 中 **46 条** `subcategory` 被污染成原文片段。
- 根因：源文本里**校勘注记**（如「继祖归，即伪称**称字据明史列传二○二补**，受朝命袭职」）与 ○ 门类标记同形，分段器误判。
- 已修复 46 条（卷04 的 37 条 → `宗藩`，卷29 的 9 条 → `叛贼`），备份 `_backup_registry_pre_subcatfix.json`。

## 3. 根因分析：为什么"重复很多次无用读取"

诚实复盘，重复读取有 **5** 类根因，其中 **3** 类工程失误、**2** 类环境与方向成本：

1. **上下文压缩后的 schema 重读（半可控）**：层 schema 字段名在两套 style 间不一致（`type` vs `event_type`、`office` vs `position`、`purpose` vs `citation_purpose`），压缩后须反复重读才能确认字段名。
   **改进**：schema 样例固化进报告与 `schemas.md`，查询时先查字段名清单。
2. **探查-执行边界没守住（失误）**：补卷01 时先建骨架再逐片段写，中途发现构造器参数名（`faction_impl` vs `faction`、`inst=` vs `institution=`）不匹配才回头改。
   **改进**：开工前一次探查，把**构造器签名逐字固化**进契约文件（本轮 `_spec_v01.md` 正是这样做的，效果显著）。
3. **产物覆盖回归导致的重复验证（失误）**：`_merge_parts.py` 非幂等导致重复写入，须去重后重跑全部验证。
   **改进**：写入器必须幂等（本轮已改为按条目注释定位 + 自检重复块）；修复并入生成器。
4. **环境噪声导致的重复跑（半可控）**：PowerShell 的 `python -c "..."` 内嵌中文双引号报「重定向不支持」；GBK 控制台中文乱码；`exec` 注入的片段拿不到 traceback 行号；minified 输出淹没 stdout。
   **改进**：验证统一写 `.py` 脚本并重定向到文件再读；脚本内 `sys.stdout = io.TextIOWrapper(..., encoding='utf-8')`；错误定位用「构造器签名位次 + 错误串前缀 grep」双路。
5. **用户多轮纠偏（方向成本，不是无用读取）**：用户多次追问"产出是否足以覆盖研究需求？还缺什么？"，推动了字段扩展设计（`faction`/`exam_info`/`vs_official_history`/`firsthand_witness`）与 6 类派生视图的诞生。
   **改进**：这类"重复"产出的是设计价值，不属于无用读取。

**最值得记的一条**：本项目最有效的工程护栏不是"事后审计"，而是**写入前的硬校验** ——
生成器的 `q(item, s, field)` 把每个 `original`/`evidence`/`quoted_text` 与该条目的源文段（去空白）**逐字子串比对**，不符即累积 `ERRORS`，
`main()` 见到非空 ERRORS 就打印「!!! 校验失败 N 项」并**拒绝写盘**。这把"AI 引文漂移"从"事后发现"变成"根本写不进去"。

## 4. 方法论沉淀（下次遇到任务的处理原则）

1. **一次探查**：开工前读完全部输入 + schema 样例 + 统计；连续两次读取不再改变计划即停止探查。
2. **先锁 schema 再写数据**：字段口径、枚举、ID 规则一次性定死；**构造器签名逐字写进契约文件**交给并行撰写者。
3. **AI 判定与代码验证严格分工**：判定逐条（AI）；代码只验缺漏，但校验必须**卡在写盘之前**。
4. **所有生成器正式化**：可重跑 + **幂等**（用不可变锚点定位，不用可变长位置锚）；修复并入生成器。
5. **验证一次到位**：校验脚本写文件输出；重跑前先确认不覆盖已修复字段。
6. **枚举单点治理**：新增枚举值 version+1 并回溯存量（registerVersion 模式）；**构造器内 `chk()` 是唯一防线**——绕过它就会产生漂移。
7. **方向假设先确认**：粒度/判定方式/交付形态开工前问清。
8. **并行撰写必须给契约**：分片外派时给「精确构造器签名 + 硬性纪律 + 参考实现 + 枚举清单 + 原料切片」，
   且**禁止片段作者改动共享的主组装文件**（本轮曾因此产生覆盖回滚）。
9. **每轮任务建 task 清单**：阶段可见、完成可核。
10. **如实报告缺口**：哪里缺、缺什么、补什么方案，不静默降级（本报告 §5 与使用报告 §8 即按此原则如实记录枚举漂移与未治理项）。
