# 层库（Layer Library）——引导参考板

> 本文件是工厂 Phase ② 反思的"引导参考板"：**先引导用户想，再给参考，后让用户自己想**。
> 层库不是强制清单，不是预设流程。每个层是一个**可定制组件**（模板），反思时选配 + 按书定制；用户自定义的新层可回写本库（registerVersion：版本+1）。
> 库版本：v17（版本明细见文末"版本记录"；新层候选先进 `pending-review.md` 待评审区，评审通过才入本库）

## 0. 怎么用这个层库

1. **先问用户**：这本书你想结构化哪些方面？（用户的回答是第一输入，无条件列候选）
2. **再给参考**：从下面挑选与本书"适用信号"匹配的层展示给用户，作为引导。
3. **后让用户想**：请用户提出层库之外的层——任何方向都可以（人物关系、地名沿革、引文索引……）。
4. **AI 补证据**：每个候选层给出建/不建理由 + 数据检验。
5. **确认锁层**：只对启用层写 schema、写源数据、建打包器；未启用层不做任何动作。

## L0 底座（公共地基，任何书必做，不算"层"）

- **定义**：章节拆分 + 条目切分 + 指纹库（原文锚点）。
- **为什么必做**：一切后续层的原文注入源；AI 源数据不手抄原文，全靠指纹库。
- **执行**：
  1. 全书按锁定粒度切分为条目（默认"条"），每章一个 XHTML/MD（含版本说明卷）。
  2. 抽原文为 `_extract\NN_卷名.txt`（格式 `条N|正文`）。
  3. 建 `_item_registry.json`：扁平 dict，key=`NN-NNN`，value 含 `original`/`norm`。
- **ID**：item_id = `NN-NNN`（卷-序），全书唯一，是所有层的共同锚点。
- **参考来源**：《新官轨范》275 条指纹库，全部层 original 注入源。

## L1 实体层（术语/人物/机构/概念成体系时建）

- **定义**：命名实体标注 + 全局归一 + 主键表（alias_index 反查）。
- **适用信号**：术语/人物/机构/概念重复出现、成体系（几乎所有书都适用；辞书/类书/名录尤其高价值）。
- **schema 要点**：每卷标注 JSON（id/text/type/start/end/normalized/confidence/source）→ 全局归一（normalized_inventory）→ 主键表（ENT-xxx + alias_index）。
- **枚举**：实体类型**从本书文本中归纳**（封闭 + 兜底"类型待定"），全文本内生词典（词条必须出现在原文，否则剔除）。
- **变体**：复合解读词形（如"把门皂隶"→皂隶）用 alias_index 手工映射，不动标注。
- **参考来源**：《新官轨范》11 类封闭枚举、1981 标注 / 591 归一实体。

## L2 规则层（规范句密集时建）

- **定义**：规范句 → IF-THEN 规则（条件/主体/动作/对象/模态/目的/处罚/出处）。
- **适用信号**：触发词密集（不可/不许/务要/须/止许/毋/勿/责罚/限 N 日……），内容为"应当/禁止/程序"型。
- **schema 要点**：rule_id / item_id / type / modals / condition / subject（含 subject_ent_ids）/ action / object / purpose / punishment / original / confidence。
- **规则类型枚举**：禁止/义务/允许/程序/时限/处罚/优先级。
- **执行注意**：判定必须 AI 逐条（代码触发词引擎只作候选）；组合规则（一条多模态）拆/并口径实例化时定死。
- **参考来源**：《新官轨范》273 条 XGF-R（代码引擎 204 条被用户否决 → AI 逐条）。

## L3 流程层（操作过程有时序时建）

- **定义**：事件流程 + 步骤链（steps + next + agent）+ 状态机。
- **适用信号**：手册/工艺/政务流程/排程，有先后步骤或显式时序。
- **schema 要点**：process_id / item_id / name / steps（step_id/seq/text/agent 含 agent_ent_ids/next）/ state_machine / events（显式引用事件层）/ original。
- **执行注意**：**显式时序素材**（如时刻表）才建 state_machine（states/transitions）；散点素材判定"点不是线"，不强行建模。
- **参考来源**：《新官轨范》274 流程 / 744 步；04 卷直日时刻表建 9 状态 10 迁移状态机。

## L4 结构化层（存在可多维组织的对象时建）

- **定义**：按领域维度组织对象（每个维度一个封闭枚举的 ID 前缀）。
- **适用信号**：用户提出维度方向；或书中存在可多维组织的对象（台账/时间/生命周期/角色职责/风险机制……）。
- **默认五维变体**（按书增删）：
  | 维度 | ID 前缀 | 干什么 |
  |---|---|---|
  | 文簿台账体系 | LGR | 簿册/台账/名籍 |
  | 时间制度 | TME | 历法/时辰/节令/排期 |
  | 〔对象〕生命周期 | DOC | 公文/物件/流程对象的生命周期阶段 |
  | 角色-职责网络 | ACT | 人物/角色及其职责关系 |
  | 防弊/风险机制库 | FRD | 防弊、风险、负面机制 |
- **执行注意**：维度从本书内容归纳，每维封闭枚举；target 用 ID 引用而非文本。
- **参考来源**：《新官轨范》677 条（LGR 98/TME 138/DOC 87/ACT 157/FRD 197）——五维是用户问"除了流程还能怎么结构化"后讨论选定。

## L5 事件层（叙事/纪事密集且用户要建时建）

- **定义**：五元组 Registry（who/action/what/when/where），未明显式写"未明"。
- **适用信号**：史书/传记/纪事/案例集，叙事与事件密集。
- **schema 要点**：event_id / item_id / type / who（含 who_ent_ids）/ action / what / when / where。
- **枚举**：事件类型**继承基准库事件类型子库**（`references/enum-library.md` §1.3 规范全集 + 别名映射），不再每本书从零封闭归纳；本书新增值走 registerVersion 动态回填（收集-报告-暂存 → 决议 → +1 → 回溯）；兜底"其他"；ID 命名空间**唯一归属本层**，其他层只引用。
- **执行方式**：试点 1 卷验收 → 全量；未建模条目如实单列缺口。
- **参考来源**：《新官轨范》229 事件 XGF-E——是用户提出"事件五元组 Registry"后才做的层（非预设）；2026-10-10 用户决策升级为跨书动态枚举（合并三实例枚举建库）。

## 跨层索引（启用 ≥2 层时必做，不算"层"）

- **定义**：条目 → 各层 ID 一行全看。
- **产出**：`_kg_join.json`（结构化）+ `_kg_join_flat.csv`（扁平，Excel 直开）。
- **schema**：item_id / volume / source / rules / procs / events / structs / ents / layer_count。
- **执行注意**：ID 对齐审计先行（实体主键唯一/引用槽位合法/item_id 全回填/target 用 ID/枚举口径一致）；P0 修复并入打包器，重跑不丢。

## 自定义层注册指南（学习回路的入口）

用户提出的层库之外的层（如"人物关系网络""地名沿革""引文索引""术语谱系"）同样按层模板设计：

1. **注册**：实例化确认后，把新层作为模板回写本文件（registerVersion：版本+1，追加小节）。
2. **模板要素**：层名 / 定义 / 适用信号 / schema 要点 / ID 前缀 / 枚举 / 执行流程 / 参考来源（首个实例）。
3. **命名空间**：新层 ID 前缀必须全局唯一，不与既有层冲突；跨层引用只指向对应层。
4. **校验**：试点校验通过后才算注册完成。

## 自定义层注册（v2，源自《水东日记》实例 shuidong-riji-knowledge）

### C1 职官任职层（APPT）

- **定义**：人物-官职-时间-状态的任职记录（"谁在何时担任何职"）。
- **适用信号**：笔记/传记/政书/史书中存在大量任职表述（"〔人名〕为/任/授/擢/迁/除〔官职〕"、"〔官职〕致仕〔籍贯〕〔人名〕"型句式）。
- **schema 要点**：appointment_id / item_id / person(含 person_ent_ids) / office(含 official_ent_ids) / institution(含 ent_ids) / when(未明写"未明") / status / evidence / original。
- **ID 前缀**：`APPT-`（全局唯一，只属本层）。
- **枚举**：任职状态 = 现任/致仕/升迁/贬谪/罢黜/兼领/暂代/追赠/未明（封闭+兜底）。
- **执行流程**：任职动词词典（授/擢/迁/改/除/罢/谪/致仕/兼/领/督/巡抚/提督）+ 官职词典 → 正则候选 → AI 复核 → 人工校验闭环；一条目多任职拆多条共享 item_id。
- **参考来源**：《水东日记》实例（用户为明朝职官知识图谱提出，2026-10-10 试点通过）。

### C2 文献资产索引层（LIT）

- **定义**：书中收录/抄录的诗文、奏议、碑志、诏敕、书启、题识等文献资产登记。
- **适用信号**：笔记/文集/类书整篇收录或转引他人作品（圣旨/碑文/长记/奏议全文）。
- **schema 要点**：lit_id / item_id / title(无题取首句) / author(含 author_ent_ids，佚名"未明") / type / content_location / original。
- **ID 前缀**：`LIT-`（全局唯一，只属本层）。
- **枚举**：文献类型 = 诏敕圣旨/碑文/奏议/书启/诗/记/题跋/序/祭文/其他（封闭+兜底）。
- **执行流程**：整卷抄录长文各算一条；事件层对长文按语义拆事件；title 无题取首句。
- **参考来源**：《水东日记》实例（用户提出，2026-10-10 试点通过）。

### C3 人物关系网络层（REL）

- **定义**：人物-人物二元关系（含方向性与证据）。
- **适用信号**：叙事/轶事/传记密集，人物间同僚/师生/恩怨/举荐/弹劾等关系可提取。
- **schema 要点**：rel_id / item_id / person_a(含 ent_ids) / person_b(含 ent_ids) / relation_type / direction(单向/双向/未明) / evidence / original。
- **ID 前缀**：`REL-`（全局唯一，只属本层）。
- **枚举**：关系类型 = 同僚/师生/姻亲/同乡/同科/举荐/弹劾/恩怨/上下级/父子亲属/敌对/其他（封闭+兜底）。
- **执行流程**：只建文本有直接证据的关系，推测关系不建（宁缺毋滥）。
- **参考来源**：《水东日记》实例（用户提出，2026-10-10 试点通过）。

## 自定义层注册（v3，源自《水东日记》实例增量）

### C4 名录谱牒层（NAM）

- **定义**：表格式名录与谱牒内容的登记——官员题名、同僚题名、迁谪录、族谱家谱话题。
- **适用信号**：笔记/政书/方志中出现分组罗列人名的表格式内容（"X 题名""X 录"），或书信叙事中提及族谱/家谱。
- **schema 要点**：nam_id / item_id / name / category / scope / entries(条目数组：seq/person/courtesy_name/hometown/office 四元组) / ent_ids / original。
- **ID 前缀**：`NAM-`（全局唯一，只属本层）。
- **枚举**：名录类型 = 官员题名/同僚题名/迁谪录/谱牒/题名记/其他（封闭+兜底）。
- **执行流程**：表格式名录整体一条 NAM 记录（entries 数组化）；分列小标题作为行 office 上下文；仅提及无完整表者登记话题（entries 空 + evidence），不强行展开。
- **参考来源**：《水东日记》实例（用户提出"结构分类层"，2026-10-10 试点通过）。

### C5 古今翻译层（TRL）

- **定义**：条目古文 → 现代汉语译文，供理解、检索与图谱注释。
- **适用信号**：任意需要现代译文的古籍/文言文本（与主知识层并行）。
- **schema 要点**：trl_id / item_id / translation / style / note / confidence / original。
- **ID 前缀**：`TRL-`（全局唯一，只属本层）。
- **枚举**：翻译风格 = 直译/意译/注释性翻译（封闭+兜底）。
- **执行流程**：AI 逐条翻译（代码只验覆盖：条目数=翻译数）；专名保留原词+括注；缺字/异体按 norm 归一后译；长文分句群翻译保留分段；支持按卷分步。
- **风格基准（可选项，源自《水东日记》增量）**：实例可指定翻译风格参考并固化为实例内 `references/translation-style.md`。《水东日记》TRL 采用**余光中风格**：译原意不译原字（防死译）/ 主从改并联（长句拆身份相当的短句串连，顺应中文句法）/ 白以为常文以应变（白话为骨干、文言作调剂）/ 精简防冗余（删多余字句、忌"……之一""进行"等翻译腔）/ 善用四字格（自然不造作）/ 忌翻译体公式 / 专名保留+括注（忠实与可读的妥协）。译文交付前按规范清单自查。《五杂俎》TRL 于 2026-10-10 固化同基准（用户指定"固化风格基准，所有翻译都固化成这样"），实例内 `references/translation-style.md` 按本书内容调整示例（书名保留《》、职官术语符合明史口径）。
- **参考来源**：《水东日记》实例（用户提出，2026-10-10 试点通过；2026-10-10 增量指定余光中风格并固化规范）。

## 索引组件注册（v4，源自《水东日记》实例增量）

### V1 卷阅读模式索引（VOL）

- **定义**：卷级启发式标注——为每一卷判定主导内容类型、次要类型与阅读模式，作为执行该卷时分配层优先级与处理方式的前置指引（不是条目级数据层，不占 ID 命名空间）。
- **适用信号**：多卷笔记/文集/政书，各卷内容形态差异大（某卷制度、某卷文献、某卷名录、某卷谱牒），用户希望"按卷针对性处理"。
- **产出**：`references/volume-profile.md`——卷标注表（卷/主导/次要/阅读模式/判定依据）+ 阅读模式枚举与各模式处理指引。
- **阅读模式枚举**（封闭+兜底）：制度优先 / 人物优先 / 文献优先 / 谱牒优先 / 名录优先 / 文事优先 / 均衡全层。
- **执行流程**：① 全书按卷抽样（首尾段+关键词密度）→ AI 逐卷判定；② 固化标注表；③ 执行任一卷前查模式，按其"处理重点"分配抽取优先级；④ 卷完成后对照主导/次要类型检查覆盖缺口；⑤ 与卷内实际不符 → 以实际为准回填修正（registerVersion）。
- **判定方法**：抽样证据（每卷首段+尾段 500 字）+ 关键词密度（题名/录/碑/记/奏/书/诗/诏/谱/图等），AI 判定，词典规则辅助。
- **参考来源**：《水东日记》实例（用户提出"每一卷标注用什么模式阅读"，2026-10-10，38 卷标注完成）。

## 治理组件注册（v5，源自《水东日记》全量执行沉淀）

> 治理组件不是"层"（不占 ID 命名空间、不产出数据层记录），是**质量闭环机制**。≥2 层启用且规模较大时建议配齐。

### V2 人工校验闭环组件（待核清单 + provenance + 同名异人登记）

- **定义**：把"机器/AI 判定拿不准的项"显式登记为待核清单，专家修订后可回写，形成"抽取 → 登记 → 人工核 → 回写 → 版本化"闭环。
- **适用信号**：任何存在歧义判定的大规模抽取——同名异人、复合词形归一、模糊关系、低置信度翻译。
- **产出**：`同名异人待核清单.csv`（ent_id/人名/身份四元组/来源卷/nam_id/原因/建议）；修订回写合并 ENT/改 normalized/修订 TRL，版本化记录。
- **配套字段（provenance 溯源）**：每个记录携带 source（卷-条号）与 evidence（判定依据）；新建实体带 first_source；图谱化阶段逐条可追溯。
- **同名异人登记表**：与 alias_index 分离的独立表；跨卷同名自动收集待核，**人工核前不强行合并**（宁建勿并）。
- **参考来源**：《水东日记》实例任务 A（名录 567 行补建 ENT：新建 391/复用 174/待核 22，2026-10-10 落地）。

### V3 枚举校准机制（收集-报告-暂存 + dry-run 回溯）

- **定义**：枚举值随实例执行动态校准的标准流程，替代"报错终止"。
- **流程**：① 实例先跑，打包器收集未匹配值（不终止，入 pending 表）；② 每卷/每片结束输出枚举使用分布；③ 批处理决议（新增/归并/改名，新增值必须有实例证据）；④ registerVersion+1；⑤ 回溯存量（旧值→新值映射，逐条 dry-run 再 commit）；⑥ 更新快照。
- **配套**：动态回填工具（按映射批量改、dry-run 预览、commit 留痕）；枚举值补"使用说明"（语义+正反例）减少同名不同义误用。
- **升级（v8，2026-10-10 用户决策）**：枚举从"每本书封闭归纳"改为"**基准值 + 新书归纳 + 树状管理**"——基准值继承 `references/enum-library.md`（权威源，树状注册表，只存当前生效值），变更历史与证据见 `references/enum-changelog.md`，归纳流程与树状设计见 `references/enum-induction-guide.md`；值多时按树组织（顶层大类封闭 → 子类 → 叶子，深度 ≤3，父类计数=子类求和）；事件类型明细见 `references/enum-library.md` §1.3。
- **参考来源**：《水东日记》实例（LIT 增"集"/EVENT 增"军政司法边政"/REG 增"祭祀"/APPT_STATUS 增"起复世袭举荐"均待 registerVersion 回溯；执行期 5 次中断的教训）。

## 自定义层注册（v16，源自《明史·食货志》实例 mingshi-shihuozhi-knowledge）

> 《明史·食货志》（明史卷五十三～五十八，6 卷 271 非空行 / 59,118 有效字）实例化新增 1 项结构资产（C16 总账树 LEDGER）+ 1 套 L4 定制四维（QUAN·INST·EVO·FISC）+ REG 制度层 13 属性基准。用户方向：用户 m05345 主动提出六项需求 → m05362 逐项裁定。

### C16 总账树层（LEDGER）

- **定义**：**「逐单位列收支来源」的表格叙事**的结构化树——把一个总账按其内含的层级（总账 → 单位 → 分类 → 明细）组织成树，回答「这些钱都从哪来、各多少」。
- **适用信号**：正文出现**连续的逐单位分列**段，每单位列若干「收入/支出项 + 数额」；典型形态为「X镇：主兵，A若干、B若干；客兵，C若干」这类**分号与逗号分层的复合句**。
- **五层结构**（`LEDGER_LEVELS`）：总账 → **单位**（镇/仓/司/关）→ **分类**（兵种/主客/年度）→ **收入或支出类别** → **明细（数额 + 单位 + 原文证据）**。
- **schema 要点**（节点）：`{ledger_id, level, name, parent, children[], quan_ids[], category, side, amount, unit, evidence, item_id}`；根节点 `parent=""`。
- **ID 前缀**：`LED-`（实例内；跨书复用时按书定前缀）。
- **配套视图**：`_views/ledger_tree.json`（树）+ `_views/ledger_flat.csv`（扁平可筛选）。
- **执行流程（「一把捞」组装器）**：写**独立构建器** `_ledger_builder.py`，由**原文段一次组装成整棵树**（不从 structs 层反向拼），产出树 + 扁平 CSV + 覆盖率报告。
- **四条解析纪律**：①**复合句须按标记切段**——一句含多组「项+数额」，不得只取第一组（承坑 #55）；②**分号是分类分隔符**（`主兵，…；客兵，…`）；③**数额必带约数后缀** `馀 / 有奇` 且可夹在数字中间（承坑 #64）；④**分类值可缺失**——用 `未分` 占位，不得因缺某分类报错。
- **与 REG / QUAN 的分工**：**REG 管制度定义（这是什么制度）**、**QUAN 管单点数额（某项多少）**、**C16 管数额的层级归属（这笔钱属于哪个总账的哪个单位哪个类别）**。三者不重叠：总账树的**叶子挂 quan_id**，不复制数额。
- **跨书适用性**：与书目无关——漕仓账、盐司账、海关税则、边镇年例、工程料估、赈济米谷账，凡「逐单位列收支」皆可复用。
- **参考来源**：《明史·食货志》实例（食货六「九边钱粮总账」13 镇逐镇列主兵/客兵各项来源与数额；用户 m05345 要求「树形图看到这些钱怎么来的」）。

### L4 定制四维：食货财政（QUAN·INST·EVO·FISC）

- **定义**：财政经济志的结构化四维（替代默认 ACT/FRD/LGR/TME 与职官四维 ORG/RANK/LINE/EVO）。
- **适用信号**：正文以**制度与数额**为纲、含大量数量定额与财政流程的书（食货志、财政志、赋役全书、盐法志、漕运志）。
- **维度与结构**：

  | 维度 | ID 前缀 | 结构 | 本书对象 |
  |---|---|---|---|
  | QUAN 数额定额 | `QUAN-` | 数组（**四元组**） | 物品 × 形态 × 数量 × 单位 |
  | INST 制度类型 | `INST-` | 数组（**反指 REG**） | 制度标签，`reg_id` 指向 REG 层 |
  | EVO 沿革阶段 | `EVO-` | 数组 | 阶段切片：初置/定制定型/增改/裁革/复设/变法/弊坏/复原 |
  | FISC 财政流转 | `FISC-` | 数组 | 环节：徵收/起运/存留/解京/内库/边镇/支放/加派/蠲免/折纳/转运 |

- **QUAN 四元组（核心）**：`{item, form, amount, unit}` —— `form` 走「**本色 / 折色 / 银 / 钞 / 钱 / 未明**」；`unit` 须经 `QUAN_UNITS` 映射到**量纲**（容量·重量·货币·织物·土地·计数）。
- **枚举**（见 enum-library §1.24）：`QUAN_FORMS` / `QUAN_UNITS` / `QUAN_ORIGINS` / `QUAN_SIDES` / `INST_TYPES` / `EVO_STAGES` / `FISC_STAGES`。
- **单点真相源纪律**：**REG 是真相源**，INST 用 `reg_id` 反指，**REG 不反记 INST**（防第四次刻画）。
- **约数后缀纪律**：中文数额的 `馀 / 有奇 / 余` 必须剥离，且可**夹在数字中间**（`四百三十馀万束`）——不处理会让整棵总账树静默为空（坑 #64）。

### REG 制度层 13 属性基准（本实例为最完整版）

> 现有政书实例（lgs / xzl / fqh / ppy）的 REG 字段远少于此，**本书的 13 属性可作其他实例的扩充起点**。

| 属性 | 字段 | 类型 |
|---|---|---|
| 制度名称 | `name` | str |
| 所属类别 | `category` | enum（可拓展） |
| 创设时间沿革 | `evolution` + `tme_ids[]` | str + list |
| 主管部门（**可跨库联动**） | `agencies[]` + `cross_kb` / `cross_id` | **list** |
| 征收对象适用人群 | `targets[]` | **list** |
| 征收物（实物·白银·钞） | `levied_items[].form` | **list** |
| 法定税率定额 | `rates[]` | **list** |
| 覆盖范围 | `scope` + `regions[]` | enum + list |
| 文书载体 | `documents[]` | **list** |
| 执行者（品官·役） | `agents[].kind` | **list** |
| 目的 | `purposes[]` | **list** |
| 弊病改革尝试 | `abuses[]` + `opn_ids[]` | **list** |
| 史料来源 | `source` + `item_id` + `evidence` | str |

- **动态追加**：未列入的字段用 `ext_<key>` 前缀，打包器不校验但须登记。
- **配套枚举**：`REG_STATUS` / `REG_QUOTA_TYPES` / `REG_SCOPES` / `REG_LEVIED_FORMS` / `REG_DOCS` / `REG_AGENT_KINDS` / `REG_PURPOSES` / `REG_SOURCES`。
- **跨库联动约定**：`agencies[].cross_kb` 记目标知识库标识、`cross_id` 记目标实体编号（如职官志 `ORG-` / `OFF-`）。**这是工厂首个书间实体对齐机制**。


## 自定义层注册（v14，源自《明史·职官志》实例 mingshi-zhiguanzhi-knowledge）

> 《明史·职官志》（明史卷四十八～五十二，5 卷 319 条）实例化新增 1 层（TME 时间沿革）+ 1 套 L4 定制四维。用户方向：AI 推荐 8 层全建 → 用户拍板"按推荐 8 层全建"；后追加 v2 结构改造（树形/数组）与 v3 员额置信度。

### C14 时间沿革层（TME）

- **定义**：沿革行中的纪年事件点登记——"某年，某机构的某变动"，是全书时间轴；与 L4-EVO 分工：**EVO 为机构视角的阶段切片（横向），TME 为时间视角的事件点（纵向）**。
- **适用信号**：年号纪年密集（本书 562 处），沿革体正文为"初，某年置X。某年设Y…某年改Z"链式表述的史书/政书。
- **schema 要点**：`tme_id` / `item_id` / `era{dynasty,reign,year,order}` / `target(含 ent_ids)` / `action` / `content` / `category` / `related_evo` / `related_org` / `ref_item` / `original`。
- **ID 前缀**：`ZG-TME-`（实例内；跨书复用时按书定前缀，全局唯一，只属本层）。
- **枚举**：`TME_CATEGORIES` = 初置/改置/升秩降秩/废置/复设/改称/裁并/增员/移驻/职掌变更/未明（封闭 + 兜底，本书归纳）。
- **两层结构（推荐）**：第一层 `TMES[]`（纪年事件点数组，AI 写）；第二层**派生时间链** `timeline/<机构>.json`（按 `REIGN_ORDER` 排序的 `chain[]`，打包器生成，AI 不手写）——实现"时间 × 事件 × 机构"拼接。
- **配套**：`REIGN_ORDER` 排序键（见 enum-library §1.21）；与 EVO **双向引用**（TME `related_evo` ↔ EVO `related_tme`），打包器校验一致性，单向报 ERR。
- **执行流程**：纪年正则 `(吴|洪武|建文|永乐|洪熙|宣德|正统|景泰|天顺|成化|弘治|正德|嘉靖|隆庆|万历|泰昌|天启|崇祯)(元|[一二三四五六七八九十百]+)年` → AI 逐条判定 → 一条纪年一记录；同一纪年多变动拆多条共享 item_id。
- **口径**：`year` 存年号内年数（"洪武十三年"→13）；`order` 存 `REIGN_ORDER[reign]`；不做公元换算（史书多不载；如需另设可选 `year_ce`）；无纪年表述 → `era.text="未明"`、`order=99`。
- **与既有 C12 CHR 的分工（重要）**：CHR（年谱纪年索引）为**年谱年条总览**（纪年/岁数/主导类型/要点概括），TME 为**机构沿革纪年事件点**（目标机构/变动类型/变动内容）——**语义不同，不归并、不套用**。
- **参考来源**：《明史·职官志》实例（用户 2026-10-13 确认，试点时间链排序 PASS）。

### L4 定制四维：职官编制（ORG·RANK·LINE·EVO）

- **定义**：机构编制书的结构化四维（替代默认 ACT/FRD/LGR/TME 与政书四维）。
- **适用信号**：正文以机构为纲、含编制表与隶属关系与沿革阶段的书（职官志、会典、官制书、题名录）。
- **维度与结构**：

  | 维度 | ID 前缀 | 结构 | 本书对象 |
  |---|---|---|---|
  | ORG 机构编制 | `ORG-` | **树形**（`children[]` 递归，**深度 ≤4**（v5 放宽：原 ≤3 不够，宦官→十二监→司礼监 + 内层嵌套达 4）） | 机构层级树 + 编制摘要 |

  | LINE 隶属统辖 | `LINE-` | 边表（数组） | 机构间上下与分隶关系 |
  | EVO 沿革阶段 | `EVO-` | 数组 | 沿革阶段切片（机构视角） |

- **枚举**（见 enum-library §1.22）：`ORG_LEVELS` / `RANK_TYPES` / `LINE_TYPES` / `EVO_TYPES`。
- **结构范式（v2，推荐）**：
  - **ORG 树形**：`{name, level, parent, org_type, core_officials, total_posts, note, children[], ent_ids}`；**树内边 = children[]；跨树边 = `superior=="天子"` 不入 children[]，单独登记在 `org_tree.json` 的 `root`**。

## 自定义层注册（v15，源自《明史·职官志》实例增量 mingshi-zhiguanzhi-knowledge）

> 用户在交付后用 8 类真实查询反向验收，发现 **3 问答不了（上级官职 / 下级官职 / 平级官职）**，根因是「把机构当唯一骨架，官职只是节点上的 `posts[]` 数组元素」——无 ID、无父子关系，L1 已标注的 `official` 实体无索引可用。用户 m02343 四项裁定（**① 建立 ② 覆盖全部官职 ③ 平级 = 同机构同品级不跨机构 ④ 俸禄做成物品/数量/量纲，且分「官品的薪水（保底）」与「实际的薪水（没有就不填）」两层**）后新增本层。

### C15 官职层（OFF）

- **定义**：**官职作为独立实体**的层——每个官职独立 ID，带所属机构、品级、员额、两层俸禄、平级集合、官职间关系边。与 L4-ORG 的分工：**ORG 是「机构」的树（组织视角、包含关系）；C15 是「官职」的图谱（职名视角、同僚与副贰关系）**。
- **适用信号**：书目含「某官之上/之下/平级有哪些」「某官的俸禄/待遇」类查询需求；正文出现官职对官职的直接上下级表述（「A…。**B佐之**」「以A任…，**B贰之**」「为**首领官**」「**兼领**」）。
- **载体**：全局单文件（不按卷切），如 `_layers/structs/officials.json`。
- **schema 要点**：
  ```python
  {"official_id":"OFF-773", "office":"右侍郎",
   "org_id":"ORG-509", "org_name":"兵部", "org_path":["兵部"],
   "grade":"正三品", "grade_order":5, "count":2,
   "item_ids":[…], "rank_ids":[…], "sources":["ORG","RANK","ENT"],
   "salary":{"grade_based":{…}, "actual":null},
   "peers":["OFF-774"], "relations":[], "subordinates":[]}
  ```
- **ID 前缀**：`OFF-`（实例内全局顺序；跨书复用按书定前缀）。
- **三层语义（关键，缺一即设计不完整）**：
  | 关系 | 定义 | 来源 | 陷阱 |
  |---|---|---|---|
  | **`peers` 平级** | **同机构 + 同品级**，**不跨机构** | 用户裁定，**必须显式确认** | 不定义清楚会退化为「同品级列表」（「吏部郎中」vs「户部郎中」同品级却非平级）；须在**校验器硬校验** |
  | **`relations` 上下级** | `副贰`/`首领`/`兼领`，**只建有原文显式表述者** | 原文关系句 | **古汉语「B佐之」中 B 才是佐者**（主语在后），方向极易判反；且**关系条 ≠ 编制条**，须回溯 `owning_item` 定语域 |
  | **`subordinates`** | 反向边（谁以本官为上级） | 由 `relations` 派生 | — |
- **俸禄两层结构（v15 新增通用模式，可复用于任何「待遇/俸给」场景）**：
  - 统一量纲化：`{item, amount, unit, form, era_text, era, source, note[, duty]}`（用户原话「做成**物品、数量、量纲**这样的形式」）。
  - `salary.grade_based` = **保底**（按品级从品级—待遇对照表查得，**恒有**）；
  - `salary.actual` = **实际**（该官职的特殊发放，**没有就不填 `null`**，**严禁臆测默认值**）。
  - 适用面：俸禄/薪饷/赏赐/配额等一切「按等级有保底、个别有特例」的定量制度。
- **准入判据（重要，勿误用）**：
  - **覆盖全部官职**（用户 m02343 明确要求）——不因「无原文关系表述」而省略节点；
  - 但**关系边**只建有原文显式表述者，**不按品级相邻自动连边**（那是 ORG 树已表达的**组织包含关系**，重复建边是冗余且方向无意义）；
  - **回溯落回自身时不得兜底**（如卷首总述），须只记 evidence 不建边，**严禁**退化为「按名字取首个匹配」（会静默产生错边）。
- **未配对表述留档**：回溯后仍未配对的关系表述**全部写进报告**（含理由 + 原文窗口）供人工判。**留档 ≠ 失败**，是按纪律拒绝臆测——本实例 410 处命中 → 去重过纪律后 **16 条边**，**13 条留档**。
- **前置依赖（务必写进管线）**：
  - **子机构必须有 ID**——ID 分配器通常只作用于顶层记录，`children[]` 子节点会被漏掉。须按「父 id + 子序号」派生（`ORG-505#1`）。
  - **`posts[]` 元素须带所在节点自身 id**（叶子**不继承**父 id，否则抹平叶子差异）。
  - **回填须覆盖所有来源**——本实例只回填了机构树、漏了品级员额层，导致「侍郎」全部无归属、「尚书→侍郎」6 条边全丢。
  - **两处 ID 空间必须同源**——第二个遍历器须**优先沿用已有 `id`**，不得自行合成。
- **查询视图（推荐）**：`officials_flat.csv`（扁平表，含 salary_base_* / salary_actual_* / relations / peers 列）/ `official_tree.json`（按机构归组，组内按品级排序）/ `official_by_grade.json`（品级倒排）。
- **执行流程**：三路合流（ORG 节点 `posts[]` + RANK `posts[]` + L1 `type=="official"` 标注）→ 去重归一 → 分配 ID → 回填 org_id/品级 → 算 `peers` → 匹配 `relations`（含 `owning_item` 回溯）→ 填两层俸禄 → 派生视图。
- **参考来源**：《明史·职官志》实例（用户 2026-10-15 m02343 四项裁定，v10 建成，实测 1241 节点 / 16 边 / 278 有平级 / 33 条实俸）。

### C17 卫所树层（WEI）

- **定义**：**「树枝状编成清单」的结构化树**——把一个编成体系按其内含层级（府 → 在京/在外 → 都司/直隶 → 卫 → 千户所）组织成树；**同一对象的多个版本清单分树建模**（`list_ver`），回答「某卫属哪府哪都司、某都司下辖哪些卫所、两版差异是什么」。
- **适用信号**：正文出现**连续的层级编成段**（如 `◎五军都督府 → ◎左军都督府 → 在京 → 在外 → △浙江都司 …卫列`），卫列长行**无分隔符**（`杭州前卫杭州右卫台州卫…`）且**括注紧贴**卫名（`(调北京)`/`(革)`/`(后为临清卫)`）。
- **双清单分树（核心，源自本书）**：旧编成（洪武二十六年定）与后定编成各建一棵树；`name_norm` = 卫名归一（去方位字：`金吾前卫`→`金吾卫`），对照结果入派生视图 `_views/weis_diff_<都司>.json`（旧有/新有/两树皆有三态）；**凡两树同卫名但沿革注不同，以 `src_loc` 保留双证据，不合并覆盖**。
- **schema 要点**（节点）：`{wei_id, name, name_norm, list_ver, level, parent, children[], notes[]（括注数组）, count_marker, src_loc, confidence, ai_review}`；根节点 `parent=""`。
- **ID 前缀**：`WEI-`（实例内；跨书复用时按书定前缀）。**注意：与 L4-WEI 编制维共用前缀属设计事实**——ID 校验器 `assert_unique_ids` 须豁免 `("ENT-","WEI-")` 对（C17 树节点与编制维引用同源）。
- **配套机制**：`WEI_NAME_INDEX` 同名词典（括注锚点预扫 + AI 复核渐进回填，**不一步到位**）+ 括注锚点切段器（`_weisuo_builder.py`）+ 双树对照视图。
- **执行纪律（解析器只产候选）**：①无分隔长行**不硬猜边界**——括注锚点断开 + 词典最长匹配，未解段整段标 `ai_review=required` 由 AI 逐卫 split（坑 #54/#55 卫列场景复发）；②**括注 ≠ 卫名**，剥离后进 `notes[]`/C14，且括注是硬边界（括注后必为新卫名开头）；③**`已上`/数量行是区块级信息**，只挂区块节点不复制到每个卫；④**含句读行是说明段**，但须**先剥离括注再判**（括注内句读 ≠ 行级句读）；⑤南京/羁縻等异区卫所**分属独立子树不得混挂**；⑥数量行（`卫三百八十四`）走 QUAN + count_marker。
- **跨书适用性**：抽象与书目无关——凡「**同一对象有多版编成/名单/目录**」的古籍皆可复用（兵志卫所、会典两京制度、实录职官、赋役黄册、钞关商则），抽象层级高于「卫所」本身，亦可称**双版本对照树**。
- **参考来源**：《明史·兵志》实例（卷66 卫所双清单；无分隔长行实测覆盖率 8.1%→99.5+%，见实例 pilot-plan.md）。

## 自定义层注册（v9，源自《蘧编》实例 qubian-knowledge）

> 《蘧编》（明·叶向高编年体年谱，1559–1627，21 卷 76 条）实例化新增 2 层。用户方向：选"完整包+年谱纪年索引层"（八层全建）。适用信号均为本书实测（全书大半为"疏辞/具揭/乞休 → 得旨/奉旨/传谕/圣谕"往来；71 个年条节标题即年号纪年）。

### C11 奏疏谕旨互动层（MEM）

- **定义**：君臣互动链登记——臣下上疏/具揭/条陈与皇帝谕旨/批答/传谕的往来记录（issue → response → result）。
- **适用信号**：年谱/实录/奏议集/政书中"臣疏 → 君批"往来成体系（"疏辞/具揭/乞休 → 得旨/奉旨/传谕/圣谕"句式密集）；本书为最大内容特征（后记自述"所记十九皆求去之疏，慰留之谕"）。
- **schema 要点**：mem_id / item_id / actor(含 actor_ent_ids，上疏之臣) / target(含 target_ent_ids，皇帝) / type / issue(议题要点，AI 解读) / response(批答要点，AI 解读) / result / original。
- **ID 前缀**：`MEM-`（全局唯一，只属本层）。
- **枚举**：互动类型 MEM_TYPES = 上疏/具揭/条陈/谕旨/批答/传谕/面奏/其他；结果 MEM_RESULTS = 允准/不准/留中/改拟/慰留/未报/其他（封闭+兜底，本书归纳）。
- **执行期决议（v10，源自《蘧编》全量执行）**：MEM_TYPES「密揭 → 具揭」归并（密揭为秘密具揭，不新增值，本书 05-001 考选密揭）；MEM_RESULTS「允准（X）→ 允准」归并（括注信息移入 response 字段，共 4 处）；MEM_RESULTS 新增「不允」（皇帝不允辞/不允所请，年谱辞疏批答常态，证据 02-005/03-001/04-001/05-001 等多数批答）。
- **执行流程**：触发词表（臣方：疏辞/再疏/具疏/具揭/条陈/乞休/求去/引罪；君方：得旨/奉旨/奉圣旨/上传/上谕/圣谕/传谕/批出/留中/不报）→ 正则候选 → AI 复核；一条 MEM = 一次往来，一条目多往来拆多条共享 item_id；完整谕旨文本另归 LIT（LIT 收文献文本、MEM 收互动链）；皇帝主动下发（非回应）也登记（actor 为皇帝）。
- **参考来源**：《蘧编》实例（用户选"完整包"时确认，2026-10-10 试点通过）。

### C12 年谱纪年索引层（CHR）

- **定义**：按年（节）一条总览——纪年信息、主导内容类型、要点概括与跨层引用（ref_events/ref_appts）。
- **适用信号**：编年体年谱/实录/日记（节标题即"年号+干支+公元+岁数"，天然时间轴）。
- **schema 要点**：chr_id / item_id / era(年号+干支) / year(公元，未明"未明") / age(岁数，未明"未明") / category(主导类型) / summary(AI 要点概括，非原文) / ref_events(引用事件层 ID 数组) / ref_appts(引用任职层 ID 数组) / first_person(是否第一人称亲历) / original。
- **ID 前缀**：`CHR-`（全局唯一，只属本层）。
- **枚举**：主导类型 CHR_CATEGORIES = 幼年行迹/科举应试/宦途任职/朝政事务/乞休辞官/家居闲适/营建修造/家事姻亲/病逝后事/其他（封闭+兜底，本书归纳；他书按阶段调整）。
- **执行期决议（v10，源自《蘧编》全量执行）**：CHR_CATEGORIES 新增 5 个组合值——家事（纯家内事件年：10-003 弟亮卒/19-001 为亡妻造赐塋）、家事居乡（里居兴造营建：10-001/10-002）、家事边事（家事与辽事并重：10-004/10-005）、家事朝政（居乡而朝政主导：10-006/17-001）、朝政家事（朝政为主兼家事：18-001）；registerVersion v3。年谱体一年常兼家事/朝政/边事多线，组合值优于单一主导值。
- **执行流程**：年条各 1 条 CHR（与节一一对应）；category 取该节主导内容类型；summary 只写要点不抄原文；ref_events/ref_appts 在 EVT/APPT 完成后回填（跨层引用）。

### C13 文书条目层（DOC）

- **定义**：文书式条目的体例登记——"某文书长什么样、写给谁、程式如何"（状词/票单/册簿/牌批/谕告/结状/启禀）。
- **适用信号**：政书/官箴书/幕友书中"文书式"内容形态成体系（状式/票单/结状/谕告/启禀等文书体例密集）；本书刑名部卷13~21 状词/票单/结状为全书骨架（状式 60+），卷33 禀启附 33 篇全为启禀（四六大启 20+四六小启 13）。
- **schema 要点**：doc_id / item_id / name / category / issuer(含 issuer_ent_ids) / recipient(含 recipient_ent_ids) / format(程式结构，AI 解读) / purpose / original。
- **ID 前缀**：`DOC-`（全局唯一，只属本层）。
- **枚举**：文书类型 DOC_TYPES = 状词/票单/册簿/牌批/谕告/结状/启禀/其他（封闭+兜底，本书归纳；已入 enum-library v7 §1.19）。
- **执行流程**：文书条目按"体例实例"建模——name 取文书名（状式名/票单名等），format 写程式要点（如状式"首列告状人→被呈状人→干证→状由→结状"），不手抄全文（原文锚点走指纹库 original）；卷33 骈文书信按篇成条、doc 为主战场；与 L4 LGR 维度分工——LGR 收文簿台账**体系**（簿册/账册/格叶），DOC 收单件文书**条目**（体例/程式）；与 L1 分工——L1 标文书名实体（type=doc），DOC 记条目级体例描述。
- **参考来源**：《福惠全书》实例（用户提出"文书式按文书条目建模"，2026-10-12 试点通过，206 条全量）。
