# 方法论：层候选池、反思选择与操作原则

> 本文是"书籍知识工厂"的方法论底座，源自《新官轨范》数字化工程（明代官箴书 → 多层可溯源知识资产）的实战沉淀，已抽象为适用任意书籍的通用方法。

## 0. 工厂与实例的两层关系

本技能是**工厂（meta-skill）**，产出物是**书实例 skill**，两者职责分离：

| | 工厂（book-knowledge-factory） | 书实例（如 xinguan-guifan-knowledge） |
|---|---|---|
| 何时出现 | 用户传书时说"形成规范/技能" | 工厂实例化后，用户说"处理《X》"时 |
| 职责 | 结构性探查 → 引导式反思 → 固化实例 skill | 按固化的规范执行：底座→抽取→整合→交付 |
| 产出 | **一个新的 skill** | 知识文件 + 报告 |
| 使命 | 交付实例 skill 后退出 | 可反复调用、扩展数据 |

工厂不产出执行命令或知识文件——那是实例 skill 的职责。实例化后，通用方法论仍可引用工厂 references，但该书特有的 schema/枚举/触发词/模板固化在实例内部（自包含）。

## 1. 层库引导（Layer Library）——层是设计出来的，不是预设的

底座（章节拆分 + 条目指纹库）是**公共地基，任何书都做**；其上的"层"按书设计。工厂提供**层库（引导参考板）**，由 Phase ② 引导式反思决定每本书启用哪些：

```
公共地基：底座（章节拆分 + 条目指纹库）
层库参考：L1 实体 → L2 规则 → L3 流程 → L4 结构化 → L5 事件（+ 自定义层）
公共收口：跨层索引（启用 ≥2 层时必做）
```

**为什么不能固定层级**：《新官轨范》的事件层不是预设层——是用户提出"事件五元组 Registry"后才做的；结构化五维也是用户问"除了流程整理外还可以怎么结构化？"后讨论选定的。传一本字典过来，没有事件时序，就没有事件层；传一本史书，叙事成体系，才值得建事件层。**任何层都要能回答"这本书为什么建/为什么不建"。**

### 引导式反思（Phase ②，顺序不可颠倒）

1. **先问用户**：基于结构性探查发现，请用户先说想法——"这本书你想结构化哪些方面？"（用户方向无条件列候选并记录来源）。
2. **给层库参考**：展示 `references/layer-library.md` 中与本书信号匹配的参考层（适用信号 + 示例），作为引导，不是推荐必选。
3. **再让用户想**：请用户提出层库之外的自己的想法（人物关系网络/地名沿革/引文索引……），完整开放。
4. **AI 补证据**：每个候选层给出"建的理由 / 不建的理由 / 数据支持检验"。
5. **确认锁层**：候选层清单（标注"用户提出 / 层库参考 / 自定义"）交用户拍板，可增删调整；确认结果固化进实例 skill 的"反思记录"节。

> 层模板细节（定义/适用信号/schema/ID/枚举/执行流程/变体/参考来源）见 `references/layer-library.md`；通用 schema 规范见 `references/schemas.md`。**仅对确认启用的层写 schema、写源数据、建打包器**；未启用层不做任何动作。

## 2. 十条操作原则

1. **结构性探查**：工厂阶段读目录/序跋/凡例 + 抽样（首/中/尾卷）+ 密度信号统计，够设计用即可；全文逐条精读留给实例执行，不与执行重复读。
2. **先锁 schema 再写数据**：字段口径、枚举、ID 规则一次性定死；源数据按 schema 编写，打包器注入指纹/关联/校验。
3. **AI 判定与代码验证严格分工**：判定逐条人工（AI）完成；代码只验缺漏（覆盖/格式/引用/枚举/对齐）。
4. **所有生成器正式化**：`build_` 前缀 + 可重跑 + 幂等；修复并入生成器，不落一次性散文件。
5. **验证一次到位**：校验脚本写文件输出，重跑前先确认不会覆盖已修复字段。
6. **枚举单点治理**：新增枚举值必须版本+1 并回溯存量（registerVersion 模式）。
7. **方向假设先确认**：粒度（卷/条/段）、判定方式（AI/规则）、交付形态（JSON/CSV/文档）、**层清单（含不建层的理由）**在开工前问清。
8. **交付按层聚合**：按层一组（归一汇总 + 验证清单 + 卷示例 + 跨层索引），不逐件散交付。
9. **每轮任务建 task 清单**：阶段可见、完成可核。
10. **如实报告缺口**：数据不足处写"哪里缺、缺什么、补什么方案"，不静默降级。

## 2.5 学习回路（记录强制，入库有门槛）

每次实例化一本书都会产生新经验；**记录是强制的，进正式库是有门槛的**——防止单本书的特殊经验无评审地污染跨书基准库：

1. **强制记录**：探查/反思过程与用户原话 → `case-feedback-<book-slug>.md`（实例只固化结论，过程不进实例）；候选新层/新坑/新枚举/模板改进 → 以提案写入 `references/pending-review.md` 待评审提案区（附证据）。
2. **评审合并**：满足三条件——① 跨书复用潜力（≥2 本书用得上，或方法/纪律类天然通用）；② 与既有条目不冲突，归并优先于新增；③ 用户确认——才移入对应库正式区（`layer-library.md` / `pitfalls.md` / `enum-library.md` / `assets/templates/`），该库版本行+1；不满足 → 留待评审区观察或驳回留档。
3. **设计级教训**（影响实例骨架的，如 ID 分配/增量语义/写盘纪律）：评审通过后同步母版与检查单，不能只进坑库。
4. 各库版本行支持回滚（合并引入问题回退上一版本）；实例 skill 不受学习回路影响（自包含）。

## 3. 分工边界（判定 vs 验证）

| 环节 | 谁来做 | 说明 |
|---|---|---|
| 条目判定（实体/规则/流程/结构/事件） | AI 逐条 | 核心智力工作，不可用代码规则引擎替代（代码引擎结果仅作候选，须 AI 复核） |
| 原文注入（original/norm） | 打包器（代码） | AI 源数据只写条号/解读，杜绝手抄漂移 |
| 覆盖/格式/引用/枚举/ID 校验 | 验证脚本（代码） | 输出"验证缺漏清单"，问题数必须为 0 |
| 枚举版本 + 存量回填 | 代码 + AI 复核 | registerVersion 模式 |

## 4. 数字口径（汇报/校验用）

- 每层总量、ID 范围、校验结果（0 issue）写进数字总表。
- 槽位引用覆盖率（如"规则 subject 227/273"）如实汇报，不四舍五入成 100%。
- 未建模/未命中项（如"01 卷 44 条未建模事件"）单列缺口，不并入总量。

## 5. 与用户偏好的双库架构对接

用户项目（kgWorkflow）采用 WorkflowCore(kg_wf) + SqlSugar(kg_ming) 双库，统一基类 WorkflowStepBase，架构见 docs/ARCHITECTURE.md。书实例产出的知识资产如需落库，将启用层归一汇总按 kg_ming 表结构导入、将流程步骤链按 kg_wf 工作流注册；此步骤在实例执行完成后按用户要求执行，非默认动作。
