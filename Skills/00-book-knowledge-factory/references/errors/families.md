## 工程侧四族（A/B/G/P）——已落成骨架代码

### A 族｜「校验通过」≠「数据可用」　`engineering`
**共同根因**：验收指标测的是「层内自洽」，不是「用户要查的东西在不在」。
**子型**：A1 字段空转（#45/#56）｜A2 解析器静默丢组（#55/#35）｜A3 映射静默失配（#28/#29/#19）｜A4 计数器与真相源不一致（#46）｜A5 验收口径本身错（#50/#20/#49）｜A6 把关者自身没被验证（#62）｜A7 自检喂的形状 ≠ 生产形状（#63）
**纪律**：① 交付另报**字段填充率表**与**目标查询问句逐问验收表**，与 ERR/GAP 并列；② 填充率为 0 的排查顺序固定为「**是否被调用 → 解析覆盖面 → 最后才接受『原文确实没有』**」；③ 索引/适配器改键名后跑「各层条数 vs 索引层计数」对账；④ **凡新增「把关者」（校验器/回填器/护栏/断言），其有效性必须由可重跑自检证明**（正反例各一）；⑤ **测试替身只允许替换「数据内容」，不允许替换「容器的类型/形状/键名」**。
**装置**：`FieldCoverage` / `assert_no_silent_zero()` / `query_acceptance()`

### B 族｜键名 / ID / 编号：命名是隐形契约　`engineering`
**共同根因**：命名在源数据、打包器、适配器、注册表四处分头书写，**无单一来源**；单复数与硬编码序号会静默错位。
**代表**：#5 ID 对齐断裂｜#13 业务 ID 撞号｜#39 序号取自 `slot`（50 条规则只有 9 个唯一 ID 全撞 `ZG-R-501`）｜#22 段容量按卷条数估｜#23 源 `chr` vs 容器 `chrs`（前 5 卷漏打包）｜#28 目录复数 vs 索引槽位单数（7 层静默空回填）｜#54 子机构无 ID（446/869，`右侍郎@兵部` 与 `@南京兵部` 不可区分）
**纪律**：① **ID 分配权归打包器**——源数据只写槽位；② 派生节点与父节点**同一分配器**（`<父ID>#<序号>`），两处遍历器不得各自合成；③ 目录名 + 文件名前缀 + 索引槽位名**三处统一复数**。
**装置**：`LAYER_SPECS` 四处同源 / `assign_ids()` / `assign_child_ids()` / `check_naming_consistency()`

### G 族｜写盘幂等性 / 原子性缺失　`engineering`
**共同根因**：打包器只有「全量重建」语义，没有「增量合并」语义。
**代表**：#12 单卷复跑把指纹库从 **1197 条抹成该卷条数**｜#14 并行子代理半写与汇总竞态｜#2 产物覆盖回归（P0 修复用一次性脚本落在生成器之外，重跑丢失）｜#3 original 手抄漂移｜#24 卷号映射依赖读取顺序（残留旧映射致验证合计虚高 147 vs 真实 76）
**纪律**：① 所有 build 脚本统一增量语义（带 `--volumes` 则「加载现有 → 只重算请求卷 → 合并写回」）；② 写文件一律「临时文件 + rename」；③ **修复必须并入正式生成器**（`build_` 前缀、幂等），不落一次性散文件；④ AI 源数据只写条号/解读，**原文由打包器从 `_item_registry.json` 注入**。
**装置**：`atomic_write_json/text()` / `merge_layer()` / `merge_shared_json()`

### P 族｜流程与语境失配　`engineering`（唯一「装置只能减轻、不能根除」的族）
**共同根因**：做法本身没错，但用在**错的场景 / 错的语境 / 错的口径**上；症状常表现为「效率损失」或「归层错误」而非数据错误，所以容易被漏记。
**代表**：#1 重复探查（**最高频**）｜#6 环境噪声致验证读不全（「显示乱码」≠「文件坏了」）｜#7 规则引擎喧宾夺主（可切分 ≠ 该抽）｜#16 TRL 长文滑向翻译体（代码只能验覆盖验不了风格）｜#36 编制清单被误建 NAM｜#48 量纲前缀误读（「一千四十四石」读成 144 或 1444）｜#51 「平级」不定义就退化成「同品级列表」｜#61 台账未回填致行数被误读为待办数｜#64 中文数字不认约数后缀（「十三万二千馀石」静默返回 `None`，整棵总账树为空）
**纪律**：① 探查须有**终止条件**（同结论不再变化即停）；② **可切分 ≠ 该抽**——层准入判据写「语义条件」而非「形态条件」；③ **影响范围可枚举时，定义必须落到校验器**（如「平级」）；④ **数值/单位类解析一律单点函数化**，且**先枚举本书实际书写变体再写实现与自检**；⑤ **记录与动作同时完成**。
**装置**：`SemanticGate`（锚定匹配）/ `cn2int()` / `drift_ratio()` / `ProbeTracker` / `check_enum()`

## 语义侧十二族（C–F / H–O）——靠判据，不能靠装置

> 这 12 族与书的文体强相关，**无法预先写进骨架**。三条通用判据：**方向先验 / 映射显式化 / 判据写语义**。

### C 族｜语义判据方向判反 / 粒度选错　`semantic`
**根因**：判据选错了维度，或方向搞反；**错了以后数量往往正常，计数发现不了**。
**代表**：#52 关系句主宾判反（古汉语「司历、监候佐之」**主语在后**，首跑配成「尚书佐侍郎」）｜#32 多模式分类器优先级写反｜#47 用全串匹配判语域（`"留守司。" in scope_text` 致 `05-051` 漏填 3 条世官）｜#57 把「机构地位排序键」当「包含关系约束」（v5/v8/v12 三次加 `if` 特例）｜#42 层级用「严格递减」而非「非递减」｜#40 层级枚举混装中央/地方（`府` 兼指宗人府与府州县）
**纪律**：① **方向先验、数量后验**；② 多模式分类器的**判定顺序本身是设计的一部分**（高频常见句式必须排在低置信桶之前）；③ **语域闸门锚定位置**（`startswith`）；④ **每次要加 `if` 特例时先问「地位排序还是包含关系」**；⑤ 层级校验的价值上限是「拦住明显笔误」，不该期待它验证语义正确性。

### D 族｜枚举 / 字段与库不一致　`semantic`
**根因**：枚举单点（`_kg_enums.py`）未随实例原文校准，**缺值即报错或静默吸收**。
**代表**：#4 枚举口径漂移（注释 41 值 / 代码 43 值）｜#15 枚举校验「报错终止」致《水东日记》**5 次中断**｜#27 封闭枚举执行期被就地吸收（事件 23→111 种、文献 11→114 种、名录 **100% 库外**）｜#34 职掌陈述句被抽成规则
**纪律**：① 校验改**收集-报告-暂存**（未匹配值入 pending 不中断）→ registerVersion+1 → dry-run 回溯 → commit；② 但**打包前**对封闭枚举做 `value ∈ ENUM_SET` 硬校验；③ 验证报告输出每层「值种数 vs schema 定义数」，比值 > 1.5 判口径漂移；④ 顶层太粗会迫使 AI 自造顶层——宁用「顶层封闭 + 子类开放登记」的树状（深度 ≤3）。

### E 族｜「条目 → 目标」映射被默认为一对一　`semantic`
**根因**：抽取时假设「目标所属 = 该条目所属」，靠**文本位置**推断，多目标共处一条时必然错。
**代表**：#53 关系句所在条目 ≠ 该关系所属编制条目（须回溯 `owning_item`，跨卷不回）｜#60 沿革与机构无关联字段（273 条仅 101 条查得到；`01-016` 一条含 5 条沿革属六部共有，而六部 ORG 在**另外 6 条**）｜#59 派生机构（内阁）未挂回母机构（翰林院）成孤岛｜#37 通用机构被另立模板排除在 ORG 外｜#44 ORG 树与 LINE 边表未同源（补 74 个节点缺 107 条边）
**纪律**：**凡「条目 → 目标」映射都要显式建关联字段，不得依赖文本位置**。① 沿革用 `owner_orgs[]` **可多值**；② **个体名优先于集体名**（否则单独沿革被吞进"六部全体"）／**集体名须用显式触发形态**（原文 `吏、户、礼、兵、刑、工六部` 是**并列单字**，成员全名一次不出现）／**去重按 `name` 不按 `id`**；③ **树是单一真相源**，新增子节点须同步补边；④ 挂回母机构须**三处同步补齐**（`parent` + 母机构 `children[]` + LINE 边）。

### F 族｜字段值语义不足（空值不携带信息）　`semantic`
**根因**：**字段存在 ≠ 字段有值 ≠ 字段的值可解释**。A 族讲「该有值却没有」，F 族讲「有值但值不够用」。
**代表**：#58 「归属留空」与「判定为无归属」共用一个值（1241 官职节点 387 个 `org_id=""` = 31%，**绝大多数是正确留空**）｜#46 全书性表无处安放（5 张表被整体跳过）｜#21 年谱年龄双轨口径误判（虚岁 = `chr.age`+1，属设计非 bug）｜#11 外部资料与用户文件不一致（**以用户文件为唯一权威来源**）
**纪律**：① 用「空串」表达两件事是设计缺陷——须拆成**具名类别**（`org_binding`：`机构 859 / 未明 253 / 差遣军职 112 / 封爵 12 / 土官 10`）+ 理由字段；② 完成率须**剔出「不适用」做分母**；③ 分类判定放**最终化阶段**（各来源合流后），不可在单路 `add()` 时做；④ 双轨口径须**单点书面声明**。

### H 族｜切分口径按书而异、首次估算常错　`semantic`
**根因**：每本书的符号体例/OCR 质量不同，**底座切分不能复用同一套规则**。
**代表**：#33 无条级标记文本的「行=条」口径（漏计 `◆` 章标记 5 行：324→319→正式 **317** 条）｜#17 名录卷「行=表格行」与条目切分的张力（题名表一行多人）｜#18 CSV 物理行 ≠ 逻辑行（译文含换行，**1313 ≠ 1192**）｜#24 同前
**纪律**：① 动工先查 `_item_registry.json` **实切条数**，不按标题数/非空行数建 task；② 估算基准必须是「**非空行 − 全部标记行**」（首跑拿实切数与非空行数比，**误报 3 处「超 5%」**）；③ 名录/表格卷的切分在底座阶段用 `mode_hint` 前标注；④ **计数一律按逻辑行**（`csv.reader`），不数物理行。

### I 族｜源文本污染（编码 / OCR）　`semantic`
**代表**：《明会典》OCR 系统性误识（`会→防`、`御→防`；卷 128/129/130 标题漏识别）——「**不归一，后续实体识别全错**」｜《平平言》GBK 合并源文件（PowerShell 直读乱码，须实例内统一 UTF-8 重合并 + 可重跑脚本）
**纪律**：**底座归一阶段就必须处理错字与编码**，不能留给下游。

### J 族｜规模与上下文　`semantic`
**代表**：《明会典》教训 1「**大书必须分卷组执行**」（85 万字 / 2.5MB / 26608 行全量载入爆上下文 → 分 G0–G8、每组 ≤64 卷）｜《水东日记》TRL 长文翻译体风险（代码只能验覆盖验不了风格）
**纪律**：规模超出单次上下文时**分组执行 + 预先设计分段/截断保护**；风格类质量留给**人工复核闭环**兜底。

### K 族｜层级结构设计　`semantic`
**代表**：#43 `children[]` 深度上限预设为 ≤3（宦官→十二监→司礼监 达深度 4）｜《明会典》「25 个平铺层会让执行时迷失」
**纪律**：**树深上限不可预设**，须由原文实测；层组织用**父子树**而非平铺清单。

### L 族｜核查器自身缺陷　`semantic` / `engineering`
**代表**：#38 校验器维度分派顺序写错（`if "posts" in r` 优先分派 RANK，转正 ORG 节点同时带 `posts[]` 与 `children[]` → **120 条假 ERR**）｜#9 覆盖缺口被掩盖（某卷 94 条只建模 50 条，用户误以为全量完成）｜#25 实例增量不走工厂（增量成「野分支」）
**纪律**：① 维度分派顺序**定死** `children`（ORG）→ `change_type`（EVO）→ `line_type`（LINE）→ `posts`（RANK），else 报「无法识别维度」；② **假 ERR 指纹**：值全为 `None` 且集中于一批新记录 → 是「字段根本不存在」而非「值非法」，**先怀疑分派**；③ 未建模/未命中项**单列缺口清单，不并入总量**；④ 已交付实例的一切规范级变更走 `increment-upgrade.md` 七步。

### M 族｜AI 流程与上下文卫生　`semantic`
**代表**：#0 把工厂当执行器（**定位错误，最根本的坑**）｜#0.1 层模板套用（层是设计出来的，不是预设的）｜#26 把反思过程全量塞进实例（实例是**执行规范**，不是会议纪要）
**纪律**：工厂流程止步于「生成书实例 skill」；反思阶段**逐层回答「为什么建/为什么不建」并给数据证据**；实例反思记录只固化**结论与锁层依据**。

### N 族｜操作事故　`semantic`
**代表**：#41 LINE 边表节点名与 ORG 树不一致（树内 `验封清吏司` vs 边表 `验封司`）｜#31 树与边表互校未划「树内边/跨树边」（根机构直隶「天子」的边不在 `children[]` 内 → 首跑误报）
**纪律**：① 跨树引用**必须用节点主键而非名称**；② 树表互校前**先定死哪条边属于树、哪条属于跨树参照**；③ 多行字典用行级编辑工具删改时，**必须以完整记录为单位（含首行）**。

### O 族｜粒度 / 交付形态　`semantic`
**代表**：#8 粒度反复（先按段 620 段做，用户改口「既然做了条，就用条的」，返工）｜#10 交付散件淹没重点（每层每卷 12 件 × 5 层逐件 present，用户找不到入口）
**纪律**：方向性假设（粒度/判定方式/交付形态）**开工前跟用户确认**并写进《操作指南》第 0 节；交付**按层一组**（归一汇总 + 验证清单 + 卷示例 + 跨层索引），6 组以内。

## 元教训（跨族，最值得记住的两条）

1. **建表本身暴露的**：首版归族时 **#1 / #6 / #7 / #16 / #36 / #48 / #51** 七条**无处可归**——说明**分类学的作用不只是整理已知，它还会暴露「哪些坑连归类都归不进去」**，而那些往往最容易被反复忽略。
2. **同型坑第 2 次出现 = 升级为通用纪律**（不是再记一条症状）：#45→#56（A 族）、#53→#60（E 族）、#48→#64（P 族）都是同型复发。**复发说明检查单缺失，故对策必须写进检查单或骨架，而不是坑库。**
