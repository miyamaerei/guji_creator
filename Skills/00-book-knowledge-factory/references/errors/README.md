## 〇、三条不必读档案的理由

工厂里有两个反复出现的**元教训**，它们解释了为什么"档案变厚"反而是危险的：

1. **纪律写在文档里 = 下一个实例必然重踩**（#45 首记后 #56 复发，第 2 次才落进骨架）。
   → 所以 A/B/G/P 四族的纪律**已经全部变成代码**（`assets/skeletons/packer_skeleton.py`）。你要做的是**复制骨架**，不是读 65 条坑。
2. **「写了装置」≠「装置有效」**（#62：护栏自己首轮自检就抓出 4 个真缺陷；#63：自检替被测对象换了容器类型，缺陷照旧出厂）。
   → 所以护栏必须跑 `self_test.py`。**跑自检 > 读文档**。

## 一、快速分诊表（出问题时按症状查）

|---|---|---|

## 二、A/B/G/P 四族的纪律（已落成代码，只需接线）

> 四族合计 **30 / 65 ≈ 46%**，**全部跨 3–5 本复现、且与书的内容无关**——无论做哪本书都会重踩。
> 数字以 `references/facts.json` 为真相源；此处不重复写死。

| 族 | 共同根因 | 骨架装置 | 一句话纪律 |
|---|---|---|---|
| **A** | 验收指标测「层内自洽」，不测「用户要查的东西在不在」 | `FieldCoverage` / `assert_no_silent_zero()` / `query_acceptance()` | 交付必须**另报填充率表 + 问句逐问验收表**，与 ERR/GAP 并列 |
| **B** | 命名在四处（源数据/打包器/适配器/注册表）分头书写，无单一来源 | `LAYER_SPECS` 四处同源 / `assign_ids()` / `assign_child_ids()` / `check_naming_consistency()` | **ID 分配权归打包器**；源数据只写槽位 |
| **G** | 只有「全量重建」语义，没有「增量合并」语义 | `atomic_write_json/text()` / `merge_layer()` / `merge_shared_json()` | 写盘一律「临时文件 + rename」；共享文件增量合并 |
| **P** | 做法没错，但用在错的场景/语境/口径上 | `SemanticGate` / `cn2int()` / `drift_ratio()` / `ProbeTracker` / `check_enum()` | 判据**写语义不写形态**；能落校验器就落校验器 |

## 三、剩下 12 族（C–F / H–O）为什么不落代码

**23 条（37%）是「语义侧」错误**，与书的文体强相关（典志体最重 E 族、年谱体最重 F 族），**只能靠「原文实测 + 显式判据 + 方向先验」逐本处理**——无法预先写进骨架。

它们的要求已经内化为**三条通用判据**（这就是你真正需要记住的部分）：

1. **方向先验**：排序、从属、主宾类结果，**先看方向再看条数**。想加第二个特例时，先问「排序问题还是包含问题」。
2. **映射显式化**：凡「条目 → 目标」的映射都要有**关联字段**（可多值），**不得依赖文本位置**。个体名优先于集体名；树是单一真相源。
3. **判据写语义**（层准入看"语义是什么"而非"看起来像什么"）；「平级」这类词必须在设计阶段向用户确认定义，并**落到校验器**。

> 需要某族完整机理、代表坑号、全部对策时，读 `references/errors/families.md`（16 族摘要，约 1/6 篇幅）。
> 需要某条坑的原始症状与实测数字时，才去 `references/archive/pitfalls.md` 查坑号。
