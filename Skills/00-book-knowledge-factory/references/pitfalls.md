# 常见坑与对策（Pitfalls）

> 从《新官轨范》《水东日记》《蘧编》工程的真实踩坑中提炼，按"症状 → 根因 → 对策"组织。出问题时先查本表，再决定修复路径。
> 坑库版本：v8（2026-10-15 追加 #45~#50：字段回填≠字段定义 / 全书性专表无处安放 / 语域闸门须锚定位置 / 量纲前缀误读 / 写盘集合与计数不一致 / 骨架构型漏官职层 / 查询问句反推层设计；v7 为 2026-10-14 追加 #37~#44；v6 为 2026-10-13 追加 #31~#36）
> 新坑候选先进 `pending-review.md` 待评审区，评审通过才入本库（编号顺延）。

## 0. 把工厂当执行器（定位错误，最根本的坑）

- **症状**：调用工厂后直接产出执行命令、中间文件或正式知识产物（EPUB/指纹库/各层 JSON），把工厂当成"执行器"；或交付一份《操作指南》文档就完事，没有固化为 skill。
- **根因**：混淆了工厂与实例的职责。工厂的使命是**生成书实例 skill**（像 skill-creator 生成本工厂一样），执行是实例 skill 的职责。用户说"传一本书形成规范"要的是一个可复用的技能实例，不是一次性的执行结果。
- **对策**：
  - 工厂流程止步于：探查 → 反思设计 → 固化为书实例 skill（生成到本目录同级编号目录）→ 试点校验 → 交付 skill 本身。
  - 工厂阶段不生成 EPUB/指纹库/各层 JSON/报告——这些全部是实例 skill 被调用后的事。
  - 交付物是 skill 的路径、结构与调用方式，不是执行命令。
  - 用户后续说"处理《X》"→ 触发书实例 skill → 才执行底座与抽取。

## 0.1 层模板套用（结构设计错误，次根本的坑）

- **症状**：把六层当固定管线，每本书都全走一遍——传一本字典也硬建事件层、硬建状态机；或凭书类型标签（"史书"）直接默认全建，不做反思。
- **根因**：把《新官轨范》的具体层清单当成了方法本身。实际上事件层是用户提出"事件五元组 Registry"后才做的，结构化五维是用户问"除了流程还能怎么结构化"后讨论选定的——**层是设计出来的，不是预设的**。
- **对策**：
  - 反思阶段逐层回答"这本书为什么建/为什么不建"，给出数据证据（规范句密度/时序结构/叙事密度/术语体系）。
  - 用户方向优先：用户提出的结构化方向无条件列为候选。
  - 数据检验：素材不足判"点不是线"，不强行建模；未启用层写明理由。
  - 候选层清单交用户拍板后锁层；实例 skill 只含启用层，未启用层不做任何动作。

## 1. 重复读取 / 反复探查（最高频）

- **症状**：同一批输入读了很多遍；每轮靠 summary 恢复后仍要重读 schema。
- **根因**：① 上下文压缩后 schema 细节丢失；② 探查-执行边界没守住，探查蔓延成多次小步读取；③ 会话过长导致重复加载章节/指纹库/规则映射。
- **对策**：
  - 开工前**一次探查**：输入 + schema 样例 + 统计一次读完；连续两次读取不再改变计划即停止。
  - 把"关键 schema 样例 + 关键文件路径 + 枚举清单"固化进每轮报告/总结，压缩后可直接恢复，不用重读文件。
  - 共享加载：指纹库/章节解析/规则映射抽成公共基座，各层打包器复用（import 替代复制）。

## 2. 产物覆盖回归（P0 修复丢失）

- **症状**：先做 P0 止血，后来重跑打包器把已修复字段覆盖掉，同一件事验证两遍。
- **根因**：修复用一次性脚本（`_p0_*.py`）落在正式生成器之外；重跑正式生成器时修复不生效。
- **对策**：
  - **修复并入生成器**：P0 修复写进 `build_` 打包器成为标准产出，重跑不丢。
  - 重跑前先确认不会覆盖已修复字段；脚本一律正式化（`build_` 前缀、幂等），不落一次性散文件。

## 3. original 手抄漂移

- **症状**：AI 源数据里手抄的原文与指纹库有出入（漏字/异体），逐层累积误差。
- **根因**：让 AI 直接抄原文进源数据，抄写环节必然漂移。
- **对策**：AI 源数据只写条号/解读；打包器从 `_item_registry.json` 注入 original/norm。修正差异一律以指纹库为准。

## 4. 枚举口径漂移

- **症状**：注释里写"41 值"，代码里 43 值；新增枚举值后存量数据没回填，跨层 join 断裂。
- **根因**：枚举定义散落各打包器，无单点治理与版本控制。
- **对策**：枚举收进单文件（`_kg_enums.py` 等），registerVersion 模式——**新增值 version+1 并回溯全部存量**；验证脚本比对文档与代码口径。

## 5. ID 对齐断裂（五处典型）

- **症状**：实体归一无全局主键、流程层 events 空槽位占 XGF-E 前缀、结构层缺 item_id、结构 target 是文本、枚举口径漂移。
- **根因**：各层独立产出时没对齐"引用的东西是同一个"。
- **对策**：
  - 条锚点 item_id 作为所有层共同主键；derived_rule/events 引用让层间可跳转。
  - ID 命名空间唯一归属（XGF-E 只属事件层，其他层只引用）。
  - 结构层 target 用 ID 引用而非文本。
  - 审计口径：跨层索引 layer_count 直接暴露贯通层数。

## 6. 环境噪声导致验证结果读不全（Windows/PowerShell）

- **症状**：stdout 30000 字符截断、jieba 日志被当 NativeCommandError、前台 15s 自动转后台——命令结果读不全，验证要重跑。
- **根因**：依赖 stdout 看验证结果。
- **对策**：验证脚本写 .py 文件并把结果**重定向到文件**再读，不依赖 stdout；长任务用后台任务 + 文件输出。

## 7. 规则引擎喧宾夺主

- **症状**：先用代码触发词引擎产规则（204 条），被用户否决——规则判定必须 AI 一句一句分析，代码只是验缺漏。
- **根因**：把"可代码化的触发词"当成了"规则判定本身"。
- **对策**：代码引擎结果只作候选/提示，判定必须 AI 逐条；代码只验缺漏（覆盖/格式/引用/枚举）。

## 8. 粒度反复

- **症状**：先按段（620 段）做，用户改口"既然做了条，就用条的"，返工。
- **根因**：粒度方向假设没在开工前确认。
- **对策**：方向性假设（粒度/判定方式/交付形态）开工前跟用户确认，写进《操作指南》第 0 节；中途变更要重新出方案再执行。

## 9. 覆盖缺口被掩盖

- **症状**：某卷 94 条只建模了 50 条事件，剩余 44 条没提，用户误以为全量完成。
- **根因**：把缺口并入总量，或只报成功率。
- **对策**：如实报告"哪里缺、缺什么、补什么方案"；未建模/未命中项单列缺口清单，不并入总量。

## 10. 交付散件淹没重点

- **症状**：每层每卷 12 件 × 5 层逐件 present，用户找不到入口。
- **根因**：按"层 × 卷"粒度交付，而非按层聚合。
- **对策**：按层一组交付（归一汇总 + 验证清单 + 卷示例 + 跨层索引），交付物 6 组以内；跨层 CSV 作为最常用查询入口放最前。

## 11. 版本差异坑（外部资料与用户文件内容不一致）

- **症状**：结构化探查时用外部检索（40 卷足本/点校本）定位条目内容，发现用户提供的 txt（四库本 38 卷）中找不到对应条目，或文字表述有出入（如"参赞军务"条足本有、四库本无）。
- **根因**：古书版本众多（四库本/足本/点校本卷数、文字均有差异），外部检索定位的是另一版本。
- **对策**：**以用户提供的文件为唯一权威来源**；外部资料只作内容性质/学术定位的辅助理解，不作条目抽取依据；结构探查的密度信号、抽样、条目定位一律基于用户文件本身计算。

## 12. 单卷复跑截断共享文件（增量语义缺失）

- **症状**：`build_base.py --volumes NN` 从空字典重建指纹库并按卷过滤，单卷复跑把共享指纹库从 1197 条抹成该卷条数，下游各卷产物对照"不在指纹库"报 ERR；卷概要等共享 CSV 同样被覆盖。
- **根因**：打包器只有"全量重建"语义，没有"加载现有共享文件 → 只重算所请求卷 → 合并写回"的增量语义。
- **对策**：**所有 build_ 脚本统一增量语义**——带 --volumes 时加载既有共享文件、只重算请求卷、合并写回；不带时从空重建为权威口径；共享 CSV 合并时旧行数字字段转回 int（CSV 读回全是字符串）。

## 13. 业务 ID 撞号（ID 分配权错放）

- **症状**：多卷并行执行时，各 worker 从 001 起硬编码分配 APPT/SDJ-E/REG/LIT/REL/NAM/TRL 编号，validate 按层全局判重必然撞号（试点两卷即互撞），被迫人工重编号。
- **根因**：业务 ID 的分配权在 AI 源数据（手写）而非打包器；"ID 即内容"错误耦合。
- **对策**：**ID 改打包器自动分配**——源数据只写槽位（卷内顺序），打包器按"卷号×段容量+1"段位自动编 ID；AI 不再手写业务 ID；段位方案可作临时缓解（validate 全局判重兜底）。

## 14. 并行子代理半写文件与汇总竞态

- **症状**：并行片写 sources 过程中，他片 run_all 的 build_kg_join/汇总步骤读到半写文件触发瞬时 ValueError；summary 类共享文件"最后写入者覆盖"。
- **根因**：无原子写入；共享文件无合并语义。
- **对策**：写文件走"临时文件 + rename 落盘"；共享汇总文件统一增量合并语义；并行片错峰执行重跑型步骤，或由单一收敛者（全量 run_all）在收尾统一重建。

## 15. 枚举校验"报错终止"导致执行中断

- **症状**：执行期 LIT 无"集"、EVENT 无"军政/司法/边政"、REG 无"祭祀"、APPT_STATUS 无"起复/世袭/举荐"，打包器校验抛异常即中断整卷（本实例 5 次中断）。
- **根因**：枚举校验从"收集-报告"模式做成了"报错终止"模式，原文出现未枚举值就直接失败。
- **对策**：枚举校验改为**收集-报告-暂存**——未匹配值入 pending 表不中断，每卷/每片结束输出枚举使用分布，收尾统一决议（新增/归并/改名）→ registerVersion+1 → dry-run 回溯 → commit；新增值必须有实例证据。

## 16. TRL 长文翻译体风险

- **症状**：碑文/序/奏议/书启等长文条目翻译主观性最强，易滑向翻译体公式（"当……时""……之一""进行"式腔调），且逐条质量难以代码验证。
- **根因**：长文翻译自由度大；代码只能验覆盖（条目数=翻译数），验不了风格。
- **对策**：实例固化翻译风格规范（如余光中七条：译原意不译原字/长句拆并联/专名保留+括注/忌翻译体公式）；长文提供"分句群译"模板与篇幅参考；风格校验留给人工复核闭环兜底。

## 17. 名录卷"行=表格行"与条目切分的张力

- **症状**：指纹库逐行切条，但题名表一行多人（"杨善　萧维祯　马昻"）、跨行四元组（姓名/字/籍贯行 + 官职行），按行硬拆会打碎名录结构。
- **根因**：条目切分的"行=条"假设对表格式卷不成立。
- **对策**：底座按行切候选并标注卷结构提示（volume_summary 的 mode_hint）；NAM/APPT 层按表重组——整体一条 NAM 记录、entries 四元组数组化、分列小标题作 office 上下文；卷阅读模式（名录优先/谱牒优先）前置标注例外卷。

## 18. CSV 物理行 ≠ 逻辑行（含换行单元格）

- **症状**：译文等单元格内含换行，trl.csv 物理行 1313 ≠ 逻辑行 1192，手工按行数统计出错。
- **根因**：CSV 引号内换行是合法行为，但"数行数=数记录"的心智模型失效。
- **对策**：解析与计数一律按逻辑行（csv.reader / pandas），校验脚本按 item_id 或记录数计数，不数物理行。

## 19. 层产物顶层键名不统一

- **症状**：ent 单卷 JSON 顶层键为 annotations，其余层为 records，聚合器/跨层索引需特判分支。
- **根因**：各层 schema 书写时未约定统一容器键。
- **对策**：各层产物统一顶层键（records），或聚合器自动识别 annotations/records；每记录必带 volume 字段；schema 母版中固化。

## 20. 工具参数语义名不符实

- **症状**：validate.py 带 --volumes 参数仍全卷检查，仅靠"只看本卷行"约定判定本卷质量，输出全局 ERR 数易被误读为本卷失败。
- **根因**：参数语义与实现不一致。
- **对策**：工具参数要么真正按卷过滤输出，要么改名并明确文档约定（"全卷检查、只看本卷行"）；验证汇总区分"结构性错误 ERR / 执行缺口 GAP"，两者不可混读。

## 21. 年谱年龄双轨口径误判（《蘧编》）

- **症状**：年谱类书 trl 首句用**虚岁**标注（"万历四十一年（1613 年），我五十五岁"），而 chr.age 字段存**年差**（year − 出生年，出生年记 0，1613→54）；两者恒差 1。收尾对账时未读口径文档，把 trl 与 chr.age 的差 1 当成数据缺陷，险些全量误改。
- **根因**：同一年龄两种表示并存（人类阅读用虚岁、字段存储用年差）属**设计口径**而非 bug；无单点口径声明时对账无法区分"设计如此"与"真错"。
- **对策**：开工前锁定年龄口径并写入实例 schemas.md / 交付说明（显式声明"trl 首句虚岁 = age+1"）；对账脚本比对时按口径换算后再判一致；执行期不许两轨混淆互改。

## 22. 卷×段位容量不足撞号（《蘧编》）

- **症状**：跨卷业务 ID 段位初用"卷 NN × 100"，卷一条数多（卷一 40 条、每条约 20-30 个 ent/evt）段内不够分配，撞号。
- **根因**：段容量只按"卷条数"估算，没按"卷内单层最大记录数"预留；层内记录数可远超条数（多实体/多事件/多关系）。
- **对策**：段容量按"卷条数 × 单层最大扩展系数"预留（本项目改卷 × 500 后全卷 71 条 0 撞号）；validate 全局判重兜底；容量仍不够时扩段位并全量重跑（ID 重新分配，勿手工改号）。

## 23. 层 schema 键名与打包器键名漂移（《蘧编》）

- **症状**：源数据层键用单数（chr/trl），打包器层容器键用复数（chrs/trls），打包时报 KeyError 或静默丢层；前 5 卷曾因键名不匹配漏打包。
- **根因**：源数据键名约定与打包器容器键约定分处两处书写，无单一来源；复数/单数习惯不一致即漂移。
- **对策**：打包器内建**显式 SRC_KEY 映射表**（如 `{chrs:"chr", trls:"trl"}`）——打包容器键固定复数，源数据键名由映射表声明；实例化时把映射表固化进打包器模板，验证脚本按打包容器键检查覆盖。

## 24. 汉字卷名→数字卷号映射偏移（《蘧编》）

- **症状**：build_base 首跑按序数映射卷号（第一卷→01…），序/前言/后记/附录插入后整体偏移（卷一映射成 03），条目归属卷号全错，且 `_extract` 残留旧映射文件致验证合计虚高（147 vs 真实 76）。
- **根因**：卷号映射依赖"读取顺序"而非"卷名本身"；残留文件未清理导致验证读到陈旧数据。
- **对策**：卷号映射用**汉字卷名直接映射**（序/前言=00、卷一~二十=01–20、后记=21、附录=22），不依赖文件顺序；写出前**幂等清理**目标产物（重算前先删旧文件），验证数字以清理后实算为准。

## 25. 实例增量不走工厂（口径漂移）

- **症状**：用户或执行中直接给已有实例加层/改枚举/改 schema，未经工厂增量流程——新旧枚举漂移、新层 ID 段位与既有层冲突、schemas.md 与 enums.md 不同步、registry 失真，增量部分成为"野分支"。
- **根因**：工厂只定义了"首次实例化"五阶段，没有为已交付实例定义变更通道；增量是常态（三本书实例全部发生过事后增量）却无流程约束。
- **对策**：对已交付实例的一切规范级变更一律走 `increment-upgrade.md` 七步（证据检验 → 确认锁层 → 改实例规范 → 存量与管线衔接 → 试点 → 更新 registry → 学习回路）；增量结论以追加方式进实例反思记录；变更后 registry 与各库版本行同步更新。

## 26. 把反思过程记录全量塞进实例（实例臃肿）

- **症状**：实例 SKILL.md §0.1 沉积大段用户原话、逐层谈判过程与全部证据表，执行时是死重；上下文压缩后反复重读这些过程材料，拖慢每次调用。

## 27. 封闭枚举在执行期被"就地吸收"（《客座赘语》）

- **症状**：schema 里写死"封闭 + 兜底"的枚举，执行完一统计，值数暴涨——事件类型 23 → 实际 **111 种**、文献类型 11 → **114 种**、名物 9 → **72 种**、涉明 8 → **94 种**、方言风俗 7 → **53 种**，地理层 8 → **52 种**（"山/山岭/山冈/山岳/山地/山石"六个词形并存）。库外值占比：事件 56%、文献 92%、名物 63%、名录 **100%**。枚举"封闭"名存实亡，跨卷不可比，回库时无口径可依。
- **根因**：① 打包器/验证器只校验"是否有值"，**不校验"值是否在封闭集内"**（或校验了但只警告不阻断），AI 遇到未匹配条目就自造一个词形继续写，V3"收集-报告-暂存"的闸门根本没合上；② 顶层类目太粗（名物只有 9 值、文献只有 11 值），面对笔记类书"什么都有"的内容，AI 只能往下细分；③ 缺少"新值必须先落 pending 表"的硬性动作点。
- **对策**：
  1. **验证器阻断**：打包时对封闭枚举做 `value ∈ ENUM_SET` 硬校验，不在集内 → 报错并列出待决议清单，不许静默写入（见 #15 的"报错终止"反面：这里恰恰要阻断，区别是阻断在**打包前**的源数据校验，不是执行中）。
  2. **值数告警**：验证报告输出每层"值种数 vs schema 定义数"，比值 > 1.5 即判口径漂移，必须走决议。
  3. **顶层先够用再封闭**：笔记/类书这类"内容无边界"的书，实例化时顶层类目宁可多给几个（文献按经史子集给、名物按顶层 13 类给），或用**树状**（顶层封闭 → 子类开放登记），避免 AI 被迫自造顶层。
  4. **同义归并前置**：schema 里直接给出别名映射与正反例（如"艺文/文学/著述 → 文事"），减少判定分歧。
  5. **执行期增量回库**：新值一旦决议通过，走 `enum-induction-guide.md` 的 registerVersion+1 与存量回溯，并**回写工厂基准库**（本坑与 #25 配套：不回库的增量就是野分支）。

## 28. 跨层索引目录名缺陷（《福惠全书》）

## 29. 联邦 adapter 目录名映射偏移（《福惠全书》）

- **症状**：kb-federation adapter 用单数 key（`_layers\<key>\<key>_NN.json`）扫福惠产物，首稿仅 ent 646 入库、7 层漏扫（2104 条实为 646+7 层 1458）；修复为复数映射（`LAYER_DIR_NAMES` 目录名+文件名前缀双映射）后 8 层 2104 条、折叠 0。

## 31. 树结构与边表互为校验时未划"树内边/跨树边"（《明史·职官志》）

- **症状**：机构树（`children[]` 递归）与隶属边表（LINE `subordinate→superior`）互为校验时，报"仅边表有 `('吏部','天子')`"，看似数据缺陷。
- **根因**：根机构直隶「天子」的边**不属于树内父子关系**（天子是全书树根，非某机构的子节点），不入 `children[]`；不排除即双向校验变成双向误报。
- **对策**：**先定死边归属**——**树内边 = `children[]`；跨树边 = `superior=="天子"`（或等价"最高层"），不入 children[]，单独登记在 `org_tree.json` 的 `root`**；校验式 `set(树推边) == set(边表中 superior≠"天子" 的边)`。**凡「层级树 + 关系边表」双轨建模通用**（机构树/家族谱系/地理管辖/引用网络）；与 #28「目录名/键名三处不统一致静默漏扫」同族——都是双轨结构未定死归属。

## 32. 多模式分类器判定优先级写反（《明史·职官志》）

- **症状**：员额句式分类器把 `左、右侍郎各一人`（**应为 P1 并列带各**）判成 **P3 合称共享**（低置信桶），致用户特别关心的那条记录置信度被标低；分布统计看起来"正常"（各型都有命中），症状隐蔽。
- **根因**：分类器**先判 `、`+`各`（合称型）再判并列前缀型**；而 `左、右侍郎各一人` 同时含 `、` 与 `各`，被前一条件抢先命中。判定顺序未纳入设计。
- **对策**：**判定优先级本身是设计的一部分，必须显式写死并测试**。本案例正确顺序：**先判并列前缀型（P1/P2），再判合称共享型（P3）**——`if 有并列前缀: P1 if 含"各" else P2; elif 含"、" and 含"各": P3; else: P4`。凡是"多模式 + 优先级判定"的分类器（枚举归类、规则分型、实体类型判定、句式识别）都要：① 把优先级写成显式有序规则表；② 用**同时匹配多个模式的样本**做边界测试（本例 `左、右侍郎各一人` 即边界样本）。

## 33. 无条级标记文本的「行=条」口径与估算基准（《明史·职官志》）

- **症状**：正文有章/卷/目录三级标记但**无条级符号**（无 ○/△ 逐条标记）时，切分口径与条数估算无据可依；估算基准写错（拿实切数与非空行数直接比）会误报"偏差超 5%"。
- **根因**：切分口径按"行=条"推断；估算公式**漏计某一级标记行**（本例漏计 `◆` 章标记 5 行，致估算 324 实为 319）。
- **对策**：
  ① 口径 = **一行非空段落 = 一条**；`◆/◎/○` 等标记行与空行**一律不计条**；一行含多对象仍算一条（如六部各占一行）、一行含多段体例（编制+职掌+沿革）合并为同一条目三段。
  ② 估算公式 = **非空行 − 全部标记行（含所有级别）**，逐级核对不漏；本例 = 333 − `◆`5 − `◎`5 − `○`4 = **319**。
  ③ 切分脚本须打印逐卷实计数与估算对账（偏差非 0 回查）。
  ④ **估算基准本身必须先自证正确**——装置 bug 会被误读为 schema 缺陷（与 #20「工具参数语义名不符实」同源）。
  ⑤ 与 #17「名录卷行=表格行」、政学录/宛署「○ 分组标题不计数」同族（分级标记计数纪律）。

## 34. 职掌陈述句被抽成规则（《明史·职官志》）

- **症状**：机关职掌陈述句（"X司，掌X之事，以赞尚书"）被抽进 L2 规则层，规则层被非规范句污染。
- **根因**：`掌` 被当作规范触发词；但**职掌陈述是静态描述**（这个机构管什么），不是"应当/禁止/程序"型规范。
- **对策**：**职掌陈述句不抽规则**——归 L1 实体 + L4-ORG 承载；**仅"凡…/不得…/须…/听…"等规范句抽规则**。延伸原则：**非规范句不抽规则**（含本条职掌陈述句、#35 沿革句、《平平言》官箴说理句"呜呼/嗟夫"、亲历记事句"余令某县凡五年"）——建议合并为总原则：**"规则的判据是规范性语义，不是触发词出现"**。

## 35. 沿革内容被重复刻画（《明史·职官志》）

- **症状**：同一段沿革（"洪武十三年罢中书省"）可能同时进事件层、沿革层、任职层，三处重复建模，条目量虚增且三处易不一致。
- **根因**：沿革行天然同时是"纪年事件"+"机构阶段"+"人物任职"，未定分工即重复抽取。
- **对策**：**沿革三分承载，各记一视角，互不重复**——**TME**（时间视角：纪年事件点，全书纵向可排序）/ **L4-EVO**（机构视角：阶段切片，单机构横向）/ **APPT**（人物视角：任职记录）；三者以**双向引用**（TME `related_evo` ↔ EVO `related_tme`）拼接，打包器校验一致性；**三分之后不建事件层**（避免第三次刻画）。**判别建不建事件层的标准**：若沿革含完整 who/action/what 三元组（如政学录"条陈→部覆→奉旨"）→ 建 EVT；若为"某年某机构某变动"单点陈述（who 多空）→ 三分承载即可，不建 EVT。

## 36. 名录形态的编制清单被误建 NAM（《明史·职官志》）

- **症状**：逐镇/逐卫罗列的"镇守X总兵官一人，分守参将N人，游击将军N人"形似名录，被建进 NAM 名录层，致同一内容在 NAM 与 L4 两处存放。
- **根因**：按"表格式罗列 = 名录"的形态特征判定，未看**内容性质**（是否含人名）。
- **对策**：**判别标准 = 是否含人名**——**含人名 + 字/籍贯/官职四元组者建 NAM（题名录）**；**仅含官职员额（官职+人数+品级）者归 L4-ORG/RANK（编制陈述）**。卷五逐镇总兵官清单后者，归 L4。与 #17「名录卷行=表格行」配套：先判内容性质，再定切分与归属。

## 37. 把「通用机构」另立模板容器，排除在 ORG 之外（《明史·职官志》）

- **症状**：府/州/县/道/儒学/巡检司等"通用编制"（原文只有一份模板、天下诸处复用）被当作**非实体**，另立 `ORG_TEMPLATES` 模板容器 + `TPL-` 命名空间 + 独立 `_layers/templates/` 层落盘，排除在 ORG 树外。用户一眼看出问题：「这些应该是 org 吗？」
- **根因**：把"**有没有具体实例**"当成了 ORG 的准入判据，而 ORG 的准则是"**是不是原文陈述的机构**"。府/州/县在原文（明史·职官志 卷四 条54–75）都是**正式机构条目**，有品级、有员额、有隶属、有沿革；「通用编制」只是它们编制可复用的**额外属性**，不是另一种东西。模板容器还带来三重副作用：① ORG 树缺节点，机构树索引不完整；② 这些机构的员额/隶属无处安放（RANK/LINE 只认 ORG 记录）；③ 独立层目录与 ID 命名空间增加治理面。
- **对策**：
  - **ORG 准入判据 = 原文是否作为机构陈述**（有编制行/职掌行/沿革行），**不看是否有具体实例**。通用编制机构与专设机构同列 ORG 节点。
  - **不设模板/通用容器**。若确实需要标注"编制可复用"，作 ORG 节点上的**字段**（如 `note`/`reusable`），不另立容器与 ID 空间。
  - **转正须三处同步补齐（缺一即 ERR）**：① ORG 树 `children[]` 加子机构（**节点字典形态**，非名称字符串）；② RANK 层承接品级员额（品级员额的规范归属层是 RANK，ORG 节点上的 `posts[]` 只是摘要）；③ LINE 层补隶属边（区分树内边/跨树边，见 #31）。
  - **废弃容器须显式报错**：打包器对已废弃容器（如残留的 `ORG_TEMPLATES` 导出）直接 append ERR，避免静默丢数据。

## 38. 校验器按字段存在性分派维度时顺序写错（《明史·职官志》）

- **症状**：四维（ORG/RANK/LINE/EVO）混装于同一 `structs` 记录集，校验器按"字段存在性"分派维度。原顺序 `if "posts" in r`（RANK）在前，而转正后的 ORG 节点**同时带 `children[]` 与 `posts[]`** → ORG 被误判为 RANK，产出 120 条假 ERR：`RANK ORG-2038 rank_type 越界: None` / `vacancy_type 越界: None` / `post_status 越界: None` / `selection_route 越界: None`。
- **根因**：分派字段选用了**非唯一标识字段**。`posts[]` 在 ORG（编制摘要）与 RANK（本职）都出现，不具排他性；真正排他的是 `children[]`（**每个 ORG 节点必有，RANK 必无**）。
- **对策**：
  - **分派字段必须是该维度的"充要标识"**——出现即属该维度，且其他维度必不出现。选字段时先问："这个字段会不会在别的维度也出现？"
  - 本书定死分派顺序：**`children`（ORG）→ `change_type`（EVO）→ `line_type`（LINE）→ `posts`（RANK）**，`else` 报"无法识别维度"。
  - **假 ERR 也要查根因**：120 条 ERR 全部指向 `rank_type/vacancy_type/post_status/selection_route 越界: None`，值全是 `None` —— 这是"字段根本不存在"而非"字段值非法"，是**分派错误**的典型指纹。值全 `None` 且集中在一批新记录时，先怀疑分派，不要逐条补字段。

## 39. 业务 ID 序号取自 `slot` 而非记录全局序号（《明史·职官志》）

- **症状**：打包器分配业务 ID 时用 `prefix + (段位 + slot)`，而 `slot` 是"条目内语义顺序"、每个 `item_id` 都从 1 重启 → 所有条目的第 1 条记录撞成同一 ID。实测 50 条规则仅 9 个唯一 ID（全撞 `ZG-R-501`~`508`），`validate` 报 46 条 ERR。
- **根因**：把"条目内位置"当成了"全局位置"。ID 的唯一性由**记录在待分配列表中的全局序号**保证，不由其在所属条目内的语义槽位保证。
- **对策**：
  - `assign_ids` 改用 `enumerate(records, 1)` 全局序号；调用前按 `(item_id, slot)` 排序保证确定性；
  - 验证器全局判重兜底（每条记录 id 必须唯一）；
  - **豁免 `ents` 层**：`ents` 的 `id` 是**实体主键**（同一实体多次出现共用同一 id，属设计如此），验证器须豁免 ents 撞号校验，其余层不得豁免。凡"条目内有序槽位 + 打包器分配 ID"的实例通用。

## 40. ORG 层级枚举混装"中央机构"与"地方政区"（《明史·职官志》）

- **症状**：`府` 既指宗人府/顺天府（中央机构层），又指府州县之府（地方层），单一 `LEVEL_RANK` 会误判父子关系——`宗人府(府) -> 经历司(司)` 因被判同级而报"层级非法"。
- **根因**：层级枚举名本身多义（府/司/局/监），未在实例化时选定本书语义。
- **对策**：① 明确本书 `府` 取"中央机构层"（与部/院/寺/监同级）；② `州县` 降为该层下子级；③ 或拆分枚举为 `府(中央)` / `府(地方)`。**凡层级枚举含多义层级名的实例，实例化时须选定本书语义并写入 schemas**。与 #42 互补——本条讲**枚举粒度**，#42 讲**比较判据**。

## 41. LINE 边表节点名与 ORG 树节点名不一致（《明史·职官志》）

- **症状**：同一机构在树内作 `验封清吏司`、在边表作 `验封司`，树内边集比对即报"仅 LINE 有"。
- **根因**：树与边表分别手写，各自用了简称/别称。
- **对策**：边表 `subordinate`/`superior` **一律取 ORG 树的 `name` 原值**（不用简称/别称）；打包器树内边一致性校验兜底。与 #31「树内边/跨树边」、#44「树边同源维护」同族——都是双轨结构未定死节点命名。

## 42. ORG 层级合法性判据用「严格递减」而非「非递减」（《明史·职官志》）

- **症状**：卷03 首跑报 7 处"层级非法"（宦官→十二监、太仆寺→各牧监、八局→兵仗局等）。
- **根因**：同一层级名在史书中常兼任**「同级机构群」**角色——`宦官(内府) → 十二监(监)` 中，十二监**并非宦官的下属机构**，而是 **12 个同级监的集合名**。按"子必须严格低于父"判定，这类合法结构被误报。
- **对策**：`level_ok(parent, child) = LEVEL_RANK[child] >= LEVEL_RANK[parent]`（**同级允许**）。**凡「集合名 + 成员机构」同层建模的书通用**（二十四衙门/六科/五城/十三道/九寺）。

## 43. `children[]` 深度上限预设为 ≤3（《明史·职官志》）

- **症状**：明代宦官二十四衙门为**三层嵌套**（宦官 → 十二监 → 司礼监），树深度 = **4**，v2 设定的"深度 ≤3"校验误报。
- **根因**：上限按常识拍定，未先探查本书最深嵌套。
- **对策**：实例化时**先探查最深嵌套再定上限**，或直接设宽松值（如 ≤5）并在报告里输出实测最大深度。**凡含「机构群 → 成员机构 → 内部职官」三层结构的书通用**（宦官二十四衙门/女官六局/钦天监五官/五城兵马司）。

## 44. ORG 树与 LINE 边表未同源同步维护（《明史·职官志》）

- **症状**：新增 ORG 子节点时未同步补 LINE 边，触发"树内边仅 ORG 有"批量报错。卷03 一次新增 54 个子节点（钦天监 9 / 上林苑监 5 / 宦官各监司局 25 / 内府库房 15）即产生 54 条 ERR。
- **根因**：树与边表分两次书写，无同步约束。
- **对策**：① 写源数据时**先定树、后配边**；② 打包器报错信息**逐条列出缺失边**（便于批量补齐）；③ 若某节点确为**独立树根**（如"内府诸库房厂"原文附于宦官条后但结构上平级），其跨树归属用 `superior="天子"` + `note` 记实际隶属，**不可强行挂到中间层**。凡层级树 + 隶属边表双轨建模的书通用。

## 45. 建了字段却没回填数据（字段定义 ≠ 字段填充）

- **症状**：schema 里字段齐全、文档写得很漂亮，但实际数据里该字段 **100% 是占位值「未明」**。本实例 v3 按用户要求把 12 项编制字段全部纳入 `POST_FIELDS`（`salary_ref` / `vacancy_type` / `post_status` / `is_concurrent` / `selection_route` / `succession` …），抽取时一律写 `"未明"` 占位，致 `salary_ref`、`vacancy_type` **431/431 全空**；五卷五层跑完、ERR=0 GAP=0、跨层索引 0 空条目（验收指标全绿），直到用户拿 8 类真实查询来问才暴露「薪酬查不到、实虚职查不到」。
- **根因**：**字段定义与填报规则脱钩**。新增字段时只定义了「这个字段叫什么、是什么类型」，没有定义「什么情况下填什么值、从哪句原文取、由谁填」。字段进了 schema 但从未进入抽取流程，占位值让校验器无法察觉（占位值是**合法枚举值**，不是错误）。
- **对策**：
  - ① **新增字段必须同步给出回填规则**：触发词 / 证据句式 / 判定优先级 / 无证据时的留白策略。给不出回填规则的字段，不进 schema。
  - ② **留白策略要显式**：无证据时留「未明」还是留空？本实例定「**宁缺毋滥**」——宁可留「未明」，不臆测默认值污染数据（如 `vacancy_type` 仅 2 条有确凿原文证据就只填 2 条）。
  - ③ **交付前跑字段填充率体检**：统计各字段非占位值计数。填充率 0 的字段，要么补回填规则，要么**从 schema 删掉**（留着一个永远空转的字段比没有更糟——它让下游以为数据存在）。
  - ④ 能规则化的字段改由**打包器统一回填**而非 AI 手写（本实例 `_post_backfill.py` 由 `build_struct.py` 调用，源数据里一律写 `"未明"`）。

## 46. 与条目无关的「全书性表」无处安放

- **症状**：原文里有一类**不隶属任何条目**的表——总纲性的、跨全书的。本实例《明史·职官志》有 5 张：洪武二十五年俸禄表（18 级）、文散阶 42、文勋 10、武散阶 30、武勋 12。抽取时发现它们**既不属于某机构条目，也不属于某时间点**，任何一条记录都装不下，于是被整体跳过——薪酬查询因此永久无解。
- **根因**：层设计预设了「每条层记录都从某条目抽出」，没有为**全书性总表**预留归属位。切分以条目为单位，而这些表的粒度是「全书」。
- **对策**：
  - ① **设虚拟卷位**：以 `_vol = "00"` 落盘（本实例 `_layers/structs/structs_00.json`），与真实卷位并列而不干扰。
  - ② **`item_id` 用占位形式**（`"_book_<表名>"`），显式声明「非真实条目号」，**不参与跨层索引**（否则污染条目覆盖率统计）。
  - ③ **扩展该层的类型枚举**：本实例 `RANK_TYPES` 增 `俸禄` / `散阶` / `勋级`。
  - ④ **表项可用扩展字段**：posts 元素在通用三字段外可带 `amount` / `unit` 等专表字段。
  - ⑤ 若该表可作**查表键**（如品级→俸禄），另在枚举模块建映射函数（本实例 `salary_of(grade)` / `salary_ref_of(grade)`），供其他记录按 `grade` 查表回填。
- **附带教训**：**报错计数与落盘文件不一致时，先查写盘循环的集合来源**——本实例专表记录**已在内存中参与计数**（`RANK=104`）却**永不落盘**（`_layers/structs/` 只有 `structs_01.json`–`structs_05.json`），因为写盘循环是 `for v in vols:`（只含真实卷号）。改为 `sorted(set(vols) | {"00"})` 后正常。验证器应同时比对**内存计数**与**落盘计数**。

## 47. 用范围词判语域时全串匹配，被正文同形词污染

- **症状**：回填 `selection_route` 时，用「原文含『留守司。』则判为非卫所条」作闸门。结果 `05-051`（卫指挥使司条）**漏填 3 条世官**——因为该条原文含「外卫各统于都司、行都司或**留守司**。」，其中的「留守司」是**正文提及**，不是本条主旨。
- **根因**：用**子串存在性**判断「本条是什么条文」时，无法区分「词语是主旨」还是「词语被顺带提及」。位置信息被丢弃了。
- **对策**：
  - ① 语域闸门一律**锚定位置**：`scope_text.startswith(<锚点>)` 或正则 `^`（本实例修正为 `scope.startswith("留守司")`）。
  - ② 更稳的做法是**首句/首段**取样 + 锚定，而非全文扫描。
  - ③ **教训**：位置是最廉价的消歧手段。一个词出现在开头和在正文中段，语义权重完全不同——用全串匹配等于主动丢弃这个免费信号。
- **同源**：与 #44（边表节点名逐字一致）同属「文本比对口径不清」，但本条讲的是**位置**而非**字面**。

## 48. 中文数字的量纲前缀被误读成独立数位

- **症状**：原文「**一千**四十四石」被解析为 `144` 或 `1444`（视算法而异），而非正确的 **1044**。
- **根因**：中文数字的量纲前缀（千/百/万/亿）是**量纲标记**，不是可拆分的数位。「一千四十四」= 1000 + 44，不是 1 后接 044。「一千」的「一」与「千」必须**先合并成量纲单位**再与后续数值相加。
- **对策**：
  - ① 抽金额/员额/距离类数字时，**先识别量纲前缀**（千/百/万/亿）再合并，不可逐字拆数。
  - ② 抽样核验**跨量纲级差**：本实例正一品 1044 石 vs 从一品 888 石（同级差应在合理区间）；若正一品解析出 144，量级立即暴露错误。
  - ③ 量纲级数字**优先人工核对**（本书只有 19 个俸禄数，值得逐条核）。
- **同源**：与 v3 的 P1/P2/P3 员额句式同属「中文数量表述的消歧」，但本条针对**量纲**而非**分布**。

## 49. 把「机构」当唯一骨架，官职只作数组元素

- **症状**：五卷五层全绿（ERR=0 GAP=0）、跨层索引 317 条 0 空条目、验收指标全部达标后，用户拿 8 类真实查询来问，**3 答不了（上级官职 / 下级官职 / 平级官职）/ 3 半答**。根因：ORG 树 158 个节点**全是机构**，官职只是节点上 `posts[]` 的数组元素——**无独立 ID、无父子关系、无平级字段**。同时 L1 实体层已标注 1109 条 `official` 实体，却因官职无主键而**无法索引**（标注了等于没标注）。
- **根因**：把「组织架构」当成了唯一骨架。史书里机构与官职是**两套体系**：机构有隶属链（部→司），官职有品级位与副贰关系（尚书→侍郎→郎中）。只建机构树，官职就退化成机构的附属属性，官职与官职之间的关系无处表达。
- **对策**：
  - ① **Phase ② 反思时即枚举目标查询问句清单**（谁/何时/何职/上级/下级/平级/沿革/薪酬/职掌/区域…），逐问**标注由哪一层承载**。凡无层承载者即为设计缺口，**在实例化阶段补齐，不留到交付后**。这是本条最根本的对策——把「能不能回答 N 类查询」当**设计验收手段**而非事后补救。
  - ② 若书目含官职关系查询需求，**单建「官职层」**：官职独立主键 + 上下级边。低成本打法是复用现有 `posts[]`，加 `official_id` / `parent_official` / `org_path` / `subordinate_officials` 四字段（不需新读原文）。
  - ③ **官职边只建有原文显式表述者**（「X贰之」「X佐之」「为**首领官**」「兼领」），**不按品级相邻自动连边**——品级相邻是**组织包含关系**（郎中属司、司属部），已在 ORG 树内，重复建边是冗余。
  - ④ **「平级」定义必须写死**：建议取「同机构同品级」或「同机构同层级」，**不跨机构**——否则"平级"退化成"同品级列表"，恰恰是用户不想要的答案。
- **代价参照**：本实例评估约 1 个迭代（与一次中型改造同量级），非重做全书。

## 50. 验收指标全绿 ≠ 能回答用户的问题

- **症状**：工程指标全部达标——ERR=0、GAP=0、跨层索引 317 条 0 空条目（填充率 100%）、五卷五层 5105 条层记录、幂等复跑一致、文档齐备。但这些指标测的是「**层内自洽**」，不是「**能回答什么**」。用户拿 8 类真实查询一问，**3 答不了 / 3 半答 / 仅 2 能答**。
- **根因**：验收指标是**工程视角**的（结构合法、引用完整、无缺漏），用户的验收是**查询视角**的（我想知道 X，能不能查到）。两者可以完全脱节——本实例就是：`salary_ref` 字段合法存在（枚举值「未明」是合法值），校验器无话可说；但用户问「吏部尚书的俸禄是多少」时答不出来。
- **对策**：
  - ① **Phase ② 反思阶段产出「目标查询问句清单」**：从书目体裁枚举（本实例：上级 / 下级 / 平级 / 职务人数差遣 / 沿革 / 薪酬 / 任务 / 区域品级实虚职），逐问标注**由哪一层、哪些字段承载**。
  - ② **标注不出承载层的问句 = 设计缺口**，立即在实例化阶段补层或补字段，不留到交付后。
  - ③ **交付前用问句清单反向验收**：逐问实际查一次，答不出的即是缺口。**这比跑一次 validate 更能发现真问题**。
  - ④ 把「N 类查询命中率」作为与 ERR/GAP 并列的交付指标写进《项目总结报告》。
- **关系**：本条是 #45（字段空转）的**上位坑**——#45 讲「字段建了没填」，本条讲「连字段都没建，因为设计时没问『要回答什么』」。**先有问句清单，才有字段设计**。
