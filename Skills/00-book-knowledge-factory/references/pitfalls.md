## 错误分类总表（跨实例聚类，v12 追加；v14 补入 #62）

>
> 分族：**A–O 为主表 15 族**为主表（#1–#60 的主体归类）；**P 族**为建表漏收条目补录（#61 于 v13、#62 于 v14 补入、**#64 于 v15 补入**；#62 归 A 族子型 A6、**#63 归 A 族子型 A7**）。合计覆盖 #0–#64 全部 **65** 条。部分条目**跨族互见**（#30 兼 B/D、#24 兼 G/H、#46 兼 A/F、#47 兼 C/F、#17 兼 H/I、#27 兼 D/I、#16 兼 J/P、#57 兼 C/K、#34 兼 D/P），互见条目已在各族正文注明「同前」，各族标注条数为**扣除互见重复后的净数**。

### A 族（10 条）｜「校验通过」≠「数据可用」
> 共同根因：**验收指标测的是「层内自洽」，不是「用户要查的东西在不在」**。10 条分别是同一件事的十种表现，且**已四次复发、复发位置逐层下移**（数据层 → 回填器接线层 → 工具自身层 → **自检的保真度**）。本族按条数排第二，但**跨实例复现最广（3 本）**，且是唯一直接导致「交付后才发现核心查询无解」的族。
> - **子型 A1 字段空转（建了字段没值）**：#45 建了字段却没回填数据（`salary_ref` 431/431 全空）、#56 属性回填器写完没接线（`seal` 填充 0 而 ERR=0）
> - **子型 A2 解析器静默丢组（接了线但漏采）**：#55 全书性表格的复合句只取第一组（印信表覆盖 57% 不报错）、**#35 沿革内容被重复刻画**（同段沿革同时进 TME/EVO/APPT 三处建模，条目量虚增而三处易不一致——属「不报错的重复」，须靠层间分工判据而非校验器发现）
> - **子型 A3 映射静默失配（键对不上，一行不报）**：#28 跨层索引目录名缺陷（join 槽位单数 vs 产物复数 → 7 层静默空回填）、#29 联邦 adapter 目录名映射偏移（首稿仅 ent 646 入库、7 层漏扫）、#19 层产物顶层键名不统一（`annotations` vs `records`，聚合器需特判）
> - **子型 A4 计数器与真相源不一致**：#46 报错计数与落盘文件不一致（卷00 专表在内存参与计数却不落盘，`RANK=104` 但 `_layers/structs/` 只有 01–05）
> - **子型 A5 验收口径本身错**：#50 验收指标全绿 ≠ 能回答用户的问题（ERR=0/GAP=0/0 空条目全绿，用户 8 类查询 2 能答/3 半答/3 答不了）、#20 工具参数语义名不符实（`validate --volumes` 带参仍全卷检查）、**#49 把「机构」当唯一骨架、官职只作数组元素**（骨架构型漏层，直接成因是 Phase ② 未枚举查询问句清单——架构错误与验收口径错误在此合流）
> - **子型 A6 把关者自身没被验证（#62、#63）**：#62 护栏/校验器/回填器写完就算完成，从未跑过功能自检——骨架首轮自检即抓出**自身 4 个真缺陷**（命名检查迭代 dict 崩 / `assert_unique_ids` 返回类型错 / `merge_shared_json` 传 dict 崩 / `cn2int("洪武三年")` 返回 0）。**A 族复发第 3 次，复发位置从「数据」挪到「治理数据的工具」**：护栏自己静默失效时最贵，因为它伪装成已解决的问题。
> - **子型 A7 自检喂的形状 ≠ 生产形状（#63）**：为 #62 缺陷 ① 写的「修法」把 `check_naming_consistency()` 改成遍历 `.items()`，而 `LAYER_SPECS` 的真实声明是 **list of 3-tuples** → 从「解包崩」变成 `AttributeError: 'list' object has no attribute 'items'`，**B 族核心装置 100% 不可用却已被记为「已修复」**。成因是 `self_test.py` 里 `SK.LAYER_SPECS = {...}` **替被测对象换了容器类型**，喂给它一个生产环境从不存在的形状 → 自检通过、缺陷出厂。**A 族复发第 4 次**：这次缝出现在「自检与生产形状之间」。
>
> **纪律**：① 交付必须另报「**字段填充率表**」与「**目标查询问句逐问验收表**」，与 ERR/GAP 并列；② 填充率为 0 的排查顺序固定为「**先查是否被调用 → 再查解析覆盖面 → 最后才接受『原文确实没有』**」；③ 索引/适配器改键名后，必须跑一次「各层条数 vs 索引层计数」对账，不能只看 ERR；④ **凡新增「把关者」（校验器 / 回填器 / 护栏 / 断言），其有效性必须由一段可重跑的自检证明**（正反例各一），而不是由它的存在证明；自检样本须覆盖该函数的**真实主要入参**（#62 的 ④ 号缺陷即因只测了纯数字串、漏了纪年串）；⑤ **测试替身只允许替换「数据内容」，不允许替换「容器的类型 / 形状 / 键名」**——后者本身就在被验证契约之内；自检若需要「先把它改成另一种形状才跑得动」，应**怀疑实现，而不是配合实现**（#63）。

### B 族（8 条）｜键名 / ID / 编号：命名是隐形契约
> 共同根因：**命名在源数据、打包器、适配器、注册表四处分头书写，无单一来源；单复数与硬编码序号会静默错位**。
> #5 ID 对齐断裂（五处典型）、#13 业务 ID 撞号（分配权在 AI 源数据，试点两卷即互撞）、#39 业务 ID 序号取自 `slot` 而非记录全局序号（50 条规则仅 9 个唯一 ID 全撞 `ZG-R-501`）、#22 卷×段位容量不足撞号（按卷条数估容量，未按单层最大扩展系数预留）、#30 实例编号撞号（与《明会典》10 撞号 → 改号 11）、#23 层 schema 键名与打包器键名漂移（源 `chr` vs 容器 `chrs`，前 5 卷漏打包）、#54 子机构节点没有 ID（分配器只作用顶层记录 → 446/869 无归属，`右侍郎@兵部` 与 `@南京兵部` 无法区分）
>
> **纪律**：① **ID 分配权归打包器**——源数据只写槽位，打包器按「卷号×段容量+1」自动编 ID；② 派生节点 ID 规则必须**与父节点同一分配器**（`<父ID>#<序号>`），两处遍历器不得各自合成；③ 目录名 + 文件名前缀 + 索引槽位名**三处统一复数**；④ 实例编号取「registry 现有最大 +1」并核对无重复。

### C 族（6 条）｜语义判据方向判反 / 粒度选错
> 共同根因：**判据选错了维度，或方向搞反；且错了以后数量往往正常，计数发现不了**。
> #52 关系句主语与宾语判反（古汉语「**司历、监候佐之**」中主语在后，佐者是 B 不是 A；首跑配成「尚书佐侍郎」，方向转 180°）、#32 多模式分类器判定优先级写反（`左、右侍郎各一人` 被先判 `、`+`各` → 误落 P3，**恰好把用户提的那条判错**）、#47 用范围词判语域时全串匹配（`"留守司。" in scope_text` 命中正文「外卫各统于都司、行都司或**留守司**。」→ `05-051` 误判为留守司条，漏填 3 条世官）、#57 把「机构地位的排序键」当成「树深的包含关系约束」（v5/v8/v12 三次加 `if` 特例：`{内府,监}` / `{所,司}` / `{院,中枢}`）、#42 ORG 层级合法性判据用「严格递减」而非「非递减」、#40 ORG 层级枚举混装「中央机构」与「地方政区」（`府` 兼指宗人府与府州县）
>
> **纪律**：① **方向先验、数量后验**——关系/层级类结果先看方向再看条数；② **多模式分类器的判定顺序本身是设计的一部分**——高频常见句式必须排在低置信桶之前；③ **语域闸门锚定位置**（`startswith`），不用全串子串匹配；④ **每次要加 `if` 特例时先问「这是地位排序问题，还是包含关系问题」**——若是后者，排序判据从原理上不适用，应改用显式父→子允许表，或不校验层级只校验「无环 + 节点唯一」；⑤ 层级校验的价值上限是「拦住明显笔误」，不该期待它验证语义。

### D 族（7 条）｜枚举 / 字段与库不一致
> 共同根因：**枚举单点（`_kg_enums.py`）未随实例原文校准，缺值即报错或静默吸收**。
> #4 枚举口径漂移（注释 41 值、代码 43 值）、#15 枚举校验「报错终止」导致执行中断（《水东日记》**5 次中断**）、#27 封闭枚举在执行期被「就地吸收」（事件类型 23→111 种、文献 11→114 种、名录 **100% 库外**）、#34 职掌陈述句被抽成规则（规则层被非规范句污染）、#30（同前，编号侧）
>
> **纪律**：① 枚举校验改为**收集-报告-暂存**——未匹配值入 pending 表不中断，收尾统一决议 → registerVersion+1 → dry-run 回溯 → commit；② 但**打包前**对封闭枚举做 `value ∈ ENUM_SET` 硬校验，不在集内不许静默写入；③ 验证报告输出每层「值种数 vs schema 定义数」，比值 > 1.5 判口径漂移；④ 顶层类目太粗（名物 9 值、文献 11 值）会迫使 AI 自造顶层——宁可用「顶层封闭 + 子类开放登记」的树状。

### E 族（5 条）｜「条目 → 目标」映射被默认为一对一
> 共同根因：**抽取时假设「目标所属 = 该条目所属」，靠文本位置推断，多目标共处一条时必然错**。
> #53 关系句所在的条目 ≠ 该关系所属的编制条目（`侍郎佐之` 在**职掌条** `01-034`，编制在同机构**前一条** `01-033`，须回溯 `owning_item`，跨卷不回）、#60 沿革条目与机构之间没有关联字段（273 条仅 101 条查得到归属；`01-016` 一条含 5 条沿革属六部共有，而六部 ORG 在**另外 6 条**）、#59 派生机构（内阁）未挂回母机构（翰林院）成为孤岛（编制条文在母机构条目块内部）、#37 把「通用机构」另立模板容器排除在 ORG 之外（把「有没有具体实例」当成准入判据）、#44 ORG 树与 LINE 边表未同源同步维护（卷05 一次加 74 个京卫节点 → 缺 107 条树内边）
>
> **纪律**：**凡「条目 → 目标」映射都要显式建关联字段，不得依赖文本位置**。具体三条：① 沿革用 `owner_orgs[]` **可多值**，不要单值；② **个体名优先于集体名**（否则单独沿革被吞进「六部全体」）／**集体名须用显式触发形态**（原文 `吏、户、礼、兵、刑、工六部` 是**并列单字**，成员全名一次不出现，子串匹配永远失败）／**去重按 `name` 不按 `id`**（同名机构全库 74 组多 ID，「经历司」12 个）；③ **树是单一真相源，边表可派生**——新增子节点必须同步补边；④ 挂回母机构须**三处同步补齐**（ORG `parent` + 母机构 `children[]` + LINE 边）；⑤ **同型坑出现 2 次即升级为「纪律」**（#53 与 #60 即同一根因两次表现）。

### F 族（5 条）｜字段值语义不足（空值不携带信息）
> 共同根因：**字段存在 ≠ 字段有值 ≠ 字段的值可解释**；A 族讲「该有值却没有」，F 族讲「有值但值不够用」。
> #58 「归属字段留空」与「判定为无归属」共用一个值（1241 官职节点 387 个 `org_id=""`＝31%，绝大多数是**正确留空**的差遣军职）、#46 与条目无关的「全书性表」无处安放（5 张表被整体跳过）、#21 年谱年龄双轨口径误判（trl 首句虚岁 = `chr.age`+1，属**设计口径非 bug**，无单点声明时对账无法区分「设计如此」与「真错」）、#47（同前）、#11 版本差异坑（外部资料与用户文件内容不一致，须**以用户文件为唯一权威来源**）
>
> **纪律**：① 用「空串」表达两件事是设计缺陷——须拆成**具名类别**（如 `org_binding`：`机构 859 / 未明 253 / 差遣军职 112 / 封爵 12 / 土官 10`）+ **理由字段**；② 完成率须**剔出「不适用」做分母**（`机构 / (总数 − 差遣军职 − 封爵 − 土官)`）；③ 分类判定放**最终化阶段**（各来源合流后），不可在单路 `add()` 写入时做；④ 双轨口径（虚岁/年差、中英键位）须**单点书面声明**，否则对账必然误判。

### G 族（5 条）｜写盘幂等性 / 原子性缺失
> 共同根因：**打包器只有「全量重建」语义，没有「增量合并」语义；AI 手写多段源数据一次覆盖**。
> #12 单卷复跑截断共享文件（`build_base --volumes` 把指纹库从 **1197 条抹成该卷条数**）、#14 并行子代理半写文件与汇总竞态（他片读到半写文件瞬时 `ValueError`；summary「最后写入者覆盖」）、#2 产物覆盖回归（P0 修复用一次性脚本落在生成器之外，重跑丢失）、#3 original 手抄漂移（AI 手抄原文必然漂移）、#24 汉字卷名→数字卷号映射偏移（依赖读取顺序，序/前言插入后整体偏移；残留旧映射文件致验证合计虚高 147 vs 真实 76）
>
> **纪律**：① **所有 build 脚本统一增量语义**——带 `--volumes` 时「加载现有共享文件 → 只重算所请求卷 → 合并写回」，不带时从空重建为权威；② 写文件一律「临时文件 + rename」；③ **修复必须并入正式生成器**（`build_` 前缀、幂等），不落一次性散文件；④ AI 源数据只写条号/解读，**原文由打包器从 `_item_registry.json` 注入**；⑤ 卷号映射用**汉字卷名直接映射**，不依赖文件顺序；写出前**幂等清理**目标产物。

### H 族（4 条）｜切分口径按书而异、首次估算常错
> 共同根因：**每本书的符号体例/OCR 质量不同，底座切分不能复用同一套规则**。
> #33 无条级标记文本的「行=条」口径与估算基准（漏计 `◆` 章标记 5 行：324→319→正式 **317** 条）、#17 名录卷「行=表格行」与条目切分的张力（题名表一行多人、跨行四元组不能按行硬拆）、#18 CSV 物理行 ≠ 逻辑行（译文单元格含换行，**1313 ≠ 1192**）、#24（同前）
>

## 0. 把工厂当执行器（定位错误，最根本的坑）

- **症状**：调用工厂后直接产出执行命令、中间文件或正式知识产物（EPUB/指纹库/各层 JSON），把工厂当成"执行器"；或交付一份《操作指南》文档就完事，没有固化为 skill。
- **根因**：混淆了工厂与实例的职责。工厂的使命是**生成书实例 skill**（像 skill-creator 生成本工厂一样），执行是实例 skill 的职责。用户说"传一本书形成规范"要的是一个可复用的技能实例，不是一次性的执行结果。
- **对策**：
  - 工厂流程止步于：探查 → 反思设计 → 固化为书实例 skill（生成到本目录同级编号目录）→ 试点校验 → 交付 skill 本身。
  - 工厂阶段不生成 EPUB/指纹库/各层 JSON/报告——这些全部是实例 skill 被调用后的事。
  - 交付物是 skill 的路径、结构与调用方式，不是执行命令。
  - 用户后续说"处理《X》"→ 触发书实例 skill → 才执行底座与抽取。

## 0.1 层模板套用（结构设计错误，次根本的坑）

- **症状**：把六层当固定管线，每本书都全走一遍——传一本字典也硬建事件层、硬建状态机；或凭书类型标签（"史书"）直接默认全建，不做反思。
- **根因**：把《新官轨范》的具体层清单当成了方法本身。实际上事件层是用户提出"事件五元组 Registry"后才做的，结构化五维是用户问"除了流程还能怎么结构化"后讨论选定的——**层是设计出来的，不是预设的**。
- **对策**：
  - 反思阶段逐层回答"这本书为什么建/为什么不建"，给出数据证据（规范句密度/时序结构/叙事密度/术语体系）。
  - 用户方向优先：用户提出的结构化方向无条件列为候选。
  - 数据检验：素材不足判"点不是线"，不强行建模；未启用层写明理由。
  - 候选层清单交用户拍板后锁层；实例 skill 只含启用层，未启用层不做任何动作。

## 1. 重复读取 / 反复探查（最高频）

- **症状**：同一批输入读了很多遍；每轮靠 summary 恢复后仍要重读 schema。
- **根因**：① 上下文压缩后 schema 细节丢失；② 探查-执行边界没守住，探查蔓延成多次小步读取；③ 会话过长导致重复加载章节/指纹库/规则映射。
- **对策**：
  - 开工前**一次探查**：输入 + schema 样例 + 统计一次读完；连续两次读取不再改变计划即停止。
  - 把"关键 schema 样例 + 关键文件路径 + 枚举清单"固化进每轮报告/总结，压缩后可直接恢复，不用重读文件。
  - 共享加载：指纹库/章节解析/规则映射抽成公共基座，各层打包器复用（import 替代复制）。

## 2. 产物覆盖回归（P0 修复丢失）

- **症状**：先做 P0 止血，后来重跑打包器把已修复字段覆盖掉，同一件事验证两遍。
- **根因**：修复用一次性脚本（`_p0_*.py`）落在正式生成器之外；重跑正式生成器时修复不生效。
- **对策**：
  - **修复并入生成器**：P0 修复写进 `build_` 打包器成为标准产出，重跑不丢。
  - 重跑前先确认不会覆盖已修复字段；脚本一律正式化（`build_` 前缀、幂等），不落一次性散文件。

## 3. original 手抄漂移

- **症状**：AI 源数据里手抄的原文与指纹库有出入（漏字/异体），逐层累积误差。
- **根因**：让 AI 直接抄原文进源数据，抄写环节必然漂移。
- **对策**：AI 源数据只写条号/解读；打包器从 `_item_registry.json` 注入 original/norm。修正差异一律以指纹库为准。

## 4. 枚举口径漂移

- **症状**：注释里写"41 值"，代码里 43 值；新增枚举值后存量数据没回填，跨层 join 断裂。
- **根因**：枚举定义散落各打包器，无单点治理与版本控制。
- **对策**：枚举收进单文件（`_kg_enums.py` 等），registerVersion 模式——**新增值 version+1 并回溯全部存量**；验证脚本比对文档与代码口径。

## 5. ID 对齐断裂（五处典型）

- **症状**：实体归一无全局主键、流程层 events 空槽位占 XGF-E 前缀、结构层缺 item_id、结构 target 是文本、枚举口径漂移。
- **根因**：各层独立产出时没对齐"引用的东西是同一个"。
- **对策**：
  - 条锚点 item_id 作为所有层共同主键；derived_rule/events 引用让层间可跳转。
  - ID 命名空间唯一归属（XGF-E 只属事件层，其他层只引用）。
  - 结构层 target 用 ID 引用而非文本。
  - 审计口径：跨层索引 layer_count 直接暴露贯通层数。

## 6. 环境噪声导致验证结果读不全（Windows/PowerShell）

- **症状**：stdout 30000 字符截断、jieba 日志被当 NativeCommandError、前台 15s 自动转后台——命令结果读不全，验证要重跑。
- **根因**：依赖 stdout 看验证结果。
- **对策**：验证脚本写 .py 文件并把结果**重定向到文件**再读，不依赖 stdout；长任务用后台任务 + 文件输出。

## 7. 规则引擎喧宾夺主

- **症状**：先用代码触发词引擎产规则（204 条），被用户否决——规则判定必须 AI 一句一句分析，代码只是验缺漏。
- **根因**：把"可代码化的触发词"当成了"规则判定本身"。
- **对策**：代码引擎结果只作候选/提示，判定必须 AI 逐条；代码只验缺漏（覆盖/格式/引用/枚举）。

## 8. 粒度反复

- **症状**：先按段（620 段）做，用户改口"既然做了条，就用条的"，返工。
- **根因**：粒度方向假设没在开工前确认。
- **对策**：方向性假设（粒度/判定方式/交付形态）开工前跟用户确认，写进《操作指南》第 0 节；中途变更要重新出方案再执行。

## 9. 覆盖缺口被掩盖

- **症状**：某卷 94 条只建模了 50 条事件，剩余 44 条没提，用户误以为全量完成。
- **根因**：把缺口并入总量，或只报成功率。
- **对策**：如实报告"哪里缺、缺什么、补什么方案"；未建模/未命中项单列缺口清单，不并入总量。

## 10. 交付散件淹没重点

- **症状**：每层每卷 12 件 × 5 层逐件 present，用户找不到入口。
- **根因**：按"层 × 卷"粒度交付，而非按层聚合。
- **对策**：按层一组交付（归一汇总 + 验证清单 + 卷示例 + 跨层索引），交付物 6 组以内；跨层 CSV 作为最常用查询入口放最前。

## 11. 版本差异坑（外部资料与用户文件内容不一致）

- **症状**：结构化探查时用外部检索（40 卷足本/点校本）定位条目内容，发现用户提供的 txt（四库本 38 卷）中找不到对应条目，或文字表述有出入（如"参赞军务"条足本有、四库本无）。
- **根因**：古书版本众多（四库本/足本/点校本卷数、文字均有差异），外部检索定位的是另一版本。
- **对策**：**以用户提供的文件为唯一权威来源**；外部资料只作内容性质/学术定位的辅助理解，不作条目抽取依据；结构探查的密度信号、抽样、条目定位一律基于用户文件本身计算。

## 12. 单卷复跑截断共享文件（增量语义缺失）

- **症状**：`build_base.py --volumes NN` 从空字典重建指纹库并按卷过滤，单卷复跑把共享指纹库从 1197 条抹成该卷条数，下游各卷产物对照"不在指纹库"报 ERR；卷概要等共享 CSV 同样被覆盖。
- **根因**：打包器只有"全量重建"语义，没有"加载现有共享文件 → 只重算所请求卷 → 合并写回"的增量语义。
- **对策**：**所有 build_ 脚本统一增量语义**——带 --volumes 时加载既有共享文件、只重算请求卷、合并写回；不带时从空重建为权威口径；共享 CSV 合并时旧行数字字段转回 int（CSV 读回全是字符串）。

## 13. 业务 ID 撞号（ID 分配权错放）

- **症状**：多卷并行执行时，各 worker 从 001 起硬编码分配 APPT/SDJ-E/REG/LIT/REL/NAM/TRL 编号，validate 按层全局判重必然撞号（试点两卷即互撞），被迫人工重编号。
- **根因**：业务 ID 的分配权在 AI 源数据（手写）而非打包器；"ID 即内容"错误耦合。
- **对策**：**ID 改打包器自动分配**——源数据只写槽位（卷内顺序），打包器按"卷号×段容量+1"段位自动编 ID；AI 不再手写业务 ID；段位方案可作临时缓解（validate 全局判重兜底）。

## 14. 并行子代理半写文件与汇总竞态

- **症状**：并行片写 sources 过程中，他片 run_all 的 build_kg_join/汇总步骤读到半写文件触发瞬时 ValueError；summary 类共享文件"最后写入者覆盖"。
- **根因**：无原子写入；共享文件无合并语义。
- **对策**：写文件走"临时文件 + rename 落盘"；共享汇总文件统一增量合并语义；并行片错峰执行重跑型步骤，或由单一收敛者（全量 run_all）在收尾统一重建。

## 15. 枚举校验"报错终止"导致执行中断

- **症状**：执行期 LIT 无"集"、EVENT 无"军政/司法/边政"、REG 无"祭祀"、APPT_STATUS 无"起复/世袭/举荐"，打包器校验抛异常即中断整卷（本实例 5 次中断）。
- **根因**：枚举校验从"收集-报告"模式做成了"报错终止"模式，原文出现未枚举值就直接失败。
- **对策**：枚举校验改为**收集-报告-暂存**——未匹配值入 pending 表不中断，每卷/每片结束输出枚举使用分布，收尾统一决议（新增/归并/改名）→ registerVersion+1 → dry-run 回溯 → commit；新增值必须有实例证据。

## 16. TRL 长文翻译体风险

- **症状**：碑文/序/奏议/书启等长文条目翻译主观性最强，易滑向翻译体公式（"当……时""……之一""进行"式腔调），且逐条质量难以代码验证。
- **根因**：长文翻译自由度大；代码只能验覆盖（条目数=翻译数），验不了风格。
- **对策**：实例固化翻译风格规范（如余光中七条：译原意不译原字/长句拆并联/专名保留+括注/忌翻译体公式）；长文提供"分句群译"模板与篇幅参考；风格校验留给人工复核闭环兜底。

## 17. 名录卷"行=表格行"与条目切分的张力

- **症状**：指纹库逐行切条，但题名表一行多人（"杨善　萧维祯　马昻"）、跨行四元组（姓名/字/籍贯行 + 官职行），按行硬拆会打碎名录结构。
- **根因**：条目切分的"行=条"假设对表格式卷不成立。
- **对策**：底座按行切候选并标注卷结构提示（volume_summary 的 mode_hint）；NAM/APPT 层按表重组——整体一条 NAM 记录、entries 四元组数组化、分列小标题作 office 上下文；卷阅读模式（名录优先/谱牒优先）前置标注例外卷。

## 18. CSV 物理行 ≠ 逻辑行（含换行单元格）

- **症状**：译文等单元格内含换行，trl.csv 物理行 1313 ≠ 逻辑行 1192，手工按行数统计出错。
- **根因**：CSV 引号内换行是合法行为，但"数行数=数记录"的心智模型失效。
- **对策**：解析与计数一律按逻辑行（csv.reader / pandas），校验脚本按 item_id 或记录数计数，不数物理行。

## 19. 层产物顶层键名不统一

- **症状**：ent 单卷 JSON 顶层键为 annotations，其余层为 records，聚合器/跨层索引需特判分支。
- **根因**：各层 schema 书写时未约定统一容器键。
- **对策**：各层产物统一顶层键（records），或聚合器自动识别 annotations/records；每记录必带 volume 字段；schema 母版中固化。

## 20. 工具参数语义名不符实

- **症状**：validate.py 带 --volumes 参数仍全卷检查，仅靠"只看本卷行"约定判定本卷质量，输出全局 ERR 数易被误读为本卷失败。
- **根因**：参数语义与实现不一致。
- **对策**：工具参数要么真正按卷过滤输出，要么改名并明确文档约定（"全卷检查、只看本卷行"）；验证汇总区分"结构性错误 ERR / 执行缺口 GAP"，两者不可混读。

## 21. 年谱年龄双轨口径误判（《蘧编》）

- **症状**：年谱类书 trl 首句用**虚岁**标注（"万历四十一年（1613 年），我五十五岁"），而 chr.age 字段存**年差**（year − 出生年，出生年记 0，1613→54）；两者恒差 1。收尾对账时未读口径文档，把 trl 与 chr.age 的差 1 当成数据缺陷，险些全量误改。
- **根因**：同一年龄两种表示并存（人类阅读用虚岁、字段存储用年差）属**设计口径**而非 bug；无单点口径声明时对账无法区分"设计如此"与"真错"。
- **对策**：开工前锁定年龄口径并写入实例 schemas.md / 交付说明（显式声明"trl 首句虚岁 = age+1"）；对账脚本比对时按口径换算后再判一致；执行期不许两轨混淆互改。

## 22. 卷×段位容量不足撞号（《蘧编》）

- **症状**：跨卷业务 ID 段位初用"卷 NN × 100"，卷一条数多（卷一 40 条、每条约 20-30 个 ent/evt）段内不够分配，撞号。
- **根因**：段容量只按"卷条数"估算，没按"卷内单层最大记录数"预留；层内记录数可远超条数（多实体/多事件/多关系）。
- **对策**：段容量按"卷条数 × 单层最大扩展系数"预留（本项目改卷 × 500 后全卷 71 条 0 撞号）；validate 全局判重兜底；容量仍不够时扩段位并全量重跑（ID 重新分配，勿手工改号）。

## 23. 层 schema 键名与打包器键名漂移（《蘧编》）

- **症状**：源数据层键用单数（chr/trl），打包器层容器键用复数（chrs/trls），打包时报 KeyError 或静默丢层；前 5 卷曾因键名不匹配漏打包。
- **根因**：源数据键名约定与打包器容器键约定分处两处书写，无单一来源；复数/单数习惯不一致即漂移。
- **对策**：打包器内建**显式 SRC_KEY 映射表**（如 `{chrs:"chr", trls:"trl"}`）——打包容器键固定复数，源数据键名由映射表声明；实例化时把映射表固化进打包器模板，验证脚本按打包容器键检查覆盖。

## 24. 汉字卷名→数字卷号映射偏移（《蘧编》）

- **症状**：build_base 首跑按序数映射卷号（第一卷→01…），序/前言/后记/附录插入后整体偏移（卷一映射成 03），条目归属卷号全错，且 `_extract` 残留旧映射文件致验证合计虚高（147 vs 真实 76）。
- **根因**：卷号映射依赖"读取顺序"而非"卷名本身"；残留文件未清理导致验证读到陈旧数据。
- **对策**：卷号映射用**汉字卷名直接映射**（序/前言=00、卷一~二十=01–20、后记=21、附录=22），不依赖文件顺序；写出前**幂等清理**目标产物（重算前先删旧文件），验证数字以清理后实算为准。

## 25. 实例增量不走工厂（口径漂移）

- **症状**：用户或执行中直接给已有实例加层/改枚举/改 schema，未经工厂增量流程——新旧枚举漂移、新层 ID 段位与既有层冲突、schemas.md 与 enums.md 不同步、registry 失真，增量部分成为"野分支"。
- **根因**：工厂只定义了"首次实例化"五阶段，没有为已交付实例定义变更通道；增量是常态（三本书实例全部发生过事后增量）却无流程约束。
- **对策**：对已交付实例的一切规范级变更一律走 `increment-upgrade.md` 七步（证据检验 → 确认锁层 → 改实例规范 → 存量与管线衔接 → 试点 → 更新 registry → 学习回路）；增量结论以追加方式进实例反思记录；变更后 registry 与各库版本行同步更新。

## 26. 把反思过程记录全量塞进实例（实例臃肿）

- **症状**：实例 SKILL.md §0.1 沉积大段用户原话、逐层谈判过程与全部证据表，执行时是死重；上下文压缩后反复重读这些过程材料，拖慢每次调用。
- **根因**：混淆了"规范的结论"与"得出规范的过程"——实例是执行规范，不是工厂的会议纪要；过程材料应归工厂案例档案。
- **对策**：实例反思记录只固化**结论与锁层依据**（锁层表、口径、确认结果），完整探查/反思过程与用户原话存工厂 `case-feedback-<book-slug>.md`；增量结论以条目追加，不重写历史。

## 27. 封闭枚举在执行期被"就地吸收"（《客座赘语》）

- **症状**：schema 里写死"封闭 + 兜底"的枚举，执行完一统计，值数暴涨——事件类型 23 → 实际 **111 种**、文献类型 11 → **114 种**、名物 9 → **72 种**、涉明 8 → **94 种**、方言风俗 7 → **53 种**，地理层 8 → **52 种**（"山/山岭/山冈/山岳/山地/山石"六个词形并存）。库外值占比：事件 56%、文献 92%、名物 63%、名录 **100%**。枚举"封闭"名存实亡，跨卷不可比，回库时无口径可依。
- **根因**：① 打包器/验证器只校验"是否有值"，**不校验"值是否在封闭集内"**（或校验了但只警告不阻断），AI 遇到未匹配条目就自造一个词形继续写，V3"收集-报告-暂存"的闸门根本没合上；② 顶层类目太粗（名物只有 9 值、文献只有 11 值），面对笔记类书"什么都有"的内容，AI 只能往下细分；③ 缺少"新值必须先落 pending 表"的硬性动作点。
- **对策**：
  1. **验证器阻断**：打包时对封闭枚举做 `value ∈ ENUM_SET` 硬校验，不在集内 → 报错并列出待决议清单，不许静默写入（见 #15 的"报错终止"反面：这里恰恰要阻断，区别是阻断在**打包前**的源数据校验，不是执行中）。
  2. **值数告警**：验证报告输出每层"值种数 vs schema 定义数"，比值 > 1.5 即判口径漂移，必须走决议。
  3. **顶层先够用再封闭**：笔记/类书这类"内容无边界"的书，实例化时顶层类目宁可多给几个（文献按经史子集给、名物按顶层 13 类给），或用**树状**（顶层封闭 → 子类开放登记），避免 AI 被迫自造顶层。
  4. **同义归并前置**：schema 里直接给出别名映射与正反例（如"艺文/文学/著述 → 文事"），减少判定分歧。
  5. **执行期增量回库**：新值一旦决议通过，走 `enum-induction-guide.md` 的 registerVersion+1 与存量回溯，并**回写工厂基准库**（本坑与 #25 配套：不回库的增量就是野分支）。

## 28. 跨层索引目录名缺陷（《福惠全书》）

- **症状**：跨层索引 `_kg_join.json` 按单数键（`rules`/`structs`/`regs`/`opns`/`procs`/`docs`/`rels` 应为 `rule`/`struct`/`reg`/`opn`/`proc`/`doc`/`rel`）扫 `_layers/<key>/<key>_NN.json`，但产物目录与文件名全为**复数**（`_layers\rules\rules_01.json`）→ 首稿仅 ent 646 条入库、7 层漏扫（折叠 0 但只入 1 层）。联邦 adapter 同理（首稿用单数 key 扫目录漏 7 层）。
- **根因**：目录名/文件名/join 键三处命名各写各的（单数 vs 复数），无单一来源；打包器用复数目录、索引脚本默认单数键。
- **对策**：**目录名 + 文件名前缀 + join 槽位名三处统一复数**，adapter/索引脚本用显式 LAYER_DIR_NAMES 复数映射（目录名+文件名前缀双映射）；实例化时把映射表固化进打包器与联邦 adapter 模板；并入联邦前先跑 `federation.py load` 核对各层条数与 `_kg_join.json` 层计数一致（发现仅 1 层入库即目录名映射错）。

## 29. 联邦 adapter 目录名映射偏移（《福惠全书》）

- **症状**：kb-federation adapter 用单数 key（`_layers\<key>\<key>_NN.json`）扫福惠产物，首稿仅 ent 646 入库、7 层漏扫（2104 条实为 646+7 层 1458）；修复为复数映射（`LAYER_DIR_NAMES` 目录名+文件名前缀双映射）后 8 层 2104 条、折叠 0。
- **根因**：adapter 假设产物目录名与 LAYERS 列表 key 一致，未校验实际目录；前书（lgs/xzl/ysz）产物为单数目录，福惠打包器改用复数目录后 adapter 未同步。
- **对策**：adapter 内建显式 `LAYER_DIR_NAMES` 复数映射（目录名 + 文件名前缀），注册新书时先 `load --book X` 核对各层条数非 0 且与实例 `_kg_join.json` 计数一致；并入后 `refs` 前先跑 transform 确认 members 分布。

## 30. 实例编号撞号（《福惠全书》）

- **症状**：福惠实例原编号 `10-fuhuiquanshu-knowledge` 与先登记的 `10-minghuidian-knowledge` 撞号——registry 台账两行同为 10，实例目录、SKILL.md/schemas.md/交付报告/开工计划内全部引用指向同一编号。
- **根因**：编号分配"现有最大编号 +1"未与 registry 现有行核对（明会典先行占号 10）；多实例并行实例化时撞号概率上升。
- **对策**：实例化前先读 `references/registry.md` 现有编号，取**现有最大编号 +1** 并核对无重复；撞号后统一改号（目录 + 全部内部引用 + kb-mcp registry 路径同步），改号不重写内容；registry 登记后再撞号走 #25 增量流程修正。

## 31. 树结构与边表互为校验时未划"树内边/跨树边"（《明史·职官志》）

- **症状**：机构树（`children[]` 递归）与隶属边表（LINE `subordinate→superior`）互为校验时，报"仅边表有 `('吏部','天子')`"，看似数据缺陷。
- **根因**：根机构直隶「天子」的边**不属于树内父子关系**（天子是全书树根，非某机构的子节点），不入 `children[]`；不排除即双向校验变成双向误报。
- **对策**：**先定死边归属**——**树内边 = `children[]`；跨树边 = `superior=="天子"`（或等价"最高层"），不入 children[]，单独登记在 `org_tree.json` 的 `root`**；校验式 `set(树推边) == set(边表中 superior≠"天子" 的边)`。**凡「层级树 + 关系边表」双轨建模通用**（机构树/家族谱系/地理管辖/引用网络）；与 #28「目录名/键名三处不统一致静默漏扫」同族——都是双轨结构未定死归属。

## 32. 多模式分类器判定优先级写反（《明史·职官志》）

- **症状**：员额句式分类器把 `左、右侍郎各一人`（**应为 P1 并列带各**）判成 **P3 合称共享**（低置信桶），致用户特别关心的那条记录置信度被标低；分布统计看起来"正常"（各型都有命中），症状隐蔽。
- **根因**：分类器**先判 `、`+`各`（合称型）再判并列前缀型**；而 `左、右侍郎各一人` 同时含 `、` 与 `各`，被前一条件抢先命中。判定顺序未纳入设计。
- **对策**：**判定优先级本身是设计的一部分，必须显式写死并测试**。本案例正确顺序：**先判并列前缀型（P1/P2），再判合称共享型（P3）**——`if 有并列前缀: P1 if 含"各" else P2; elif 含"、" and 含"各": P3; else: P4`。凡是"多模式 + 优先级判定"的分类器（枚举归类、规则分型、实体类型判定、句式识别）都要：① 把优先级写成显式有序规则表；② 用**同时匹配多个模式的样本**做边界测试（本例 `左、右侍郎各一人` 即边界样本）。

## 33. 无条级标记文本的「行=条」口径与估算基准（《明史·职官志》）

- **症状**：正文有章/卷/目录三级标记但**无条级符号**（无 ○/△ 逐条标记）时，切分口径与条数估算无据可依；估算基准写错（拿实切数与非空行数直接比）会误报"偏差超 5%"。
- **根因**：切分口径按"行=条"推断；估算公式**漏计某一级标记行**（本例漏计 `◆` 章标记 5 行，致估算 324 实为 319）。
- **对策**：
  ① 口径 = **一行非空段落 = 一条**；`◆/◎/○` 等标记行与空行**一律不计条**；一行含多对象仍算一条（如六部各占一行）、一行含多段体例（编制+职掌+沿革）合并为同一条目三段。
  ② 估算公式 = **非空行 − 全部标记行（含所有级别）**，逐级核对不漏；本例 = 333 − `◆`5 − `◎`5 − `○`4 = **319**。
  ③ 切分脚本须打印逐卷实计数与估算对账（偏差非 0 回查）。
  ④ **估算基准本身必须先自证正确**——装置 bug 会被误读为 schema 缺陷（与 #20「工具参数语义名不符实」同源）。
  ⑤ 与 #17「名录卷行=表格行」、政学录/宛署「○ 分组标题不计数」同族（分级标记计数纪律）。

## 34. 职掌陈述句被抽成规则（《明史·职官志》）

- **症状**：机关职掌陈述句（"X司，掌X之事，以赞尚书"）被抽进 L2 规则层，规则层被非规范句污染。
- **根因**：`掌` 被当作规范触发词；但**职掌陈述是静态描述**（这个机构管什么），不是"应当/禁止/程序"型规范。
- **对策**：**职掌陈述句不抽规则**——归 L1 实体 + L4-ORG 承载；**仅"凡…/不得…/须…/听…"等规范句抽规则**。延伸原则：**非规范句不抽规则**（含本条职掌陈述句、#35 沿革句、《平平言》官箴说理句"呜呼/嗟夫"、亲历记事句"余令某县凡五年"）——建议合并为总原则：**"规则的判据是规范性语义，不是触发词出现"**。

## 35. 沿革内容被重复刻画（《明史·职官志》）

- **症状**：同一段沿革（"洪武十三年罢中书省"）可能同时进事件层、沿革层、任职层，三处重复建模，条目量虚增且三处易不一致。
- **根因**：沿革行天然同时是"纪年事件"+"机构阶段"+"人物任职"，未定分工即重复抽取。
- **对策**：**沿革三分承载，各记一视角，互不重复**——**TME**（时间视角：纪年事件点，全书纵向可排序）/ **L4-EVO**（机构视角：阶段切片，单机构横向）/ **APPT**（人物视角：任职记录）；三者以**双向引用**（TME `related_evo` ↔ EVO `related_tme`）拼接，打包器校验一致性；**三分之后不建事件层**（避免第三次刻画）。**判别建不建事件层的标准**：若沿革含完整 who/action/what 三元组（如政学录"条陈→部覆→奉旨"）→ 建 EVT；若为"某年某机构某变动"单点陈述（who 多空）→ 三分承载即可，不建 EVT。

## 36. 名录形态的编制清单被误建 NAM（《明史·职官志》）

- **症状**：逐镇/逐卫罗列的"镇守X总兵官一人，分守参将N人，游击将军N人"形似名录，被建进 NAM 名录层，致同一内容在 NAM 与 L4 两处存放。
- **根因**：按"表格式罗列 = 名录"的形态特征判定，未看**内容性质**（是否含人名）。
- **对策**：**判别标准 = 是否含人名**——**含人名 + 字/籍贯/官职四元组者建 NAM（题名录）**；**仅含官职员额（官职+人数+品级）者归 L4-ORG/RANK（编制陈述）**。卷五逐镇总兵官清单后者，归 L4。与 #17「名录卷行=表格行」配套：先判内容性质，再定切分与归属。

## 37. 把「通用机构」另立模板容器，排除在 ORG 之外（《明史·职官志》）

- **症状**：府/州/县/道/儒学/巡检司等"通用编制"（原文只有一份模板、天下诸处复用）被当作**非实体**，另立 `ORG_TEMPLATES` 模板容器 + `TPL-` 命名空间 + 独立 `_layers/templates/` 层落盘，排除在 ORG 树外。用户一眼看出问题：「这些应该是 org 吗？」
- **根因**：把"**有没有具体实例**"当成了 ORG 的准入判据，而 ORG 的准则是"**是不是原文陈述的机构**"。府/州/县在原文（明史·职官志 卷四 条54–75）都是**正式机构条目**，有品级、有员额、有隶属、有沿革；「通用编制」只是它们编制可复用的**额外属性**，不是另一种东西。模板容器还带来三重副作用：① ORG 树缺节点，机构树索引不完整；② 这些机构的员额/隶属无处安放（RANK/LINE 只认 ORG 记录）；③ 独立层目录与 ID 命名空间增加治理面。
- **对策**：
  - **ORG 准入判据 = 原文是否作为机构陈述**（有编制行/职掌行/沿革行），**不看是否有具体实例**。通用编制机构与专设机构同列 ORG 节点。
  - **不设模板/通用容器**。若确实需要标注"编制可复用"，作 ORG 节点上的**字段**（如 `note`/`reusable`），不另立容器与 ID 空间。
  - **转正须三处同步补齐（缺一即 ERR）**：① ORG 树 `children[]` 加子机构（**节点字典形态**，非名称字符串）；② RANK 层承接品级员额（品级员额的规范归属层是 RANK，ORG 节点上的 `posts[]` 只是摘要）；③ LINE 层补隶属边（区分树内边/跨树边，见 #31）。
  - **废弃容器须显式报错**：打包器对已废弃容器（如残留的 `ORG_TEMPLATES` 导出）直接 append ERR，避免静默丢数据。

## 38. 校验器按字段存在性分派维度时顺序写错（《明史·职官志》）

- **症状**：四维（ORG/RANK/LINE/EVO）混装于同一 `structs` 记录集，校验器按"字段存在性"分派维度。原顺序 `if "posts" in r`（RANK）在前，而转正后的 ORG 节点**同时带 `children[]` 与 `posts[]`** → ORG 被误判为 RANK，产出 120 条假 ERR：`RANK ORG-2038 rank_type 越界: None` / `vacancy_type 越界: None` / `post_status 越界: None` / `selection_route 越界: None`。
- **根因**：分派字段选用了**非唯一标识字段**。`posts[]` 在 ORG（编制摘要）与 RANK（本职）都出现，不具排他性；真正排他的是 `children[]`（**每个 ORG 节点必有，RANK 必无**）。
- **对策**：
  - **分派字段必须是该维度的"充要标识"**——出现即属该维度，且其他维度必不出现。选字段时先问："这个字段会不会在别的维度也出现？"
  - 本书定死分派顺序：**`children`（ORG）→ `change_type`（EVO）→ `line_type`（LINE）→ `posts`（RANK）**，`else` 报"无法识别维度"。
  - **假 ERR 也要查根因**：120 条 ERR 全部指向 `rank_type/vacancy_type/post_status/selection_route 越界: None`，值全是 `None` —— 这是"字段根本不存在"而非"字段值非法"，是**分派错误**的典型指纹。值全 `None` 且集中在一批新记录时，先怀疑分派，不要逐条补字段。

## 39. 业务 ID 序号取自 `slot` 而非记录全局序号（《明史·职官志》）

- **症状**：打包器分配业务 ID 时用 `prefix + (段位 + slot)`，而 `slot` 是"条目内语义顺序"、每个 `item_id` 都从 1 重启 → 所有条目的第 1 条记录撞成同一 ID。实测 50 条规则仅 9 个唯一 ID（全撞 `ZG-R-501`~`508`），`validate` 报 46 条 ERR。
- **根因**：把"条目内位置"当成了"全局位置"。ID 的唯一性由**记录在待分配列表中的全局序号**保证，不由其在所属条目内的语义槽位保证。
- **对策**：
  - `assign_ids` 改用 `enumerate(records, 1)` 全局序号；调用前按 `(item_id, slot)` 排序保证确定性；
  - 验证器全局判重兜底（每条记录 id 必须唯一）；
  - **豁免 `ents` 层**：`ents` 的 `id` 是**实体主键**（同一实体多次出现共用同一 id，属设计如此），验证器须豁免 ents 撞号校验，其余层不得豁免。凡"条目内有序槽位 + 打包器分配 ID"的实例通用。

## 40. ORG 层级枚举混装"中央机构"与"地方政区"（《明史·职官志》）

- **症状**：`府` 既指宗人府/顺天府（中央机构层），又指府州县之府（地方层），单一 `LEVEL_RANK` 会误判父子关系——`宗人府(府) -> 经历司(司)` 因被判同级而报"层级非法"。
- **根因**：层级枚举名本身多义（府/司/局/监），未在实例化时选定本书语义。
- **对策**：① 明确本书 `府` 取"中央机构层"（与部/院/寺/监同级）；② `州县` 降为该层下子级；③ 或拆分枚举为 `府(中央)` / `府(地方)`。**凡层级枚举含多义层级名的实例，实例化时须选定本书语义并写入 schemas**。与 #42 互补——本条讲**枚举粒度**，#42 讲**比较判据**。

## 41. LINE 边表节点名与 ORG 树节点名不一致（《明史·职官志》）

- **症状**：同一机构在树内作 `验封清吏司`、在边表作 `验封司`，树内边集比对即报"仅 LINE 有"。
- **根因**：树与边表分别手写，各自用了简称/别称。
- **对策**：边表 `subordinate`/`superior` **一律取 ORG 树的 `name` 原值**（不用简称/别称）；打包器树内边一致性校验兜底。与 #31「树内边/跨树边」、#44「树边同源维护」同族——都是双轨结构未定死节点命名。

## 42. ORG 层级合法性判据用「严格递减」而非「非递减」（《明史·职官志》）

- **症状**：卷03 首跑报 7 处"层级非法"（宦官→十二监、太仆寺→各牧监、八局→兵仗局等）。
- **根因**：同一层级名在史书中常兼任**「同级机构群」**角色——`宦官(内府) → 十二监(监)` 中，十二监**并非宦官的下属机构**，而是 **12 个同级监的集合名**。按"子必须严格低于父"判定，这类合法结构被误报。
- **对策**：`level_ok(parent, child) = LEVEL_RANK[child] >= LEVEL_RANK[parent]`（**同级允许**）。**凡「集合名 + 成员机构」同层建模的书通用**（二十四衙门/六科/五城/十三道/九寺）。

## 43. `children[]` 深度上限预设为 ≤3（《明史·职官志》）

- **症状**：明代宦官二十四衙门为**三层嵌套**（宦官 → 十二监 → 司礼监），树深度 = **4**，v2 设定的"深度 ≤3"校验误报。
- **根因**：上限按常识拍定，未先探查本书最深嵌套。
- **对策**：实例化时**先探查最深嵌套再定上限**，或直接设宽松值（如 ≤5）并在报告里输出实测最大深度。**凡含「机构群 → 成员机构 → 内部职官」三层结构的书通用**（宦官二十四衙门/女官六局/钦天监五官/五城兵马司）。

## 44. ORG 树与 LINE 边表未同源同步维护（《明史·职官志》）

- **症状**：新增 ORG 子节点时未同步补 LINE 边，触发"树内边仅 ORG 有"批量报错。卷03 一次新增 54 个子节点（钦天监 9 / 上林苑监 5 / 宦官各监司局 25 / 内府库房 15）即产生 54 条 ERR。
- **根因**：树与边表分两次书写，无同步约束。
- **对策**：① 写源数据时**先定树、后配边**；② 打包器报错信息**逐条列出缺失边**（便于批量补齐）；③ 若某节点确为**独立树根**（如"内府诸库房厂"原文附于宦官条后但结构上平级），其跨树归属用 `superior="天子"` + `note` 记实际隶属，**不可强行挂到中间层**。凡层级树 + 隶属边表双轨建模的书通用。

## 45. 建了字段却没回填数据（字段定义 ≠ 字段填充）

- **症状**：schema 里字段齐全、文档写得很漂亮，但实际数据里该字段 **100% 是占位值「未明」**。本实例 v3 按用户要求把 12 项编制字段全部纳入 `POST_FIELDS`（`salary_ref` / `vacancy_type` / `post_status` / `is_concurrent` / `selection_route` / `succession` …），抽取时一律写 `"未明"` 占位，致 `salary_ref`、`vacancy_type` **431/431 全空**；五卷五层跑完、ERR=0 GAP=0、跨层索引 0 空条目（验收指标全绿），直到用户拿 8 类真实查询来问才暴露「薪酬查不到、实虚职查不到」。
- **根因**：**字段定义与填报规则脱钩**。新增字段时只定义了「这个字段叫什么、是什么类型」，没有定义「什么情况下填什么值、从哪句原文取、由谁填」。字段进了 schema 但从未进入抽取流程，占位值让校验器无法察觉（占位值是**合法枚举值**，不是错误）。
- **对策**：
  - ① **新增字段必须同步给出回填规则**：触发词 / 证据句式 / 判定优先级 / 无证据时的留白策略。给不出回填规则的字段，不进 schema。
  - ② **留白策略要显式**：无证据时留「未明」还是留空？本实例定「**宁缺毋滥**」——宁可留「未明」，不臆测默认值污染数据（如 `vacancy_type` 仅 2 条有确凿原文证据就只填 2 条）。
  - ③ **交付前跑字段填充率体检**：统计各字段非占位值计数。填充率 0 的字段，要么补回填规则，要么**从 schema 删掉**（留着一个永远空转的字段比没有更糟——它让下游以为数据存在）。
  - ④ 能规则化的字段改由**打包器统一回填**而非 AI 手写（本实例 `_post_backfill.py` 由 `build_struct.py` 调用，源数据里一律写 `"未明"`）。

## 46. 与条目无关的「全书性表」无处安放

- **症状**：原文里有一类**不隶属任何条目**的表——总纲性的、跨全书的。本实例《明史·职官志》有 5 张：洪武二十五年俸禄表（18 级）、文散阶 42、文勋 10、武散阶 30、武勋 12。抽取时发现它们**既不属于某机构条目，也不属于某时间点**，任何一条记录都装不下，于是被整体跳过——薪酬查询因此永久无解。
- **根因**：层设计预设了「每条层记录都从某条目抽出」，没有为**全书性总表**预留归属位。切分以条目为单位，而这些表的粒度是「全书」。
- **对策**：
  - ① **设虚拟卷位**：以 `_vol = "00"` 落盘（本实例 `_layers/structs/structs_00.json`），与真实卷位并列而不干扰。
  - ② **`item_id` 用占位形式**（`"_book_<表名>"`），显式声明「非真实条目号」，**不参与跨层索引**（否则污染条目覆盖率统计）。
  - ③ **扩展该层的类型枚举**：本实例 `RANK_TYPES` 增 `俸禄` / `散阶` / `勋级`。
  - ④ **表项可用扩展字段**：posts 元素在通用三字段外可带 `amount` / `unit` 等专表字段。
  - ⑤ 若该表可作**查表键**（如品级→俸禄），另在枚举模块建映射函数（本实例 `salary_of(grade)` / `salary_ref_of(grade)`），供其他记录按 `grade` 查表回填。
- **附带教训**：**报错计数与落盘文件不一致时，先查写盘循环的集合来源**——本实例专表记录**已在内存中参与计数**（`RANK=104`）却**永不落盘**（`_layers/structs/` 只有 `structs_01.json`–`structs_05.json`），因为写盘循环是 `for v in vols:`（只含真实卷号）。改为 `sorted(set(vols) | {"00"})` 后正常。验证器应同时比对**内存计数**与**落盘计数**。

## 47. 用范围词判语域时全串匹配，被正文同形词污染

- **症状**：回填 `selection_route` 时，用「原文含『留守司。』则判为非卫所条」作闸门。结果 `05-051`（卫指挥使司条）**漏填 3 条世官**——因为该条原文含「外卫各统于都司、行都司或**留守司**。」，其中的「留守司」是**正文提及**，不是本条主旨。
- **根因**：用**子串存在性**判断「本条是什么条文」时，无法区分「词语是主旨」还是「词语被顺带提及」。位置信息被丢弃了。
- **对策**：
  - ① 语域闸门一律**锚定位置**：`scope_text.startswith(<锚点>)` 或正则 `^`（本实例修正为 `scope.startswith("留守司")`）。
  - ② 更稳的做法是**首句/首段**取样 + 锚定，而非全文扫描。
  - ③ **教训**：位置是最廉价的消歧手段。一个词出现在开头和在正文中段，语义权重完全不同——用全串匹配等于主动丢弃这个免费信号。
- **同源**：与 #44（边表节点名逐字一致）同属「文本比对口径不清」，但本条讲的是**位置**而非**字面**。

## 48. 中文数字的量纲前缀被误读成独立数位

- **症状**：原文「**一千**四十四石」被解析为 `144` 或 `1444`（视算法而异），而非正确的 **1044**。
- **根因**：中文数字的量纲前缀（千/百/万/亿）是**量纲标记**，不是可拆分的数位。「一千四十四」= 1000 + 44，不是 1 后接 044。「一千」的「一」与「千」必须**先合并成量纲单位**再与后续数值相加。
- **对策**：
  - ① 抽金额/员额/距离类数字时，**先识别量纲前缀**（千/百/万/亿）再合并，不可逐字拆数。
  - ② 抽样核验**跨量纲级差**：本实例正一品 1044 石 vs 从一品 888 石（同级差应在合理区间）；若正一品解析出 144，量级立即暴露错误。
  - ③ 量纲级数字**优先人工核对**（本书只有 19 个俸禄数，值得逐条核）。
- **同源**：与 v3 的 P1/P2/P3 员额句式同属「中文数量表述的消歧」，但本条针对**量纲**而非**分布**。

## 49. 把「机构」当唯一骨架，官职只作数组元素（**跨 A/M 两族：既是骨架构型错误，也是「验收口径错」的成因**）

- **症状**：五卷五层全绿（ERR=0 GAP=0）、跨层索引 317 条 0 空条目、验收指标全部达标后，用户拿 8 类真实查询来问，**3 答不了（上级官职 / 下级官职 / 平级官职）/ 3 半答**。根因：ORG 树 158 个节点**全是机构**，官职只是节点上 `posts[]` 的数组元素——**无独立 ID、无父子关系、无平级字段**。同时 L1 实体层已标注 1109 条 `official` 实体，却因官职无主键而**无法索引**（标注了等于没标注）。
- **根因**：把「组织架构」当成了唯一骨架。史书里机构与官职是**两套体系**：机构有隶属链（部→司），官职有品级位与副贰关系（尚书→侍郎→郎中）。只建机构树，官职就退化成机构的附属属性，官职与官职之间的关系无处表达。
- **对策**：
  - ① **Phase ② 反思时即枚举目标查询问句清单**（谁/何时/何职/上级/下级/平级/沿革/薪酬/职掌/区域…），逐问**标注由哪一层承载**。凡无层承载者即为设计缺口，**在实例化阶段补齐，不留到交付后**。这是本条最根本的对策——把「能不能回答 N 类查询」当**设计验收手段**而非事后补救。
  - ② 若书目含官职关系查询需求，**单建「官职层」**：官职独立主键 + 上下级边。低成本打法是复用现有 `posts[]`，加 `official_id` / `parent_official` / `org_path` / `subordinate_officials` 四字段（不需新读原文）。
  - ③ **官职边只建有原文显式表述者**（「X贰之」「X佐之」「为**首领官**」「兼领」），**不按品级相邻自动连边**——品级相邻是**组织包含关系**（郎中属司、司属部），已在 ORG 树内，重复建边是冗余。
  - ④ **「平级」定义必须写死**：建议取「同机构同品级」或「同机构同层级」，**不跨机构**——否则"平级"退化成"同品级列表"，恰恰是用户不想要的答案。
- **代价参照**：本实例评估约 1 个迭代（与一次中型改造同量级），非重做全书。

## 50. 验收指标全绿 ≠ 能回答用户的问题

- **症状**：工程指标全部达标——ERR=0、GAP=0、跨层索引 317 条 0 空条目（填充率 100%）、五卷五层 5105 条层记录、幂等复跑一致、文档齐备。但这些指标测的是「**层内自洽**」，不是「**能回答什么**」。用户拿 8 类真实查询一问，**3 答不了 / 3 半答 / 仅 2 能答**。
- **根因**：验收指标是**工程视角**的（结构合法、引用完整、无缺漏），用户的验收是**查询视角**的（我想知道 X，能不能查到）。两者可以完全脱节——本实例就是：`salary_ref` 字段合法存在（枚举值「未明」是合法值），校验器无话可说；但用户问「吏部尚书的俸禄是多少」时答不出来。
- **对策**：
  - ① **Phase ② 反思阶段产出「目标查询问句清单」**：从书目体裁枚举（本实例：上级 / 下级 / 平级 / 职务人数差遣 / 沿革 / 薪酬 / 任务 / 区域品级实虚职），逐问标注**由哪一层、哪些字段承载**。
  - ② **标注不出承载层的问句 = 设计缺口**，立即在实例化阶段补层或补字段，不留到交付后。
  - ③ **交付前用问句清单反向验收**：逐问实际查一次，答不出的即是缺口。**这比跑一次 validate 更能发现真问题**。
  - ④ 把「N 类查询命中率」作为与 ERR/GAP 并列的交付指标写进《项目总结报告》。
- **关系**：本条是 #45（字段空转）的**上位坑**——#45 讲「字段建了没填」，本条讲「连字段都没建，因为设计时没问『要回答什么』」。**先有问句清单，才有字段设计**。

## 51. 「平级」不定义清楚，就会退化成「同品级列表」

- **症状**：用户问「某某官的平级有哪些」，直接按 `GRADE_ORDER` 取同品级官职返回。看起来能用，实则错——「吏部郎中」和「户部郎中」同为正五品，但它们**不是平级**，只是品级相同。
- **根因**：中文「平级」在日常语境里至少有两义：①**同机构内同品级**（真正的同级同僚）②**全国同品级**（仅品级相同）。不做区分时，实现者会取最容易实现的后者，而用户要的通常是前者。
- **对策**：
  - ① **「平级」必须在设计阶段向用户确认定义，不可自行假定**。本实例用户 m02343 明确裁定：「平级指的同机构同品级 / 同层级，**不跨机构**」。
  - ② 定义写死后**在校验器里硬校验**：`m["org_id"] != n["org_id"] or m["grade_order"] != n["grade_order"]` → ERR。让定义可执行，而不只是文档里一句话。
  - ③ **同步排除错误做法**：「不按品级相邻自动连边」。品级相邻是**组织包含关系**（已在机构树内），不是官职关系；自动连边会产生大量假边且方向无意义。
- **关系**：与 #49（官职非骨架）同批出现——#49 讲「官职层缺位」，本条讲「官职层建起来后，关系语义没定死」。

## 52. 关系句的主语与宾语判反（「A…。B佐之」中 B 才是佐者）

- **症状**：抽取「A，职掌…。B佐之」中的官职上下级时，把 A 记成了佐者。整个关系方向转 180°——本实例首跑即把「侍郎佐尚书」配成「尚书佐侍郎」。
- **根因**：**古汉语的「佐之」结构里，主语在后**。「司历、监候**佐之**」意为「司历、监候**辅佐**（前者）」，即司历、监候是**佐者**，被佐者是上文那个官职。「贰之」同理（「侍郎**贰之**」= 侍郎是尚书之副）。现代汉语语感容易读成「A 佐 B」的主谓宾顺序，方向就反了。
- **对策**：
  - ① **标记词的语义方向必须从原文句式反推，并写进 schema 注释**：`主官 = 窗口内第一个官职名，佐者 = 其余`。
  - ② 抽完**先看方向再验数量**：方向错时数量往往正常（本实例首跑也有边），只查计数发现不了。
  - ③ 用一个**已知答案的样例**反向自检（本实例：尚书—侍郎，谁是谁的副贰，史料常识可判）。
- **关系**：#48（量纲前缀误读）同属「**中文语义理解坑**」——都是从字面结构推语义时踩的，共同对策是「找一句已知答案的原文做自检」。

## 53. 关系句所在的条目 ≠ 该关系所属的编制条目

- **症状**：在「侍郎佐之」所在条目里找机构语域，找不到（该条是职掌条，不讲编制），于是退回「按官职名取第一个匹配的机构」，把关系随机挂到了南京某部。
- **根因**：**关系句通常出现在职掌条（`掌…`）或卷首总述里，而非编制条（`设官…`）**。原文的行文体例是「编制行 → 职掌行 → 沿革行」三段，官职之间关系属**职掌**语义，故与关系句同条的是职掌行。而该机构的编制（官职清单）在同机构**前一条**。
- **对策**：
  - ① **沿条目序回溯到最近的前序同机构条目**（本实例定名 `owning_item`）来确定语域，**跨卷不回**。
  - ② **回溯落回自身时不得兜底**：本实例 `01-001` 是卷首总述，回溯后仍无对应机构，此时**只记 evidence 不建边**，**严禁**退化为「按名字取首个匹配」——那会静默产生错边。
  - ③ 回溯后仍未配对的关系表述**全部留档**进报告（含理由 + 原文窗口）供人工判，**留档 ≠ 失败**，是按纪律拒绝臆测。
- **关系**：本条是 #50（查询反推设计）在**语域归属**上的具体化——「这条边属于哪个机构」这一问，必须正面回答，不能靠兜底糊过去。

## 54. 子机构节点没有 ID，同名官职无法区分归属

- **症状**：官职层里「右侍郎」有两条，一条属兵部、一条属南京兵部，但两者**都无法确定机构归属**；或 `org_id` 全空，只能用 `(org_name, office)` 二级匹配。本实例 446/869 条无机构归属。
- **根因**：ID 分配器只作用于**顶层记录**，`children[]` 里的子节点从未进入分配循环——它们在数据结构上是「记录的字段」，不是「记录」。而官职层恰恰需要**叶子级粒度**（司务厅的司务 ≠ 兵部的司务）。
- **对策**：
  - ① 分级 ID：顶层用 `PREFIX-NNN`，子节点**按「父 id + 子序号」派生**（本实例 `ORG-505#1`），保证可递归定位且幂等。
  - ② **两处 ID 空间必须同源**：若有第二个遍历器（本实例 `walk_org`）也合成子节点 ID，必须**优先沿用记录里已有的 `id`**，仅在缺失时兜底，否则两处 ID 空间不一致。
  - ③ `posts[]` 元素要带**所在节点自身的 id**（本实例 `org_id`），**叶子不继承父 id**（继承会抹平叶子差异）。
  - ④ 回填要**覆盖所有来源**：本实例只对机构树回填了 `posts[].org_id`，漏了品级员额层，导致「侍郎」全部无归属。
- **关系**：#39（业务 ID 取 slot）同属 **ID 空间坑**——#39 讲「序号来源错」，本条讲「分配范围漏了子节点」。

## 55. 全书性表格的「复合句」，解析器只取第一组就丢掉了后续组（《明史·职官志》）

- **症状**：印信表解析后覆盖率长期只有 ~57%（157 个机构名），但**不报任何错误** —— 被丢的组不是「解析失败」，而是**从未进入解析结果**。实测漏采：`苑马寺`、`宣慰司`、`招讨司`、`安抚司`（原文有明确印信规格，却查不到）。
- **根因**：原文的表格句是**复合句**，一个句子含**多组「机构清单 + 品级 + 规格」**：
  ```
  通政司、大理寺、太常寺、詹事府、京卫、各按察司、各卫，俱正三品，
  苑马寺、宣慰司，俱从三品，铜印，方二寸七分，厚六分。
  ```
  解析器按「找**第一个**品级/规格标记 → 之前的都算机构清单」实现，于是 `苑马寺、宣慰司` 这段出现在**第一个标记之后**，被当成规格 token 直接跳过。
- **对策**：
  - ① 解析前先数**格式标记的个数**（本实例：句内 `俱X品` 出现次数 ≥2）→ 判定为复合句 → **按标记切段，逐段独立登记**（每段规格 = `该段标记 + 公共 spec 词起`）。
  - ② **首段可能没有标记**（`A、B、王府审理所，俱正六品，…`）：把「spec 词之前、首个标记之前」的 token 作为**独立首段**并入，否则首段同样会丢。
  - ③ 覆盖率提升要**当作验收指标报出来**（本例 157→235 个机构名，顶层覆盖 57%→81.6%）——静默丢数据不会自己暴露。
- **关系**：与 #45（字段定义≠字段填充）互补——#45 是「根本没接线」，本条是「接了线但解析漏了组」，两者症状都是「字段大量为空」，排查顺序：先查接线，再查解析覆盖面。

## 56. 属性回填器写完没接线，字段全域为空却不报错

- **症状**：新增 7 类属性字段，枚举定义齐全、回填函数可独立运行且逻辑正确，但打包后 ORG 节点上 `seal` 等字段**填充数为 0**，`ERR=0`，一切指标正常。
- **根因**：回填模块 `_xxx_backfill.py` 写完了、也 import 了，但 `build_struct.py` 里**从未调用其 `backfill()`**；而字段缺失不会触发任何校验（校验只管「值是否合法」，不管「值有没有」）。
- **对策**：
  - ① **新增字段必做「填充率体检」**：交付前逐字段统计非空节点数，输出成表（本实例：`seal` 165 / `jurisdiction` 64 / `powers` 27 / `station` 19 / `doc_channel` 5 / `assess` 4）。
  - ② **填充率为 0 时的排查顺序**：先确认 **build 脚本真的 import 且调用了**回填器 → 再确认回填器**覆盖面**（如 #55 的复合句丢组）→ 最后才接受「原文确实没有」。
  - ③ 把「字段填充率表」列入交付清单，与 ERR/GAP 并列——**ERR=0 只证明值合法，不证明有值**。
- **关系**：#45 是同一坑的首次记录（`salary_ref` 431/431 全空），本条是其**复发与升级**：首次是「建字段忘了写回填规则」，本次是「写好了回填器忘了接线」。**同坑复发说明检查单缺失**——故本条的正式对策是「把填充率体检写进交付清单」，而非再记一次症状。


## 57. 把「机构地位的排序键」当成「树深的包含关系约束」

- **症状**：树形校验器一次次报「层级非法」，每次都要为某个真实存在的隶属关系加一条 `if` 特例；加到第 3 次时才发现这**不是边界情况，是判据本身错了**。
- **根因**：`LEVEL_RANK = {"中枢": 1, "部": 2, "司": 3, ...}` 是**机构地位的粗略序**（谁比谁大），却被当作**父子包含关系的合法约束**（谁能包含谁）。这两件事**不相关**：地位高的机构可以被地位低的机构包含，地位相同的机构可以互相嵌套。
- **实测三例（本书三次放宽，同一根因）**：
  | 版本 | 报错场景 | 真实关系 |
  |---|---|---|
  | v5 | `宦官(内府) -> 十二监(监)`、`太仆寺(寺) -> 各牧监(监)` | 中间层是**同级机构群**，不是下级 |
  | v8 | `锦衣卫五所(所) -> 十司(司)` 与 `都司(司) -> 卫 -> 千户所(所)` | 军事编制里「司/所」**互为包含**，方向随体系而反 |
  | v12 | `翰林院(院) -> 内阁(中枢)` | 内阁**地位最高但由翰林院派生** |
- **对策**：
  - ① 判据改为**非递减** `LEVEL_RANK[child] >= LEVEL_RANK[parent]`（v5），至少不再把「同级嵌套」误报；
  - ② 但仍须逐个登记**方向相反**的组合特例（`{所,司}` / `{院,中枢}`）；
  - ③ **每次要加特例时，先问「这是地位排序问题，还是包含关系问题」**——若是后者，排序判据从原理上就不适用，加特例只是掩盖。正确做法是改用**显式的父→子允许表**，或干脆不校验层级、只校验「无环 + 节点唯一」；
  - ④ 层级校验的价值上限是「拦住明显笔误」，**不该期待它验证语义正确性**。
- **关系**：#42（严格递减→非递减）、#43（树深不得预设）与本条同源；本条是把前两条的**根因显式化**：判据选错了维度。#40（层级枚举混装中央/地方）是同一维度的枚举侧表现。


## 58. 「归属字段留空」与「判定为无归属」共用一个值，查询时分不清

- **症状**：1241 个官职节点中 387 个 `org_id=""`（31%）。抽样发现**绝大多数是正确留空**（差遣军职原文确无固定机构），但用户查询时会问「这 387 个是**查不到**还是**本来就没有**」——结构层面**无法区分**。
- **根因**：用「空字符串」同时表达了两件不同的事：**尚未判定**（待复核，是欠债）与**判定为不适用**（正确结果，不是欠债）。二者混装导致：① 无法计算真实完成率（387 中究竟多少是欠债？）；② 查询接口无法给用户任何解释；③ 交付时「31% 无归属」看起来像重大缺陷，实际大部分不是。
- **对策**：
  - ① 新增**分类字段**（本书 `org_binding`）+ **理由字段**（`org_binding_reason`），把「空」拆成多个**具名类别**：
    | 取值 | 语义 | 实测 |
    |---|---|---|
    | `机构` | 已归属（**唯一「已完成」值**） | 859 |
    | `未明` | 真未判定，待复核 | 253 |
    | `差遣军职` | 原文确无固定机构（总兵/参将/游击/把总） | 112 |
    | `封爵` | 爵位性官职（公侯伯/驸马都尉/仪宾） | 12 |
    | `土官` | 土司所辖（隶宣慰/宣抚/安抚/长官等司） | 10 |
  - ② **分类字段的取值必须能算出「目标完成率」**：本实例 `机构 / (总数 - 差遣军职 - 封爵 - 土官)` 才是真实完成率，把「不适用」剔出分母；
  - ③ 分类判定放在**最终化阶段**（各来源已合流后），不要放在 `add()` 单路写入时——后者只见单路来源，拿不到跨来源的判据（本书差遣军职判据需读卷段 `item_ids`）。
- **关系**：#45/#56（字段空转）讲「字段该有值却没有」；本条讲「字段**有值**但值的语义不够，空值不携带信息」。三者构成同一族：**字段存在 ≠ 字段有值 ≠ 字段的值可解释**。


## 59. 派生机构（内阁）未挂回母机构（翰林院），成为组织树上的孤岛

- **症状**：内阁有独立 ORG 节点、有 `core_officials` 列表，但 `children=[]`、`total_posts=0`；其下 6 个殿阁大学士官职节点**只有 1 个能关联到机构**，其余 6 个 `org_name` 为空；内阁所属的诰敕房/制敕房更被挂到了**另一个机构**（中书科）下。用户一眼看出：「我记得内阁应该是属于翰林院的。」

  - ① **归属以语义派生关系为准，不以文本位置为准**：原文三处互证内阁属翰林院 —— 条目位置（六殿阁大学士条在翰林院块内）／派生表述（「永乐初，**选翰林官入直内阁**」）／人选身份（所用皆翰林官）。

  - ④ **审计信号**：ORF 节点 `total_posts=0 且 children=[]` 却挂着 `core_officials`，是「有官无编制」的典型孤岛指纹，宜做成交付前的自动体检项。
- **关系**：#57（层级判据维度错）是本条修改判据时才暴露的连带坑；#54（子机构无 ID）与本条同属「组织树结构不完整」族。


## 60. 沿革条目与机构之间没有关联字段，273 条沿革中只有 101 条查得到归属

- **症状**：用户要求「列出机构沿革」，结构答不出来 —— EVO 记录键里**根本没有 owner/org/target 字段**，只有 `item_id`；于是只能按「同一 `item_id` 下有没有机构」间接关联，273 条里只有 101 条命中。
- **根因**：抽取时把「沿革」当成**条目级叙述**记录，假设「沿革所属机构 = 该条目所属机构」。这个假设对「一机构一条目」成立，但本书有**多机构共处一条总述条**的形态：`01-016` 一条内含 5 条沿革，属六部共有，而六部各自的 ORG 节点在**另外 6 条**编制条下（吏部 `01-009` / 户部 `01-019` / 礼部 `01-025` / 兵部 `01-033` / 刑部 `01-041` / 工部 `01-046`）→ `01-016` 自身无 ORG 节点，纯按 `item_id` 必失败。
- **对策**：
  - ① 新增 **`owner_orgs[]`（可多值）** ——沿革天然可属多个机构，**不要用单值字段**；
  - ② 四级归属判定（宁缺毋滥，判不出即空数组）：**① 该 item 下唯一 ORG → 直接归** / **② 多 ORG → 看沿革文本显式点名** / **③ 无 ORG → 个体名优先、其次集体名展开** / **④ 全库同名兜底**；
  - ③ **三条必守纪律**（均为实测踩坑）：
    - **个体名优先于集体名**：同一总述条内也有「只点名户部」的单条沿革；若先判集体，会把 8 条单独沿革错误挂到六部全体（首跑实测全被吞）。
    - **集体名须用显式触发形态**：原文写 `吏、户、礼、兵、刑、工六部` —— **并列单字**，成员全名「吏部」一次也不出现，「成员全名 in 文本」永远匹配不上（实测命中 `[]`）。须显式列出 `("六部", [...成员...], ["吏、户、礼、兵、刑、工", "六部", "六卿", "五部属"])`。
    - **去重按 `name` 而非按 `id`**：同名机构在全库有 74 组多 ID 实例（「经历司」12 个 /「司务厅」8 个），按 id 去重会得到 `['四司','四司','四司','四司']` 同义重复；同名多 ID 时保留**作用域最贴近该 item** 者。
  - ④ 交付时须报告**归属覆盖率**（本书 169/273 = 61.9%，多 owner 4）而非笼统说「已支持沿革查询」。
- **关系**：#53（关系句所在条目 ≠ 关系所属编制条）是本条的**同型坑**——都是「条目 → 机构」的映射被默认为一对一；#60 是沿革侧的复发，且因为多了「多机构共述 + 并列单字枚举」两个文本形态，「猜测式兜底」的破坏面更大。**同型坑第二次出现，应升级为「凡『条目 → 目标』映射都要显式建关联字段，不得依赖文本位置」的通用纪律。**

## 62. 护栏装置自己没跑过自检——「写了装置」被当成「装置有效」

- **症状**：为消除 A/B/G/P 四族错误，把纪律落成了代码骨架（`assets/skeletons/packer_skeleton.py`，五项护栏 + 公共基座）。骨架写完、`python packer_skeleton.py` 能跑出输出，看起来完成了。**给它写功能自检（验证「护栏遇到坏数据时真的会响」）后，首轮即抓出骨架自身 4 个真缺陷**：
  - ① `check_naming_consistency()` 直接 `for dir_name, slot_key, _ in LAYER_SPECS` 迭代 **dict** → 只拿到 key 字符串 → `ValueError: too many values to unpack (expected 3)`。**命名一致性检查整个是坏的**——而它正是 B 族的核心装置。
  - ② `assert_unique_ids()` 实现用 `seen[rid] = rec` 的 dict 结构却 `return dups`（list），文档与返回类型不一致，按文档用 `.get()` 的调用方会崩。
  - ③ `merge_shared_json()` 传 **dict** 时崩溃：`AttributeError: 'str' object has no attribute 'get'`——对 dict 也走 `it.get(key_field)`。而「指纹库增量合并」正是 G 族要修的那个场景。
  - ④ **`cn2int("洪武三年")` 返回 0**：函数从串首解析，遇「洪」非数字字立即 `break` → 0。而本函数在本书中的**主要用途恰恰是解析纪年串**（「洪武三年」「永乐二十二年」）。原实现只对「一千四十四」这类纯数字串做了自检，纯数字串是**通过**的——自检样本选得太窄。
- **根因**：把「装置存在」当成「装置有效」。这四个缺陷有一个共同特征：**它们全是静默的**——装置自己不会报错，只是不工作（① 直接崩，但只在实例真的配了不一致的 LAYER_SPECS 时才触发；②③④ 更隐蔽，只在特定入参下才现形）。**没有自检的护栏，本身就成为下一批静默失败，而且是最贵的一批——因为它伪装成已解决的问题。** 这与 #45（字段空转）、#56（回填器未接线）是同一族（A 族）的第三次复发，只是复发位置从「数据」挪到了「治理数据的工具」。
- **对策**：
  - ① **凡护栏/校验器/回填器，必须配功能自检**，且自检要验「**遇坏数据会不会响**」（正向 + 反向各一例），不能只验「函数能 import / 能跑通」。骨架自检 `assets/skeletons/self_test.py` 24 项即为范例，`PASS 24 / FAIL 0` 是接线的完成判据；
  - ② **自检样本要覆盖函数的真实主要用途**——④ 的漏网正因为只测了「纯数字串」这一种入参，而纪年串才是高频入参。**新函数先写下它「最常被喂什么」，再据此选样本**；
  - ③ **改动骨架任何函数后必须重跑自检**（已写进 `checklists.md` 检查单 K 与 `assets/skeletons/README.md`）；
  - ④ **缺陷留档**：骨架 README 保留了这 4 个缺陷的症状↔修法对照表，使后续实例看到的是「经过验证的骨架」，而不是「一份自认为对的代码」。
- **关系**：**A 族第 3 次复发**（#45 数据层 → #56 回填器接线层 → #62 工具自身层）。三次的共同句式都是**「看起来做完了，但没有任何机制证明它真的在工作」**。因此本条的通用形式应写为：**「任何新增的『把关者』（校验器/回填器/护栏/断言），其自身的有效性必须由一段可重跑的自检证明，而不是由它的存在证明。」**


## 63. #62 的修法本身制造了新缺陷：自检喂的形状 ≠ 生产形状，把关者照旧全坏

- **症状**：#62 记录骨架首版缺陷 ① 为「`check_naming_consistency()` 迭代 **dict** → `ValueError: too many values to unpack`」，并把修法写成 **遍历 `.items()`**。但 `LAYER_SPECS` 的真实声明是 **list of 3-tuples**（`packer_skeleton.py` 里明写「全部用复数，与 `_layers/<dir>/` 物理目录一致」）。于是修完变成：
  ```
  AttributeError: 'list' object has no attribute 'items'
    File "_common.py", line 134, in check_naming_consistency
      for name, spec in LAYER_SPECS.items():
  ```
  **从「解包崩」变成「AttributeError 崩」，B 族核心装置依然 100% 不可用**——但坑库里已经记着「已修复」。
- **根因**：**把修法当成结论抄了下来，却把「被修对象的真实形状」记错了。** 直接原因有二：
  1. #62 的档案文字声称「`LAYER_SPECS` 是 `{名称: (...)}`」，与代码里的 list 声明矛盾，错误描述被后续读者当作事实沿用；
  2. **`assets/skeletons/self_test.py:13` 里有一句 `SK.LAYER_SPECS = { "ents": (...), "rules": (...) }`** —— 自检为了构造「命名不一致」的用例，**把 LAYER_SPECS 换成了 dict**。它恰好喂给函数一个**生产环境从不存在的形状** → `.items()` 版实现顺利通过自检、缺陷照旧出厂。
- **这是子型 A6 的教科书样本，且比 #62 更深一层**：#62 是「护栏没跑过自检」，本条是「**自检跑了，但它替被测对象换了身衣服**」——把关者检验的是自己造的幻影，不是生产对象。**自检给假数据是可以的，换掉被测对象的类型/形状是不可以的。**
- **对策**：
  - ① **自检的被测对象形状必须与生产声明逐字一致**（本骨架改为 `SK.LAYER_SPECS = [("ents","ents","records"), ("rule","rules","records")]`，并加一条回归用例「**生产形状（list）下不崩**」）；
  - ② **测试替身（test double）只允许替换「数据内容」，不允许替换「容器的类型/形状/键名」**——后者正是被验证契约的一部分；
  - ③ **禁止为了让测试通过而改被测对象**：一旦自检需要「先把它改成另一种形状才跑得动」，正确反应是**怀疑实现，而不是配合实现**；
  - ④ **修 #62 类缺陷时，先回代码确认声明，再改实现**；坑库里的「修法」文字也须与代码同源（本条即是「坑库自身漂移」的实例）。
- **关系**：与 **#56**（回填器写完没接线）同族——**「装置的存在」与「装置的有效」之间那道缝，本条出现在「自检与生产形状之间」**。A 族第 4 次复发（#45 数据 → #56 接线 → #62 工具 → **#63 自检的保真度**）。


## 64. 中文数字解析器不认约数后缀：「十三万二千馀石」静默返回 `None`，整棵总账树为空

- **症状**：《明史·食货志》食货六的九边钱粮总账段（L272–L285，13 镇逐项数额）解析后**全为 `None`**。实测：
  ```
  cn2int('十三万二千馀')   = None
  cn2int('七十八万七千馀') = None
  ```
  但 `cn2int('一千四十四')` = 1044 正常——**函数没坏，是入参风格没覆盖**。
- **根因**：`cn2int` 的尾部剥离正则只列了量词与单位（`年|月|日|石|斗|升|人|员|名|匹|两|斤|贯|间|所|个|等`），**不含约数标记**。而史书/政书类文本的数额**绝大多数带约数后缀**：`馀 / 余 / 有奇 / 有馀 / 众 / 许 / 数`（「十三万二千**馀**石」「七十八万七千**馀**两」「十六万两**有奇**」）。`馀` 不是数字字，尾部锚定的 `re.search(r"[〇零一二三四五六七八九十百千万]+$", core)` 因串尾是 `馀` 而**失配** → 静默返回 `None` → 下游把 `None` 当 0 或跳过 → **整棵树为空，且不报任何错**。
- **更深一层的形态**：约数标记**不只在尾部，也会夹在数字中间**：
  | 原文 | 语义 | 处理 |
  |---|---|---|
  | `十三万二千馀石` | 132,000 余 | 尾部剥离 |
  | `四百三十馀万束` | 430 **余万** = 4,300,000 余 | **居中**，须整串剔除 |
  | `三十馀万` | 30 余万 = 300,000 余 | **居中** |
  | `万两有奇` | ≈10,000 两 | 尾部复合标记 |
  | `十六万两有奇` | ≈160,000 两 | 同上 |

  只做「尾部剥离」仍会漏掉居中形态（首修实测：`十三万二千馀石` 对了，`四百三十馀万束` 仍是 0）。**正确做法是：约数标记一律从整串中删除**（它们在任何位置都不贡献量值），再解析剩余的中文数字串。
- **顺带暴露的第 3 个独立缺陷**：修完约数后发现**裸「万」也解析为 0**——累加器在「万」分支写成 `section = (section + number) * unit`，**没有 `number or 1` 默认值**（`else` 分支才有）。故 `万`→0、`万两有奇`→0。但**简单补 `or 1` 又会过度修正**：`十万` 变成 110000、`四百三十馀万` 变成 4310000。
  **正解**：默认系数 1 只在**本段尚无任何数字**时生效——
  ```python
  coeff = number if (number or section) else 1
  section = (section + coeff) * unit
  ```
  （`万`→10000 ✅ ｜ `十万`→100000 ✅ ｜ `四百三十馀万`→4300000 ✅）
- **对策**：
  - ① **数值解析函数必须先探明本书的数额书写风格**再定剥离集：先 grep 高频后缀（`馀 / 有奇 / 许 / 数`），把它们全部登记进剥离集；**不得只按「标准中文数字」写**；
  - ② **约数标记按「全串剔除」实现，不按「尾部剥离」**（位置不固定）；
  - ③ **量纲单位与约数标记分两张表**管理，可重复剥离循环（`二千馀石`：先 `石` 再 `馀`）；
  - ④ **返回 `None` 必须被下游当错误处理**，不得静默当 0——本条的隐蔽性正来自「`None` 被无声吞掉」；
  - ⑤ **自检样本必须取真实原文串**：本函数自检原先只有 `一千四十四 / 三百 / 洪武三年`，**全是纯数字或纪年串，一个约数后缀都没有**——这正是 #62 对策 ② 「自检样本要覆盖函数的真实主要用途」的**再次失守**。现已补 11 条实测串（`十三万二千馀石 / 七十八万七千馀两 / 四百三十馀万束 / 万两有奇 / 十万 / 三十馀万` 等）。
- **量纲口径说明**：「有奇」意为「有余、零头」，**不参与数值**，解析结果即 `160000`；如需保留「该数为约数」这一语义，**由调用方另读原文**，不由 `cn2int` 承担（单值函数不额外返回标记，避免契约膨胀）。
- **关系**：与 **#48**（「一千四十四石」量纲前缀误读）**同一函数上的第 2 次复发**，同属 **P 族**——都是「数值解析的单点实现没覆盖真实主要入参」。**同型坑第 2 次出现应升级为通用纪律**：「凡中文数值解析器，先枚举本书实际出现的书写变体（约数后缀 / 量纲前缀 / 复合单位），再写实现与自检样本。」
