## 一、总论：这批错误是**一类**错误

把 65 条坑摊开按根因聚类，会发现它们**不是 65 件互不相干的事故**，而是同一件事在不同环节的复现：

> **工程流水线的每一段都在「静默假设」上一段的输出是对的、完整的、按你预期格式来的 —— 而它往往不是；错的输出不会报错，它会一路流到下游，最后变成一个「数字全绿但答不出用户问题」的成品。**

这条主线又分三层：

| 层次 | 内容 | 对应族 |
|---|---|---|
| **机制层**：错为什么不被发现 | 静默假设 + 静默失配 + 静默空转 | A / B / G / L |
| **语义层**：错为什么必然发生 | 古文语义与结构化工程的固有落差 | C / D / E / F |
| **方法层**：人（与 AI）在流程上怎么绕过去 | 口径不定、反思缺位、粒度反复 | M / N / O |

**四个最贵的复现模式**（反复出现 3 次以上，是本分类学的核心结论）：

1. **「静默失败」模式**（出现 **19** 次，最高频）：错不报错，指标全绿。
   - 代表：`salary_ref` 431/431 全空（#45）、`seal` 填充 0 但 ERR=0（#56）、跨层索引 7 层静默空回填（#28）、adapter 目录名偏移漏扫 7 层（#29）、印信表只取首组覆盖 57%（#55）、卷00 专表不落盘但计数（#46）。
   - **一句话纪律**：**没有报错 ≠ 有数据**。任何「填充率 0 / 覆盖率异常偏低」的指标，先查接线，再查解析，最后才接受「原文没有」。

2. **「命名即契约，但契约没有单一来源」模式**（出现 **7** 次）：单复数、前缀、序号在 4 处各写一份。
   - 代表：`ents`/`ent`、`rules`/`rule` 单复数混用（#28）、`annotations` vs `records`（#19）、源 `chr` vs 容器 `chrs`（#23）、ID 分配器只作用顶层（#54）、`slot` 当全局序号（#39）。
   - **一句话纪律**：**目录名 / 文件名前缀 / 索引槽位名 / schema 键名四者同源**；ID 分配权归打包器，源数据只写槽位。

3. **「方向判反」模式**（出现 **4+** 次）：排序、从属、主宾、层级比较的**方向写反**，而数量仍然正常。
   - 代表：`司历、监候佐之` 判成「尚书佐侍郎」（#52）、层级判据用严格递减（#42）、把「地位排序键」当「包含关系约束」（#57，三次加特例）、分类器优先级写反把用户提的那条判错（#32）。
   - **一句话纪律**：**关系/层级类结果先验方向，再验数量**；每次想加 `if` 特例时先问「这是排序问题还是包含问题」。

4. **「条目 → 目标映射被默认一对一」模式**（出现 **5** 次）：靠文本位置推断归属，多目标共处一条时必错。
   - 代表：沿革条与机构无关联字段（#60，273 条仅 101 可归属）、关系句所在条 ≠ 该关系所属条（#53）、派生机构未挂回母机构（#59）、通用机构另立模板容器（#37）、树与边表不同源（#44）。
   - **一句话纪律**：**凡「条目→目标」映射都要显式建关联字段（可多值）**，不得依赖文本位置。

## 二、十六族分类

### A 族（10 条）｜「校验通过」≠「数据可用」

**定义**：验收指标（ERR=0 / GAP=0 / 0 空条目）测的是**层内自洽**，不是**用户要查的东西在不在**。数据可以完全自洽而完全无用。

**实例分布**（跨 5 本）：mingshi-zhiguanzhi 6 条（#45 #46 #50 #55 #56 + #50 的 8 问验收）、wuzazu 2 条（#28 #29 同类）、pingpingyan 1 条（#20 参数语义）、**全工厂 2 条（#62 骨架自身 4 缺陷、#63 自检与生产形状不一致）**。
**两次独立命中同一结论**：《明史·职官志》8 类查询「2 能答 / 3 半答 / 3 答不了」（#50）与《五杂俎》#28/#29 的「7 层静默空回填」——**两本完全不同的书、两套不同的层设计，撞进同一族**，说明这不是实例问题而是方法问题。

**子型**：
- **A1 字段空转**：字段定义了、schema 写了、打包器读了，但没回填。#45（只定字段不加回填规则）、#56（回填器写完没接线）。
- **A2 解析器静默丢组**：接了线，但解析只覆盖首组。#55（复合句表格「X：A，Y：B，Z：C」只取第一组）。
- **A3 映射静默失配**：键名对不上，一行不报。#28 #29 #19。
- **A4 计数器与真相源不一致**：#46（内存计数 vs 落盘文件）。
- **A5 验收口径错**：#50 #20（指标本身没测到该测的东西）。
- **A6 把关者自身没被验证**（v1.1 新增）：**护栏 / 校验器 / 回填器写完即算完成，从未跑过功能自检**。#62（骨架首轮自检即抓出自身 4 个真缺陷：命名检查迭代 dict 崩 / `assert_unique_ids` 返回类型错 / `merge_shared_json` 传 dict 崩 / `cn2int("洪武三年")` 返回 0）。
- **A7 自检喂的形状 ≠ 生产形状**（v1.2 新增）：**自检为了跑通，替被测对象换了容器类型/形状/键名**，于是把关者检验的是自己造的幻影。#63 —— 为 #62 缺陷 ① 写的「修法」把 `check_naming_consistency()` 改成 `for name, spec in LAYER_SPECS.items()`，而 `LAYER_SPECS` 的真实声明是 **list of 3-tuples** → 从「解包崩」变成 `AttributeError: 'list' object has no attribute 'items'`。**B 族核心装置 100% 不可用，却被记为「已修复」**；漏网原因正是 `self_test.py` 里 `SK.LAYER_SPECS = {...}` 一句。
  > **A 族已四次复发，且复发位置逐层下移**：#45（数据层：字段没值）→ #56（接线层：回填器没被调用）→ #62（工具层：护栏自己静默失效）→ **#63（自检层：自检与被测对象形状不一致）**。四次的共同句式是**「看起来做完了，但没有任何机制证明它真的在工作」**。**把关者失效最贵——因为它伪装成已解决的问题。**

**系统性对策（六件套，缺一不可）**：
1. **字段填充率表**：每层每个扩展字段输出「已填 / 总数」，与 ERR/GAP 并列交付。填充率 = 0 直接判失败。
2. **目标查询问句逐问验收表**：开工前（Phase ②）就写「用户会拿这本书查什么」的问句清单，交付时逐条实测作答。**先有问句清单，才有字段设计**（#50）——这是根治 A5。
3. **各层条数 vs 索引层计数对账**：索引/适配器改动后必跑。
4. **静默失败专项自查**：交付前扫一遍「有没有哪个字段/哪一层是 0」，0 值必须给出解释（原文没有？还是没接线？）。
5. **把关者自检**（根治 A6）：凡新增校验器 / 回填器 / 护栏 / 断言，**其有效性须由一段可重跑的自检证明**（正反例各一），而不是由它的存在证明；自检样本必须覆盖该函数的**真实主要入参**（#62 第 ④ 号缺陷即因只测纯数字串、漏了纪年串）。骨架范例：`assets/skeletons/self_test.py`（现 36 项，`PASS 36 / FAIL 0` 为接线完成判据）。
6. **自检的保真度**（根治 A7）：**测试替身只允许替换「数据内容」，不允许替换「容器的类型 / 形状 / 键名」**——后者本身就在被验证契约之内。铁律：**自检若需要「先把它改成另一种形状才跑得动」，应怀疑实现，而不是配合实现**（#63）。自检须含一条「**生产形状下不崩**」的回归用例。

### B 族（8 条）｜键名 / ID / 编号：命名是隐形契约

**定义**：命名在**源数据、打包器、适配器、注册表**四处分头书写，没有单一来源；单复数差异与硬编码序号会静默错位。

**实例分布**：wuzazu（#5 #28 #29）、mingshi-zhiguanzhi（#22 #39 #54）、minghuidian（#13 #30）、yuanshuzaji（#23）。

**机理**：所有这类错误的**共同症状是「一行不报错」**——dict 取不到键返回 `None`/`""`，`for` 循环遍历空目录返回 0 次，ID 撞号在 JSON 里看不出来（除非专门查重）。因此它们全部被 A 族「静默失败」放大。

**对策**：
1. **ID 分配权归打包器**。源数据只写槽位（`slot`），打包器按「卷号 × 段容量 + 1」自动编 ID。分配权一旦落到 AI 手写的源数据里，试点两卷就会互撞（#13 实测：50 条规则只有 9 个唯一 ID）。
2. **段容量按「单层最大扩展系数」预留**，不按「条目数」估（#22）。
3. **派生节点与父节点同一分配器**：子节点 ID 用 `<父ID>#<序号>`，两个遍历器不得各自合成（#54 实测：446/869 子节点无 ID，导致同名官职 `右侍郎@兵部` 与 `右侍郎@南京兵部` 不可区分）。
4. **三处统一复数**：目录名 + 文件名前缀 + 索引槽位名（`ents`/`ent` 混用是 #28 的直接原因）。
5. **实例编号 = registry 现有最大 + 1**，登记前查重（#30 曾与《明会典》撞号）。

### C 族（6 条）｜语义判据方向判反 / 粒度选错

**定义**：判据选错了维度或方向搞反；**错了以后数量往往正常，计数发现不了**——这是本族最危险的特征。

**实例分布**：mingshi-zhiguanzhi 4 条（#52 #47 #57 #42 #40）、minghuidian 1 条（#32）、wuzazu/K 族交叉。

**典型三例**：
- **#52 主宾判反**：古汉语 `司历、监候佐之`，**主语在后**（B 佐 A），首跑配成「尚书佐侍郎」，方向转 180°，条数完全正常。
- **#47 语域闸门被正文同形词污染**：用 `"留守司。" in scope_text` 全串匹配，`05-051` 原文含「外卫各统于都司、行都司或**留守司**。」被误判为留守司条，漏填 3 条世官。**修法：锚定位置（`startswith`），不用全串子串匹配**。
- **#57 排序键当包含约束**：`LEVEL_RANK` 是「机构地位的粗略序」，不是「树深的严格约束」。v5 加特例 `{内府,监}`、v8 加 `{所,司}`、v12 加 `{院,中枢}` —— **同一个根因加了三次特例**，等于在声明「这个判据从原理上就不该用」。

**对策（本族最有价值的一条）**：
> **每次想加 `if` 特例时，先问：「这是『地位排序』问题，还是『包含关系』问题？」**
> - 若是**地位排序**（品级、官阶）→ 用有序枚举 + `>=`，允许同级（非递减）。
> - 若是**包含关系**（树深、隶属、编制）→ **排序判据从原理上不适用**；要么改用**显式父→子允许表**，要么**不校验层级，只校验「无环 + 节点唯一」**。
> - 加第 2 个特例时就应当触发这次追问；加到第 3 个已属「自我批评」欠账。

其余纪律：**方向先验、数量后验**；**多模式分类器的判定顺序本身是设计的一部分**（高频常见句式必须排在低置信桶之前，#32 就是把用户特意提的那条判错）。

### D 族（7 条）｜枚举 / 字段与库不一致

**定义**：枚举单点（`_kg_enums.py`）未随实例原文校准，缺值即报错或静默吸收。

**实例分布**：shuidongriji（#15，5 次中断）、wuzazu（#4 #27）、mingshi-zhiguanzhi（#34）、minghuidian（#30 交叉）。

**两种失败形态，恰好相反**：
- **报错终止型**（#15）：枚举校验遇未匹配值直接抛错 → 《水东日记》执行中**中断 5 次**，每次都要改枚举重跑。
- **静默吸收型**（#27）：封闭枚举在执行期被 AI「就地扩展」→ 事件类型 23→111 种、文献 11→114 种、名录 **100% 库外**。数据入库了，但 schema 形同虚设（且 100% 库外意味着**枚举定义完全没覆盖这本书**）。

**对策**：
1. **收集-报告-暂存，不中断**：未匹配值入 pending 表，收尾统一决议 → `registerVersion+1` → dry-run 回溯 → commit。
2. **打包前对封闭枚举做硬校验**：`value ∈ ENUM_SET`，不在集内不许静默写入（防静默吸收型）。
3. **口径漂移探针**：验证报告输出每层「值种数 vs schema 定义数」，比值 > 1.5 判漂移（#4 的根因是注释写 41 值、代码 43 值——**枚举定义自己都不一致**）。
4. **顶层类目太粗会迫使 AI 自造顶层**：名物 9 值、文献 11 值太窄；宁可用「**顶层封闭 + 子类开放登记**」的树状结构。

### E 族（5 条）｜「条目 → 目标」映射被默认为一对一

**定义**：抽取时假设「目标所属 = 该条目所属」，靠文本位置推断归属；**多目标共处一条时必然错**。

**实例分布**：mingshi-zhiguanzhi 5 条（#53 #60 #59 #37 #44）。**本族是《明史·职官志》贡献最集中的族**——因为典志体天然「一条讲一整个机构群」。

**四例**：
- **#53 关系条 ≠ 编制条**：`侍郎佐之` 出现在**职掌条** `01-034`，而编制在同机构**前一条** `01-033`。须沿条目序回溯到最近前序 ORG 条（`owning_item`），**跨卷不回**；回溯落回自身时不得兜底（严禁退化为「按名字取首个」）。
- **#60 沿革无归属字段**：273 条 EVO 仅 101 条能按 `item_id` 关联机构。`01-016` 一条含 5 条沿革（「洪武元年始置吏、户、礼、兵、刑、工六部」、「十三年，罢中书省，升六部秩」…）属**六部全体**，而六部 ORG 在**另外 6 条**里。→ 修法：EVO 加 `owner_orgs[]` **可多值**；**个体名优先于集体名**；**集体名须用显式触发形态**（原文 `吏、户、礼、兵、刑、工六部` 是**并列单字**，成员全名一次不出现，任何子串匹配都失败）；**去重按 `name` 不按 `id`**（同名机构全库 74 组多 ID，「经历司」有 12 个）。
- **#59 派生机构未挂回母机构**：内阁由翰林官入直而生，编制条文（`01-005` 六殿阁大学士）**位于翰林院条目块内部**，但 ORG 树里内阁 `parent="天子"`、翰林院 `children=[]` —— 双孤岛。用户凭常识指出（「我记得内阁应该是属于翰林院的」），机器没发现。**教训：原文的组织关系要用原文的条文位置来判定，不要用现代常识或名称直觉**。
- **#37 #44**：通用机构另立模板容器（把「有没有具体实例」当准入判据）／树与边表不同源（加 74 个京卫节点 → 缺 107 条树内边）。

**对策（五条）**：
1. **凡「条目 → 目标」映射都显式建关联字段**，可多值，不得依赖文本位置。
2. **个体名优先于集体名**，集体名须有显式触发形态。
3. **去重按 `name`**，不按 `id`。
4. **树是单一真相源，边表可派生**；新增子节点必须同步补边。
5. **挂回母机构须三处同步**：ORG `parent` + 母机构 `children[]` + LINE 边。
6. **同型坑出现 2 次即升级为「纪律」**（#53 与 #60 即同一根因两次表现）。

### F 族（5 条）｜字段值语义不足（空值不携带信息）

**定义**：字段**存在 ≠ 有值 ≠ 值可解释**。A 族讲「该有值却没有」，F 族讲「有值但值不够用」。

**实例分布**：mingshi-zhiguanzhi（#58 #46）、pingpingyan（#21）、fuhuiquanshu（#11）、wuzazu（#27 交叉）。

**核心案例 #58**：1241 个官职节点中 387 个 `org_id=""`（31%）。这 387 个**绝大多数是正确留空**——它们是 `05-006` 京营条「设副、参、游、佐、坐营、号头、中军、千把总等官」里的**差遣性军职，本就不属任何固定机构**。但「归属未明」（该有但没有）与「无归属（差遣军职）」（本就不该有）**共用一个空串**，查询时无法区分，也无法判断 31% 是缺陷还是正确。

→ 修法：拆成**具名类别**。最终 `org_binding` 五值：`机构 859 / 未明 253 / 遣差军职 112 / 封爵 12 / 土官 10`，**完成率剔出「不适用」做分母**：`859 / (1246 − 112 − 12 − 10) = 85.4%`（而非报 69%）。

**另外三例**：
- **#46 全书性专表无处安放**：5 张与单条机构无关的表（俸禄表 / 文散阶 / 文勋 / 武散阶 / 武勋）被整体跳过，因为「每条记录必须挂一个 item_id」的隐含设计容不下它们。→ 虚拟卷位 `_vol="00"` + `_book_<表名>` 占位 + 扩展类型枚举。
- **#21 双轨口径误判**：年谱「虚岁 = `chr.age` + 1」是**设计口径不是 bug**；没有单点书面声明时，对账无法区分「设计如此」与「真错」。→ 双轨口径（虚岁/年差、中英键位）**须单点书面声明**。
- **#11 版本差异**：外部资料与用户文件内容不一致时，**以用户文件为唯一权威来源**。

**对策**：① 用空串表达两件事是设计缺陷 → 拆具名类别 + 理由字段；② 完成率剔出不适用项；③ 分类判定放**最终化阶段**（各来源合流后），不可在单路 `add()` 写入时做；④ 双轨口径单点声明。

### G 族（5 条）｜写盘幂等性 / 原子性缺失

**定义**：打包器只有「全量重建」语义，没有「增量合并」语义；AI 手写多段源数据互相覆盖。

**实例分布**：shuidongriji（#12 最典型）、kezuozhuiyu（#14）、wuzazu（#2 #3）、fuhuiquanshu（#24）、pingpingyan。

**四例**：
- **#12 单卷复跑截断共享文件**：`build_base --volumes` 把指纹库从 **1197 条抹成该卷条数**。根因是所有 build 脚本的写盘语义是「重建」而非「合并」，而共享文件（指纹库、跨层索引）是跨卷累积的。
- **#14 并行竞态**：多个子代理同时写，他片读到半写文件瞬时 `ValueError`；summary 文件「最后写入者覆盖」。→ 写文件一律「**临时文件 + rename**」。
- **#2 产物覆盖回归**：P0 修复用一次性脚本落在生成器之外，重跑即丢失。→ **修复必须并入正式生成器**（`build_` 前缀、幂等），不落一次性散文件。
- **#3 original 手抄漂移**：AI 手抄原文必然漂移。→ **AI 源数据只写条号/解读，原文由打包器从 `_item_registry.json` 注入**。
- **#24 汉字卷名 → 数字卷号映射偏移**：依赖读取顺序，序/前言插入后整体偏移；残留旧映射文件致验证合计虚高（147 vs 真实 76）。→ 卷号映射用**汉字卷名直接映射**；写出前**幂等清理**目标产物。

**对策**：统一增量语义（带 `--volumes` 时「加载现有 → 只重算所请求卷 → 合并写回」，不带时从空重建为权威）；临时文件 + rename；修复并入正式生成器。

### H 族（4 条）｜切分口径按书而异、首次估算常错

**定义**：每本书的符号体例/OCR 质量不同，**底座切分不能复用同一套规则**。

**实例分布**：mingshi-zhiguanzhi（#33）、minghuidian（#19 交叉）、yuanshuzaji（#18）、fuhuiquanshu（#24）。

- **#33 无条级标记文本的切分**：《明史·职官志》首跑按「非空行」估条数 324，正式切分 **317**。修正判据为「**被正文包围的无句号段**」（不依赖 `○` 标记）。逐卷 53/74/55/75/60。**失败判据留档**：① 按 `◎` 后遍历遇 `。` 即停（卷序论含句号会中断）；② 从首个含 `。` 行向前回溯（首个即 index 0，不执行）。
- **#17 名录卷「行=表格行」与条目切分的张力**：题名表一行多人、跨行四元组不能按行硬拆。
- **#18 CSV 物理行 ≠ 逻辑行**：译文单元格含换行，**1313 ≠ 1192**。计数一律按逻辑行（`csv.reader`）。

**对策**：① 动工先查 `_item_registry.json` 实切条数，**不按标题数/非空行数建 task**；② 估算基准必须是「**非空行 − 全部标记行**」，试点装置要拿**实切数**与它比（首跑拿实切数与非空行数比，**误报 3 处「超 5%」**）；③ 名录/表格卷在底座阶段用 `mode_hint` 前标注。

### I 族（3 条）｜源文本污染（编码 / OCR）

**定义**：源文本本身是脏的，**不在底座归一阶段处理，下游全错**。

### J 族（3 条）｜规模与上下文

**定义**：书太大，一次读不完；或某类内容体量特别大，风格易滑。

### L 族（3 条）｜核查器自身缺陷

**定义**：核查/验证工具本身写错，产出**假 ERR 或假通过**。

### N 族（2 条）｜操作事故

### P 族（9 条）｜流程与语境失配

**定义**：做法本身没错，但用在**错的场景 / 错的语境 / 错的口径**上。症状多表现为「效率损失」或「归层错误」而非数据错误，因此最容易被漏记——本族 9 条是建表时的**遗漏补录**，这本身即是证据；#61 于 v13、**#64 于 v15** 补入。

- **#1 重复读取 / 反复探查（最高频）**：同一文件反复读、探查久不收口。→ **探查须有终止条件**：连续两次读取不再改变设计结论时立即停止（SKILL.md Phase ① 的硬性条款）。
- **#6 环境噪声导致验证结果读不全**（Windows/PowerShell）：中文显示乱码、多卷参数被逗号拆成 3 个参数致 0 条、输出截断。→ **「显示乱码」不等于「文件坏了」**（这是实例中反复确认的结论）；校验中文一律写临时 `.py` 再跑；每次设 `PYTHONIOENCODING=utf-8`；多卷不逗号并写。
- **#7 规则引擎喧宾夺主**：规则层条目数是实体层数倍，且多为职掌陈述句的机械切分。→ **可切分 ≠ 该抽**；规则层只收规范性语句（义务/程序/禁止/处罚型），职掌陈述句与官箴说理句不抽（同 #34）。
- **#16 TRL 长文翻译体风险**：碑文/序/奏议长文卷译文滑向公式化。→ **代码只能验覆盖验不了风格**，风格类质量交人工复核闭环（同 J 族）。
- **#36 名录形态的编制清单被误建 NAM**：编制清单被当成名录谱牒。→ 层准入判据必须是**语义条件**（名录层 = 有谱系/行辈/家世语义），不是形态条件（「看起来像清单」）。
- **#48 中文数字量纲前缀被误读成独立数位**：「一千四十四石」读成 1+44 或 1444。→ **数值/单位类解析一律单点函数化**（`salary_of()`），散落实现必然漂移。
- **#51 「平级」不定义清楚就退化成「同品级列表」**：278 条平级边混入跨机构同品级者。→ **影响范围可枚举时，定义必须落到校验器**（`m.org_id != n.org_id or m.grade_order != n.grade_order` → ERR）；本实例裁定「同机构同品级，不跨机构」。
- **#61 升级动作执行了但台账未回填，表格行数被误读为待办数**：`pending-review.md` 34 行状态停在「待评审」，实际 26 行早已编号入库（pitfalls #45–#60）。→ **「记录用文件」无校验器读取 → 缺回填压力**；升级与回填必须同一次完成，交付前对账「状态==待评审」行数，**不要用表格行数当待办数**。

**对策**：① 探查要有终止条件；② 层准入判据写**语义条件**不写形态条件；③ 定义能落校验器就落校验器；④ 数值/单位解析单点函数化；⑤ **记录与动作同时完成**——台账类文件无 ERR 兜底，写完动作不回填即失真。

> **落地过程本身产生了 #62**：骨架写完即可运行，但给它补写功能自检后，**首轮即抓出骨架自身 4 个真缺陷**（含 `cn2int("洪武三年")` 返回 0 —— 而解析纪年串正是该函数在本类书目中的主要用途）。这说明**「把纪律落成代码」并不自动等于「纪律生效」**：代码自己也需要被验证。故 A 族新增子型 A6 与纪律第 5 条，并要求此后**凡新增把关者（校验器/回填器/护栏/断言）必须附可重跑自检**。

相对地，**C / D / E / F 族（23 条，37%）是「语义侧」错误**，与书的文体强相关（典志体最重 E 族、年谱体最重 F 族），只能靠「原文实测 + 显式判据 + 方向先验」逐本处理。

> **建表本身暴露的元教训**：本分类学首版（v1，用户 m04106 指令）在归族时发现 **#1 / #6 / #7 / #16 / #36 / #48 / #51** 等 7 条**无处可归**——它们既不是「校验通过≠可用」，也不是命名/语义/写盘问题，而是「**做法本身没错，但用在错的场景/口径上**」（如 #1 探查没有终止条件、#7 可切分≠该抽、#36 名录形态的编制清单被误建 NAM）。故增设 **P 族「流程与语境失配」**。这说明**分类学的作用不只是整理已知，它还会暴露「哪些坑连归类都归不进去」**——而那些往往是最容易被反复忽略、也最难自动化的部分。P 族也是四族里唯一**装置只能减轻、不能根除**的一族（`ProbeTracker` 管终止条件、`SemanticGate` 管语域锚定，但「该不该抽」仍需 AI 逐句判断，见 #7）。

## 四、给工厂的八条总纪律

1. **静默失败优先怀疑**：任何指标异常偏低（填充率 0、某层 0 条、覆盖率 < 60%），排查顺序固定为「**是否被调用 → 解析覆盖面 → 最后才接受原文没有**」。
2. **命名四处同源**：目录名 / 文件名前缀 / 索引槽位名 / schema 键名；ID 分配权归打包器。
3. **关系方向先验**：排序、从属、主宾类结果，**先看方向再看条数**；想加第二个特例时先问「排序问题还是包含问题」。
4. **映射显式化**：凡「条目 → 目标」都要有关联字段（可多值）；个体名优先于集体名；树是单一真相源。
5. **先问句，再设计**：Phase ② 就产出「用户会查什么」的问句清单，交付时逐问验收 —— 这是 A 族（最大族）的唯一根治手段。
6. **判据写语义，不写形态；能落校验器就落校验器**：层准入看「语义是什么」而非「看起来像什么」（#36）；「平级」这类定义必须落到校验器（#51）；探查要有终止条件（#1）。这是 P 族的沉淀。
7. **记录与动作同时完成**：台账类文件（`pending-review.md` / `registry.md`）**无校验器读取、无 ERR 兜底**——升级动作做了不回填，它就会长期撒谎而无人发现（#61）。凡「动作改了正式库」的场合，同一次操作内回填台账，并在检查单里加对账项。
8. **纪律要落成代码或校验器**：只写在文档里的纪律，下一个实例必然重踩（#45 首记后 #56 复发的直接原因）。**A/B/G/P 四族的每条纪律都已有对应装置**（`FieldCoverage` / `LAYER_SPECS` / `atomic_write_*` / `SemanticGate`），新实例**复制骨架即接**；新增此四族的坑，必须同步落到 `assets/skeletons/` 的代码，不允许只更新本文件。
