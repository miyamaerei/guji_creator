### 第 2 轮（AI 补证据 + 确认锁层）

对每个候选层给出建/不建理由 + 数据检验：

**建的层（8）**：L0 底座 / L1 实体 / L2 规则 / L3 流程 / L4 四维（ORG·RANK·LINE·EVO）/ APPT / TME / 跨层索引。
（Phase ④ 试点实测：3 条真实条目跨 6 层试跑，枚举越界 ERR 0、分层边界断言 FAIL 0，方案可执行。）

其中 **L4 四维为本书定制**（未套用层库默认五维 LGR/TME/DOC/ACT/FRD，也未套用 enum-library §1.18 政书四维 ACT/FRD/LGR/TME）——因为：
- LGR（文簿台账）本书无（无簿册/格叶/状式）；
- FRD（防弊风险）本书无（职官志不载积弊）；
- ACT（角色职责）与 APPT + L1 重叠；
- 取而代之的是本书特有对象：**机构编制（ORG）/ 品级员额（RANK）/ 隶属统辖（LINE）/ 沿革阶段（EVO）**。

**TME 层为本书自定义层**（非层库既有）。
**注意**：层库既有 C12「年谱纪年索引层 CHR」与本书 TME 语义不同（CHR 为年谱年条总览，TME 为职官沿革纪年事件点），**不归并、不套用**。

**不建的层（14）**：L5 事件 / C2 文献资产 / C6 引书索引 / C7 名物 / C8 方言风俗 / C9 作者论说 / C10 明代纪事 / C11 奏疏谕旨互动 / C12 年谱纪年 / C13 文书条目 / REL 人物关系 / NAM 名录谱牒 / TRL 古今翻译 / V1 卷阅读模式。

**关键不建判定（有争议项，记录理由）**：

1. **L5 事件层不建**——理由：沿革中的"设/革/改"事件性内容已由 **TME（时间视角）+ L4-EVO（机构视角）** 双承载；再建事件层是**同一内容的第三次刻画**，无增量信息。这与《政学录》"沿革事件型"判建不同——政学录是"条陈→部覆→奉旨"的三元互动链（有 who/action/what 完整元组），本书是"某年某机构某变动"的单点陈述（who 多为空）。
2. **NAM 名录谱牒不建**——理由：卷五有大量"镇守X总兵官一人，分守参将N人，游击将军N人"逐镇清单，形似名录，但**本质是编制陈述**（员额 + 品级），归 **L4-ORG + L4-RANK** 承载更准确；建 NAM 会把同一内容两处存放。这是本实例与《水东日记》NAM 判建的关键分歧点。
3. **REL 人物关系不建**——理由：本书人名多为单点举例（李善长/徐达/杨士奇/夏言/严嵩/张居正），几无成对关系证据；建 REL 会产出大量证据薄弱的关系。
4. **V1 卷阅读模式不建**——理由：5 卷结构同质（均为机构编制罗列），无《水东日记》38 卷那样的内容形态差异，V1 无区分价值。

**确认结论**：用户拍板 8 层全建 + 机构条目粒度 + JSON/CSV 本地交付。

### 5.6 v3 员额置信度（用户 m00284 发现歧义后补）

用户原话（m00284，逐字）：
> "ok，可以，然后的话，我发现一个问题，   {"office":"左、右侍郎", "count":2, "grade":"正三品", "grade_order":5}, 这个感觉是左侍郎1，右侍郎1，但是不确定，所以需要补一个置信度，方便之后验证。然后都可以，请你入库"

**用户的直觉判断完全正确**，且源文本自身给出了判定依据。

**源文本实测：并列职官员额句式分三型**

| 型 | 句式 | 实测 | 语义 | confidence |
|---|---|---|---|---|
| **P1** | `左、右X各N人`（**带"各"**） | 55（全文）/ 49（装置） | **N × 并列项数** | **0.95** |
| **P2** | `左、右X N人`（**不带"各"**） | 11 / 8 | **N（本身即合计）** | **0.90** |
| **P3** | `各A、B N人`（合称共享） | 4（真歧义） | 疑共 N 亦可能各 N | **0.60 → 待核** |
| P4 | 单纯（"尚书一人"） | 1247 | 字面值 | 1.00 |

实例：P1 = `左、右侍郎各一人`（7 处，**全部带"各"**）/ `左、右都御史各一人` / `左、右佥都御史各二人`；P2 = `左、右司丞四人` / `左、右给事中二人` / `左、右断事二人`；P3 = `各设尚书、侍郎一人` / `各郎中、员外郎一人` / `各道置御史或五人或三、四人` / `各设左、右断事二人`。

**决定性对照（原文自证）**：同书用 `每属部设郎中、员外郎、主事各一人`（**各一人** = 各 1）表述"各1"，而 `各郎中、员外郎一人`（**一人**）表述含糊 —— **原文自身用「各」字的有无区分"各N"与"共N"**。故 P1/P2 可高置信判定，P3 须低置信 + 待核。

其他并列符号：`[东西南北]、[东南西北]…人` = 0 处；`正、副各一人` 类 = 2 处。

**v3 设计**：
- `COUNT_FORMS` 枚举 = `P1 并列带各 / P2 并列不带各 / P3 合称共享 / P4 单纯 / 未明`（封闭 + 兜底）。
- `posts[]` 元素新增 5 字段：`count_form` / `count_confidence` / `verify_needed` / `verify_reason` / `count_evidence`（另加 `office_parts` 原子职官数组）。
- 判决式：`verify_needed=True` ⟺ `count_form ∈ {P3,未明}` 或 `count_confidence < 0.8`；此类记录自动进 `_views/verify_needs_review.csv`。
- `office_parts` 由打包器生成，**原始层不拆**（保持原文可溯），仅在视图层按原子职官展开（`左侍郎 count=1 / 右侍郎 count=1`）。

**v3 实测**（`scripts/_pilot_validate_v3.py` → `_pilot_report_v3.txt`，抽样 1411 条句式 / **ERR 0**）：P4 1247 (88.4%) / P3 107 (7.6%) / P1 49 (3.5%) / P2 8 (0.6%)；语义判定 7/7 PASS；`office_parts` 展开 1411 → 1468 行（差 57 = 并列型拆分增量）；待核 156 条。

**v3 首跑撞到的判定优先级陷阱（重要教训）**：
- 首跑把 `左、右侍郎各一人` 误判为 **P3**（因分类器先判 `、`+`各`），致用户关心的那条记录被标成低置信 —— **恰好把用户提的那条记录判错**。
- **修正**：判定优先级改为 **先判并列前缀型（P1/P2），再判合称共享型（P3）**：`if is_par: P1 if has_ge else P2; elif ("、" in office) and has_ge: P3; else: P4`。修正后 `左、右侍郎` = **P1 / conf=0.95**。

## 7. 可跨书复用潜力（候选提案，见 `pending-review.md`）

1. **正史典志体型方案组合（zgz 型）**：L0 + L1 + L2 + L3 + L4 定制四维（ORG·RANK·LINE·EVO）+ APPT + TME。可复用于《明史》其余十四志、《宋史·职官志》《唐六典》类职官典志、乃至任何"机构编制 + 沿革"体史书。
2. **L4 四维 ORG/RANK/LINE/EVO 枚举**：机构视角的结构化维度，与既有 ACT/FRD/LGR/TME 语义不同档，缺此四类语义的基准值。
3. **TME 记时间、EVO 记机构、APPT 记人——沿革三段分工口径**：可复用于任何"沿革行"密集的史书/政书，避免重复建模。
4. **坑（切分纪律）：无条级标记文本的"行=条"口径**：`◆/◎/○` 三级标记但无条级符号时，须以「行 = 条 + 标记行不计数」为口径，并打印实计数与估算对账。
5. **坑（分层纪律）：职掌陈述句不抽规则**：与「官箴说理句不抽规则」同源异形（平平言坑），主体为机关职掌（"X司，掌X之事，以赞尚书"）时归实体/结构化承载，不抽规则。
6. **坑（层级判据）：`LEVEL_RANK` 是「机构地位粗略序」不是「树深严格约束」**：v5「同级允许」→ v8「内设机构放行」是**同一条设计原则的两级延伸**。凡层级枚举含多义层级名（府/司/局/监/所）的实例，须在实例化时认定：① 判据只防明显倒挂；② 实例化时先探查最深层级结构（v5 的「机构群」与 v8 的「内设机构」）；③ 必要时允许特定层级对**双向合法**（v8 的 `所` ↔ `司`）。可复用于《明会典·兵部》《清会典》武职、任何含卫所/营制的书。
7. **正向操作：树内边可**从 ORG 树递归派生**（`_gen_lines05.py` 模式）**：新增子树后不手写 LINE 边，写一次性脚本从 `children[]` 递归推出树内边、与已有边比对差集、按固定形态自动追加。这是 #44「树边同源维护」的操作化：**树是单一真相源，边表可派生**，两者不一致时优先怀疑口径而非逐条补数据。
8. **坑（多行结构批量编辑）**：用行级编辑工具删改多行字典时，必须以**完整记录**为单位（含首行），否则吞掉相邻记录开头行致 `SyntaxError`；批量删除优先用脚本配对匹配，改完立刻做语法预检。
9. **坑（枚举覆盖度探查）**：实例化阶段须实测**层级枚举覆盖度**——原文明示的层级名（京营/卫/所/都司/土司）是否都在 `ORG_LEVELS` 内有值。卷05 的 `京营` 无值只能靠 `LEVEL_RANK` 特判，属可避免的设计债。
10. **正向操作：全书性专表用「虚拟卷位 `_vol="00"`」承载**：与单条条目无关的总纲性表（俸禄/散阶/勋级等）落为该卷位的层记录，`item_id` 用 `"_book_<表名>"` 占位（不入跨层索引），该层类型枚举相应扩展。可复用于任何含「总表」的典志体/政书（《明会典》品级表、《唐六典》俸禄表）。
11. **正向操作：可规则化的字段由打包器统一回填（`_post_backfill.py` 模式）**：能按品级/白名单/证据词确定性判定的字段（`salary_ref` 按品级查表、`selection_route` 按语域闸门判定），源数据一律写 `"未明"`，由打包器在 `build_*` 内统一回填。好处：① 规则集中可测；② 源数据不被机械字段污染；③ 改规则即全量重算，不必逐条改源文件。
12. **坑（字段空转）：建了字段 ≠ 填了数据**：新增字段必须同步给出**回填规则 + 触发证据词**，否则不进 schema；交付前跑**字段填充率体检**，填充率 0 的字段要么补回填、要么从 schema 删掉。可复用于所有实例（本实例 `salary_ref` / `vacancy_type` 曾 431/431 全空）。
13. **坑（根本）：验收指标全绿 ≠ 能回答用户的问题**：ERR=0 / GAP=0 测的是「层内自洽」，不是「能不能查到 X」。**Phase ② 即产出「目标查询问句清单」并逐问标注承载层**，标注不出的即设计缺口。这是本实例最有价值的教训——五卷全绿之后才发现 3 类核心查询无解。
14. **坑（骨架构型）：把「机构」当唯一骨架会漏掉官职层**：史书里机构与官职是两套体系（机构有隶属链，官职有品级位与副贰关系）。只建机构树，官职就退化为附属属性，「官职的上下级/平级」类查询永久无解。**官职边只建有原文显式表述者**（「X贰之」「X佐之」「为首领官」「兼领」），不按品级相邻自动连边。「平级」须定义为「同机构同品级/同层级，不跨机构」。
