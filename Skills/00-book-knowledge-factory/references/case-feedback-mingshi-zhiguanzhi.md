## 1. 本实例的三条「元教训」（写进工厂，非本书特有）

**这是本档最该读的一节。** 完整推导见 §6 与 `error-taxonomy.md`。

1. **「结构自洽」与「能回答问题」是两件不同的事**（对应 A 族）
   五卷全部 ERR=0 / GAP=0 / 0 空条目之后，用户 m03393 一问「一般人查职官志会查什么」，实测 30 问得 **20 能答 / 10 答不了**。ERR/GAP/空条目测的是**层内自洽**；用户的验收是**「我想知道 X 能不能查到」**——二者可完全脱节（`salary_ref` 字段合法存在、「未明」是合法枚举值，校验器无话可说，但用户问薪酬时答不出来）。
   → **工程指标不是验收终点**。此后交付一律附「**字段填充率表**」+「**领域问句逐问验收表**」，与 ERR/GAP 并列（pitfalls #50 / #56；error-taxonomy §一 结论 1）。最根本对策：**Phase ② 就产出「目标查询问句清单」并逐问标注承载层**。

2. **加特例是判据错误的症状，不是修法**（对应 C 族）
   `LEVEL_RANK` 三次加 `if` 特例（v5 `{内府,监}` / v8 `{所,司}` / v12 `{院,中枢}`），加到第三次才承认「这是地位排序键，不该拿来当包含关系约束」。
   → **纪律：加第 2 个特例时就必须追问判据本身**（pitfalls #57；error-taxonomy §四 纪律 3）。**这是本实例最值得其他实例借鉴的一条流程纪律**——它把「反复打补丁」的隐性代价变成了显式的触发条件。

3. **一个根因出现两次，就该从「坑」升级为「纪律」**（对应 E 族）
   #53（关系条≠编制条）与 #60（沿革无 owner 字段）本是两条独立记录的坑，直到第二次出现才识别出共同根因「**条目→目标映射被默认一对一**」。若在 #53 时即升级为纪律，可**提前避免 #60 整轮返工**（273 条 EVO 事后补 `owner_orgs[]`）。
   → **判据：同一根因出现 2 次 → 停止记症状，改写为通用纪律**（见 §2 复用项 34；pitfalls #60）。

## 2. 可跨书复用潜力（34 条，候选提案见 `pending-review.md`）

> **本节是抽取出来的资产清单。** 每条都注明「正例（值得复用）」或「坑（需防范）」。按性质分四组。

### 2.1 层方案与结构（可直接复用的设计）

1. **正史典志体型方案组合（zgz 型）**：L0 + L1 + L2 + L3 + L4 定制四维（ORG·RANK·LINE·EVO）+ APPT + TME。可复用于《明史》其余十四志、《宋史·职官志》《唐六典》类职官典志、乃至任何「机构编制 + 沿革」体史书。
2. **L4 四维 ORG/RANK/LINE/EVO 枚举**：机构视角的结构化维度，与既有 ACT/FRD/LGR/TME 语义不同档，缺此四类语义的基准值。
3. **TME 记时间、EVO 记机构、APPT 记人 —— 沿革三段分工口径**：可复用于任何「沿革行」密集的史书/政书，避免重复建模。
4. **官职层（C15）**：官职作为独立实体 + `peers`（同机构同品级）+ `relations`（副贰/首领/兼领）+ `subordinates`；适用题名录 / 缙绅录 / 官制书 / 会典。
5. **机构附加属性族（v11）**：ORG/官职上挂 6 类制度性属性（`seal` 印信 / `powers` 权力类型 / `assess` 考核 / `doc_channel` 文书权限 / `jurisdiction` 管辖范围 / `station` 驻地），每类都是「值 + 证据 + confidence」三元组。可复用于《明会典》《清会典》《唐六典》及任何载有印信制度/职掌/驻地沿革的官制书。**这 6 类弥补了纯编制/品级模型的空白：它回答的不是「谁领导谁」，而是「这个机构实际怎么运转」。**
6. **两层定量结构**：`grade_based`（按等级保底）+ `actual`（个别实际，没有就不填）——可复用于俸禄 / 赏赐 / 配额 / 赋役 / 驿传供给。
7. **正道操作：全书性专表用「虚拟卷位 `_vol="00"`」承载**：与单条条目无关的总纲性表（俸禄/散阶/勋级等）落为该卷位的层记录，`item_id` 用 `"_book_<表名>"` 占位（不入跨层索引），该层类型枚举相应扩展。可复用于任何含「总表」的典志体/政书（《明会典》品级表、《唐六典》俸禄表）。
8. **正道操作：可规则化的字段由打包器统一回填（`_post_backfill.py` 模式）**：能按品级/白名单/证据词确定性判定的字段（`salary_ref` 按品级查表、`selection_route` 按语域闸门判定），源数据一律写 `"未明"`，由打包器在 `build_*` 内统一回填。好处：① 规则集中可测；② 源数据不被机械字段污染；③ 改规则即全量重算，不必逐条改源文件。
9. **正道操作：原文有「现成且有结构」的数据段时，写确定性解析器而非调 AI**：道制驻点（括注 `(驻省)` 类 79 处 + 行内 `驻` 121 处）形态规整，写解析器得 206 道 / 89 驻点，**零抽取误差且可重跑**。判据：**数据段有固定标记形态 → 解析器；语义需理解 → AI 抽取**。
10. **正道操作：树内边可从 ORG 树递归派生**（`_gen_lines05.py` 模式）：新增子树后不手写 LINE 边，写一次性脚本从 `children[]` 递归推出树内边、与已有边比对差集、按固定形态自动追加。这是 #44「树边同源维护」的操作化：**树是单一真相源，边表可派生**，两者不一致时优先怀疑口径而非逐条补数据。

### 2.2 分层与抽取纪律（判断口径）

11. **坑（切分纪律）：无条级标记文本的"行=条"口径**：`◆/◎/○` 三级标记但无条级符号时，须以「行 = 条 + 标记行不计数」为口径，并打印实计数与估算对账。
12. **坑（分层纪律）：职掌陈述句不抽规则**：与「官箴说理句不抽规则」**同源异形**（平平言坑），主体为机关职掌（「X司，掌X之事，以赞尚书」）时归实体/结构化承载，不抽规则。
13. **坑（层级判据）：`LEVEL_RANK` 是「机构地位粗略序」不是「树深严格约束」**：v5「同级允许」→ v8「内设机构放行」是**同一条设计原则的两级延伸**。凡层级枚举含多义层级名（府/司/局/监/所）的实例，须在实例化时认定：① 判据只防明显倒挂；② 实例化时先探查最深层级结构（v5 的「机构群」与 v8 的「内设机构」）；③ 必要时允许特定层级对**双向合法**（v8 的 `所` ↔ `司`）。可复用于《明会典·兵部》《清会典》武职、任何含卫所/营制的书。
14. **坑（枚举覆盖度探查）**：实例化阶段须实测**层级枚举覆盖度**——原文明示的层级名（京营/卫/所/都司/土司）是否都在 `ORG_LEVELS` 内有值。卷05 的 `京营` 无值只能靠 `LEVEL_RANK` 特判，属可避免的设计债。
15. **坑（骨架构型）：把「机构」当唯一骨架会漏掉官职层**：史书里机构与官职是两套体系（机构有隶属链，官职有品级位与副贰关系）。只建机构树，官职就退化为附属属性，「官职的上下级/平级」类查询永久无解。**官职边只建有原文显式表述者**（「X贰之」「X佐之」「为首领官」「兼领」），不按品级相邻自动连边。「平级」须定义为「同机构同品级/同层级，不跨机构」。
16. **语义定义落到校验器**：「平级 = 同机构同品级」不只是文档描述，而是 `m.org_id != n.org_id or m.grade_order != n.grade_order` → ERR；**定义不可执行就等于没定义**。
17. **用户点名的类，先量证据密度再决定建不建**：勘查顺序＝先逐词计数（含假阳性甄别）→ 出表格 → 再定建/不建。用户已给「没有就算了」的口子时，**忠实执行比凑数重要**（本实例 7 类只建 6 类）。且**已有字段能承载的须明确指出「已由 X 承担」**，不新开语义重叠字段。
18. **实例化时先问「哪些数据是原文明写但项目未建」**：v11 发现道制 200+ 道名的驻点数据（`(驻省)` `(驻广信)` 类括注 79 处 + 行内 `驻` 121 处）是**现成的、有结构的**数据源却未建为 ORG 子节点。可作为后续增量，也是所有实例自检的通用问题。

### 2.3 坑（需防范的错误模式）

19. **坑 关系句主宾判反**：古汉语「B佐之」中 B 才是佐者（主语在后）；**方向错时数量往往正常**，须先看方向再验数量，并用已知答案样例自检。
20. **坑 关系条 ≠ 编制条**：关系句在职掌条，编制在同机构前一条 → 须回溯 `owning_item` 定语域；**回溯落回自身时严禁兜底**（宁可留档）。
21. **坑 子机构无 ID**：ID 分配器只作用顶层记录，`children[]` 子节点是「字段」不是「记录」；须按「父 id + 子序号」派生，且两处遍历器的 ID 空间必须同源。
22. **坑（字段空转）：建了字段 ≠ 填了数据**：新增字段必须同步给出**回填规则 + 触发证据词**，否则不进 schema；交付前跑**字段填充率体检**，填充率 0 的字段要么补回填、要么从 schema 删掉。可复用于所有实例（本实例 `salary_ref` / `vacancy_type` 曾 431/431 全空）。
23. **坑（根本）：验收指标全绿 ≠ 能回答用户的问题**：见 §1 元教训 1。
24. **坑 复合句解析静默丢数据（v11 最重要）**：一个原文句含**多组「清单 + 品级 + 规格」**时，解析器若按「找第一个标记 → 之前的都算清单」，第二组清单会被当作规格跳过。修法：数格式标记个数 ≥2 判为复合句 → 按标记切段逐段登记；且**首段可能无标记**须独立并入。实测归一后唯一机构名 157→235、覆盖率 57%→81.6%。**教训：覆盖率提升也要当验收指标报出来。**
25. **坑 新脚本写了但没接进管线**：`_seal_backfill.py` 逻辑正确、独立可跑，但 `build_struct.py` 从未调用它 → 填充数 0 而 ERR=0。**根因是检查单缺失**：pitfalls #45 当时只记了「字段要回填」，没把「填充率体检」写进流程。定死排查顺序：**先查是否被调用 → 再查解析覆盖面 → 最后才接受「原文没有」**。
26. **坑 印信表的机构—规格对照须做完整性归一**：原文这类表常以一串机构名共享一条规格；须**分词 → 归一 → 比对 → 再回填**，否则漏配且静默。可复用于所有「以品级为纲列印信/仪制/俸禄规格」的典志体表格。
27. **坑 把「地位排序键」当成「包含关系约束」**（同坑第三次复发）：见 §1 元教训 2。
28. **坑 空值必须具名化**：1241 官职节点中 387 个 `org_id=""`，其中**大多数是正确留空**（差遣军职原文确无固定机构），却与「未判定」共用空串 → 完成率算不出、查询无法解释、交付时看起来像重大缺陷。**对策**：新增分类字段（`org_binding` 5 值：`机构 859 / 未明 253 / 差遣军职 112 / 封爵 12 / 土官 10`）+ 理由字段；完成率**剔出「不适用」做分母**；分类放**最终化阶段**做。**通用**：**字段存在 ≠ 字段有值 ≠ 字段的值可解释**。
29. **坑 沿革/关系这类「归属」须建显式关联字段，不得依赖文本位置**（与「关系条≠编制条」**同型复发**）：EVO 记录无 owner 字段，273 条沿革仅 101 条可按 `item_id` 间接关联；根因是假设「沿革所属机构 = 该条目所属机构」，而本书有**多机构共处一条总述条**的形态（`01-016` 含 5 条沿革属六部共有，六部 ORG 在另外 6 条编制条下）。**对策**：`owner_orgs[]` 可多值 + 四级归属判定；三条纪律——**个体名优先于集体名**（否则单条沿革被吞进全体）／**集体名须显式触发形态**（原文 `吏、户、礼、兵、刑、工六部` 是并列单字，成员全名一次不出现，子串匹配永远失败）／**去重按 `name` 不按 `id`**（同名机构全库 74 组多 ID）。
30. **正道操作：派生机构（内阁）须以「语义派生关系」定归属，不以「文本位置」定归属**：内阁无独立条目，编制写在翰林院条目块内，按「一机构一条编制条」假设抽取时成了孤岛（`total_posts=0` 却挂 `core_officials`）。原文三处互证内阁属翰林院（条目位置／「永乐初，**选翰林官入直内阁**」／所用皆翰林官）。**审计指纹**：ORG 节点 `total_posts=0 且 children=[]` 却挂 `core_officials` = 有官无编制的孤岛，宜做成交付前自动体检项。可复用于任何含「派生物/合署办公/兼管机构」的官制书。
31. **坑（多行结构批量编辑）**：用行级编辑工具删改多行字典时，必须以**完整记录**为单位（含首行），否则吞掉相邻记录开头行致 `SyntaxError`；批量删除优先用脚本配对匹配，改完立刻做语法预检。
32. **坑（根本）：验收指标全绿 ≠ 能回答用户的问题**（本条为 §1 元教训 1 的操作版）：**Phase ② 即产出「目标查询问句清单」并逐问标注承载层**，标注不出的即设计缺口。这是本实例最有价值的教训——五卷全绿之后才发现 3 类核心查询无解。
33. **正道操作：交付前用问句清单反向实查**：工程指标（ERR/GAP/空条目）全绿 ≠ 能回答用户问题；本实例 Q1/Q2/Q3 正是靠反向实查才暴露。
34. **坑 同型坑第二次出现应升级为通用纪律**：见 §1 元教训 3。**判据：同一根因出现 2 次 → 从「坑」升级为「纪律」。**
