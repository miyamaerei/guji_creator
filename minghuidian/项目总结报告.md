## 0. 项目概述

《明会典》数字化工程，按用户锁定口径推进：

- **AI 逐条判定 + 代码只验缺漏**（判定与验证严格分工）
- **条粒度**（按条目切分；按卷/按句切分方案被用户否决）
- **original 指纹注入 + 引用关联**（AI 源数据不手抄原文）
- **每卷独立 JSON + 全局归一**（先分卷产出，再归一并验证）
- **枚举顶层封闭 + 动态回填**（新增枚举值必须 version+1 并回溯存量）
- **词典全文本内生**（用户明确否决外部词典抓取）

最终形成**底座 + 30 层知识资产**，外加 ID 对齐审计、三棵父子树、查询接口与三张可视化，全部由可重跑脚本生成。

## 2. P4「打通与交付」详解（本轮完成）

### 2.1 P4-A 重建父子关系 —— 让树真正长出来

**关键洞察（踩坑记录）**：ORG 树初看"只有 36/329 个节点有子"，像失败；实则只有 36 个父节点（户部一节点挂 48 子）。**指标误导，非缺陷。**

OFFICE 树 155 条悬空 parent 分三类，处理策略：

| 类型 | 例子 | 处理 | 标记 |
|---|---|---|---|
| (a) 虚根 | 皇帝/朝廷/内府/宗室 | 不接真节点 | `parent_kind="virtual"` |
| (b) 衙门名 | 吏部/都察院/五军都督府 | 写 `parent_org`，桥接到 `org.child_offices` | `parent_kind="org"` |
| (c) 同衙简称 | 都御史/少卿/寺丞 | 四级回退消解 | `parent_kind="office"` |

**(c) 四级回退**（P4-A 核心算法）：
0. `EXACT_PARENT` 精确覆盖表最优先（逐条钉死跨衙/斜杠/散官连缀，如 `"都督同知":"左都督"`、`"卫镇抚":"卫指挥佥事"`、`"总兵官":"兵部尚书"`）
a. `ALIAS_OVERRIDE`（都御史→[左都御史,右都御史]、寺卿/少卿/寺丞/照磨→None）
b. **本衙门前缀消歧**（关键洞察：会典里的"上级"多是**同衙内班序上级**，简称只在本衙门内有意义。如 `浙江道监察御史.parent=都御史` → 都察院左都御史；`太常寺典簿.parent=寺丞` → 太常寺寺丞）
c. 全库唯一后缀匹配 → 全库含匹配

**环路检测**：alias 消歧会造环（寺丞→少卿→寺卿→寺丞），用三色 DFS（WHITE/GRAY/BLACK），发现环把环内**最长名**的 parent 断为 None，标 `cycle_broken`。

**修复过程**：alias 未解析 81 → 22（加本衙前缀消歧）→ 2（加 EXACT_PARENT；'府教授'实为'府儒学教授'）→ **0**。
断环 0、孤立官 0、悬挂 0。

**结果**：

| 树 | 节点 | 根 | 可达 | 边 |
|---|---|---|---|---|
| ORG | 329 衙门 | 62 | 329（100%） | child_orgs 结构完整 |
| OFFICE | 566 官职 | 212 | 512（90%） | office→office 边 342，挂衙门 8 官（礼部 6 / 都察院 1 / 都督府 1） |
| GEO | 3,883 节点 | 45 | 3,883 | `children` 与 `parent_id` 完全一致（0 处不符） |

最宽节点：户部 49 节点、内府二十四衙门 32、都察院 29。最深：吏部尚书 depth=7 / 47 节点。

产出：`org_tree.json`/`.md`、`office_tree.json`/`.md`、`_trees.json`。

### 2.2 P4-B 补 join 孤立条 —— 1,306 → 0

**设计动机**：P2-E 旧 join 只按"各层已有记录"挂载，孤立条（职掌长文 775 / 名册行 399 / 事目 127 / 事例 5）从未被任何抽取器覆盖。P4-B 改为**内容法多桶命中 + 实体提及索引**。

新增：
- **`mentions` 桶**（轻量实体提及索引，不参与 layer_count）：对每条 item 的 norm+original 正文做 wordlist 最长匹配，产 `{kind: office|office_sup|org|geo, name}`。
- **官名词表扩充**（P4-B 核心）：`office_profiles` 只收 566 个"有档案"的官（主要京官），**缺宣慰司/宣抚司/盐运司/衍圣公/真人 等土司·盐运·杂职官（各 0 条）**，导致名录行全成孤立条。从 `rank_sequence` 段落用 `harvest_offices(seg)` 抽官名建 `SUPP_OFFICE` 补充词表（按衙门/机构前缀 `(?<=[监寺司院府卫局库所仓州学])` 切分 + `OFF_TAIL` 尾缀过滤），**只用于 join 挂载，不改写 office_profiles（保持档案层纯净）**。
- 去包含逻辑：命中集里若 A 是 B 的子串，只留最长。
- 去重：每桶按 `tuple(sorted(items))` 去重（排除 note 字段）。

**踩坑**：`RANK_SEQ` 在词表采集块被提前引用 → `NameError`；修法是把 `RANK_SEQ = L["rank_sequence"]` 提到使用前。

**结果**：`offices` 桶 86 → **1,799**（+1,713）；孤立条 1,306 → 0；多层贯通（≥2 层）9,106 条 = **68%**。

### 2.3 P4-C 品级序列层（P0–P3 完全缺失的结构层）

**关键发现：卷 12（稽勲清吏司）= 文职品级/资格名录**，是 1,306 孤立条里 volume 12 独占 106 条的主因。卷 8（验封清吏司）= 封赠/勋级。含品级序列的卷：8、12、29、78、106、107。

**行文规律**：品级标记「正一品」「从二品」…「未入流」与官职名**混排**，两种形态：同一 item 内（`从一品少保　少傅`）或品级独占一个 item（`012-011 名录行 从二品`），故 **cur_level 必须跨 item 延续**（初版每 item 重置 → 只解析出 34 段，修好后 **287 段**）。

- 卷 12 首段（太师/太傅/太保…）**无显式「正一品」标记**，故 `cur_level` 初值直接设为 `"正一品"`。
- 正则：`LV_RE = re.compile("(" + "|".join(LEVELS) + ")")`；`NOTE_RE = re.compile(r"【[^】]*】")` 去沿革小注；全角空格「　」作分隔符。
- 排除：`SKIP_ITEMS={"012-004"}`（旧制文武勲沿革说明）；`node_kind=="事例"` 的 012-001~003 跳过。
- `JUNK` 集合排除非官名片段（已上增/后添设/后革/后为寺/旧正八品/后陞正七品/回回监正后革… 共 23 项）。
- 纯品级标记行单独记账为 markers，产出时并入该品级的 item_ids。

**实测**：段落 287、品级 19 级、覆盖 item **191/195**（未覆盖 4 条正是 012-001~003 事例 + 012-004 沿革说明，属正当排除）。
各级段数：正一品 6/从一品 5/正二品 6/从二品 1/正三品 8/从三品 5/正四品 11/从四品 5/正五品 17/从五品 11/正六品 23/从六品 12/正七品 21/从七品 14/正八品 20/从八品 16/正九品 20/从九品 31/未入流 54。

产出：`_layers/rank_sequence.json` + join `rank_seq` 桶 191 条。

## 3. 反思结论

### 反思一（上下文压缩后的 schema 重读）
每轮被压缩后要重读 schema 才能续写，是重复读取的最大来源。**改进**：把 schema 样例固化成 `_layers/*.json` 的头部注释 + 报告中的字段清单，压缩后从报告即可恢复口径，无需回到原始探查。

### 反思二（ID 对齐 / 命名空间）
`item_id`（`NN-NNN`）作为唯一跨层主键经受住了全流程验证：30 层、13,364 条、23 桶 join，零撞号。**教训**：主键必须在阶段 0 就定死且全层强制，后期改主键的代价是指数级的。

### 反思三（指标误读）
P4-A 的"36/329 有子"是最典型的一次假警报——把"父节点数量"误读成"覆盖度"。**教训**：报指标前先问"这个分母是什么含义"，结构性指标要配合分布直方图看，不能只看单一比率。

## 4. 根因分析：为什么"重复很多次无用读取"

诚实复盘，重复读取有 5 类根因，其中 3 类工程失误、2 类环境与方向成本：

1. **上下文压缩后的 schema 重读（半可控）**：压缩后 schema 丢失 → 重读探针。改进：schema 样例固化进 summary/报告。
2. **探查-执行边界没守住（失误）**：边探查边改脚本，导致同一段数据反复读。改进：开工前一次探查，定死 schema 再写数据。
3. **产物覆盖回归导致的重复验证（失误）**：脚本重跑覆盖已修复字段。改进：修复并入打包器、脚本转 `_p4x_` 前缀可重跑。
4. **环境噪声导致的重复跑（半可控）**：PowerShell + GBK 控制台导致中文乱码/解析错误（`python -c "..."` 内嵌双引号报"重定向不支持"）→ 反复重试。改进：一律写临时 `.py` 脚本文件再执行，且 `python -X utf8` + `sys.stdout = io.TextIOWrapper(...)`。
5. **用户多轮纠偏（方向成本，不是无用读取）**：如 P2.5 驿站源卷判定从卷 149/卷 37 纠正为卷 119–121/39–40。

## 5. 方法论沉淀（下次遇到任务的处理原则）

1. **一次探查**：开工前读完全部输入 + schema 样例 + 统计；连续两次读取不再改变计划即停止探查。
2. **先锁 schema 再写数据**：字段口径、枚举、ID 规则一次性定死；打包器注入指纹/关联/校验。
3. **AI 判定与代码验证严格分工**：判定逐条人工（AI）；代码只验缺漏。
4. **所有生成器正式化**：可重跑 + 幂等；修复并入生成器。
5. **验证一次到位**：校验脚本写文件输出，重跑前先确认不覆盖已修复字段。
6. **枚举单点治理**：新增枚举值 version+1 并回溯存量。
7. **方向假设先确认**：粒度/判定方式/交付形态开工前问清。
8. **交付按层聚合**：每层一组（归一汇总 + 验证清单 + 卷示例 + 跨层索引）。
9. **每轮任务建 task 清单**：阶段可见、完成可核。
10. **如实报告缺口**：哪里缺、缺什么、补什么方案，不静默降级。
11. **结构性指标要看分布**：比率异常时先看分母含义与直方图（本轮新增，源自 P4-A 假警报）。
12. **Windows + GBK 环境铁律**：`python -X utf8` + `TextIOWrapper` 重定向 + 写临时脚本文件，三条缺一就乱码。
