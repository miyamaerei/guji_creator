# 《明会典》使用报告

> 生成日期：2026-10-14 ｜ 适用读者：后续接手者 / 需要查询这套知识资产的人
> 一句话：180 卷明清刻本残卷（约 85 万字）→ 一套可查询、可溯源、可重跑的 **30 层**知识库。

---

## 1. 项目定位

本项目为明代官修典章巨著——《大明会典》（正德本，180 卷，854,118 字，11,135 底座条）——的通读与结构化知识工程。从刻本残卷出发，逐层产出机器可读、可交叉引用的结构化知识：

```
刻本残卷 → 180 卷抽取（13,364 条）→ 指纹库 → 实体标注 → 规则层 → 结构化层
        → 数字文册/器物层 → 跨层索引 → 父子树 → 查询接口 → 可视化
```

所有层遵循同一口径：**AI 逐条判定、代码只验缺漏、条粒度、original 指纹注入、每卷独立 JSON + 全局归一、枚举封闭治理、全文本内生词典**。

## 4. 怎么使用

### 4.1 快速查询（不跑代码）

- **一行看全某条**：打开 `_kg_join_flat.csv`，按 `item_id` 过滤 → 23 个桶的 ID 平铺一列。
- **查实体**：`_layers/ents.json`（normalized/type/count/source）；人名 `nams.json`，地理 `geo.json`。
- **查官职/衙门**：`office_profiles.json` / `org_profiles.json`，字段含品级、编制、职掌、沿革、上下级、出处。
- **查制度**：`rules.json`（含 `era`/`condition`/`punishment`/`object`/`subject_ent_ids`）+ `tim.json`。
- **查可视化**：双击 `_deliver/vis_*.html`，纯单文件、无 CDN、无网络。

### 4.2 查询接口（推荐）

```python
from minghuidian_kb import MingHuidianKB
kb = MingHuidianKB()

kb.office("吏部尚书")   # 官职档案：品级/职掌/沿革/下属/出处
kb.org("户部")          # 衙门档案：品级/编制/沿革/属官/下辖
kb.geo("苏州府")        # 地理档案：层级/隶属/卫所/驿站/仓场/辖县
kb.rule("漕运")         # 制度查询：历代事例 + 年代链
kb.timeline("漕运")     # 制度时间线
kb.rank("正三品")       # 品级：章服/房舍/伞盖/鞍辔
kb.njc("户部")          # 两京对照
kb.xref("户部")         # 互见
kb.num("苏州府")        # 数字文册
kb.obj("衮冕")          # 器物
kb.profile("苏州府")    # 全景档案（一网打尽）
kb.ask("漕运怎么运")    # 自然语言式分发
kb.search("一条鞭")     # 全文检索
kb.children("户部")     # 父子树展开
kb.path("苏州府")       # 从根到叶的路径
kb.stats()              # 库概况
kb.check()              # 自检
```

命令行：

```powershell
python minghuidian_kb.py office 吏部尚书
python minghuidian_kb.py profile 苏州府
python minghuidian_kb.py ask "漕运怎么运到北京"
python minghuidian_kb.py tree 户部 --depth 3
python minghuidian_kb.py stats
python minghuidian_kb.py check
```

### 4.3 全文回查（溯源）

任何一条记录都带 `item_id`（形如 `077-001`）→ 在 `_item_registry.json` 取 `original` = 刻本原文；或在 `_extract/077_*.txt` 按条号定位。跨层引用字段（`source` / `*_source` / `rules` / `ent_ids`）直接指向对应层 ID。

### 4.4 可重跑管线（改了数据后全量重建）

```powershell
cd E:\git\ToolBox\guji\minghuidian
python -X utf8 _p4a_build_trees.py       # 三棵树（ORG/OFFICE/GEO）
python -X utf8 _p4b_build_join.py        # 跨层索引 + mentions + rank_seq 桶
python -X utf8 _p4c_build_rankseq.py     # 品级序列层（卷 12）
python -X utf8 _p4f_render_vis.py        # 三张可视化 HTML

```

每层跑完核对 `_p4_orphans.json` 孤立条数应为 0、`kb.check()` 全绿。

### 4.5 扩展指南

- **加官职/衙门**：编辑 `_layers/office_profiles.json` / `org_profiles.json`（按现有 schema；`*_source` 必须指向真实 item_id）→ 重跑 `_p4a_build_trees.py` 生成树。
- **加实体词条**：`vocab.json` / 各层词表 → 重跑 `_p4b_build_join.py`。
- **加制度主题**：`tim.json` 增主题（含 `volumes`）→ 重跑 join。
- **解读词形**：`minghuidian_kb.py` 的 alias/精确覆盖表手工加映射。
- **新增层**：`_layers/新层.json` + 在 `_p4b_build_join.py` 的 `BUCKETS` 注册 → 重跑全程。

## 5. 关键设计（为什么要这样做）

1. **original 不手抄**：AI 源数据只写条号/解读，脚本从指纹库注入原文 → 杜绝手抄漂移。
2. **条粒度锚点**：`item_id`（NN-NNN）是所有层的共同主键；引用字段让层间可跳转。
3. **枚举单点治理**：类型/模态/机制收进枚举文件，新增必须 version+1 回填存量。
4. **修复并入打包器**：P0 修复写进生成器，重跑不丢。
5. **内容法挂载（P4-B 关键改进）**：旧 join 只按"各层已有记录"挂载，导致职掌长文/名册行/事目从未被任何抽取器覆盖。改为**正文最长匹配 + 实体提及索引**（`mentions` 桶），孤立条从 1,306 → **0**。
6. **树要真长出来**：ORG 树此前只有 36 个"有子"节点，看着像失败，实为只有 36 个父节点（户部一节点挂 48 子）。P4-A 的难点不在挂载而在**消解同衙简称**（"都御史"→都察院左都御史），用了本衙前缀消歧 + 精确覆盖表 + 三色 DFS 断环。
7. **两京镜像必须并层**：卷 108 有南京镜像段，与北京重复；不并会虚增节点。
