# 《新官轨范》项目总结报告

> 生成日期：2026-10-09 ｜ 项目：明代官箴书《新官轨范》数字化知识工程
> 一句话：从一份 txt 抽离文本，到一套六层可溯源、可重跑、可交叉引用的古籍知识资产。

---

## 0. 项目概述

《新官轨范》（明代官箴书，体立为政之规范）数字化工程，按用户锁定口径推进：

- **AI 逐条判定 + 代码只验缺漏**（判定与验证严格分工）
- **条粒度**（每卷按条目切分，段粒度方案被用户否决）
- **original 指纹注入 + derived_rule 关联**（AI 源数据不手抄原文）
- **每卷独立 JSON + 全局归一**（每层先分卷产出，再归一并验证）
- **枚举顶层封闭 + 动态回填**（新增枚举值必须版本+1 并回溯存量）
- **词典全文本内生**（用户明确否决外部词典抓取）

最终形成**底座 + 六层知识资产**：实体层 → 规则层 → 流程层 → 结构化层 → 事件层 → 跨层索引，外加 ID 对齐审计（P0 止血 + P1 合并）与核心主体补标。

## 1. 全流程时间线（9 个阶段）

### 阶段 0：底座（EPUB + 章节 + 指纹库）
用户交付《新官轨范》txt，要求：①拆成 epub ②填好章节目录 ③文字分好块，先目录后章节最后汇总，一批文件交付。

- 产出 `新官轨范.epub`、`新官轨范_目录.md`、`新官轨范_章节\`（**12 个 XHTML**：00 版本说明 / 01 卷上·体立为政事情 / 02 卷首注语 / 03~11 卷下 9 章）
- 条目原文抽为 `_extract\NN_卷名.txt`（格式 `条N|正文`）
- `_item_registry.json`：**275 条指纹库**（扁平 dict，key=`NN-NNN`，value 含 original/norm）——后续所有层的 original 注入源

### 阶段 1：实体层（kg-annot v1）
用户要求循环读每卷，①定义实体类型（人物/职官/机构/地点/文书/制度/行为/器物/刑罚/时间/数量，从文本中来）②构建种子词典 ③文本预处理（标点/分词/异体归一/缺字）④校验置信度 ⑤输出每卷独立 JSON（id/text/type/start/end/normalized/confidence/source）并全局归一。

**用户关键纠偏**：词典不要抓本地的，直接从文档里创建（否决外部词典）。

- 11 类封闭枚举 + 兜底「类型待定」（沿用 ming-officials-kg 枚举治理规则）
- 产出 `新官轨范_标注\`（11 卷）、`新官轨范_实体归一_汇总.json`、`新官轨范_实体标注_总报告.md`、`新官轨范_预处理_分词.txt`
- 初始规模：**1975 条标注 / 586 个归一实体**

### 阶段 2：规则层（kg-rule-ai v1）
用户要求找规范句（触发词：不可/不许/务要/须/止许/毋/勿/痛加责治/责罚/限一日/打三十），抽规则槽位（条件/主体/动作/对象/模态/目的/处罚/出处），表示成 IF-THEN，分规则类型（禁止/义务/允许/程序/时限/处罚/优先级）。

**两次纠偏（方向校正成本）**：
1. 代码触发词引擎产出 204 条 → 用户否决："不要用代码判定规则，要用 AI 一句一句分析，代码只是验证缺漏" → 废弃，改 AI 逐条
2. 段粒度（620 段）→ 用户改口"既然已经做好了条，那么就用条的" → 锁条粒度

- 产出 `新官轨范_规则_ai\`：**273 条（XGF-R-001..273）**，02 卷注语 0 规则带 note
- 组合规则 172 条；modal 分布：prohibit 136 / procedure 130 / obligation 127 / penalty 39 / deadline 13 / allow 23
- 修正过 3 处 original 手抄差异（漏字/异体），一律以指纹库为准

### 阶段 3：知识体系设计 + 状态机数据判定
用户要求：根据标注、规则搭建知识体系（本体/关系/事件/流程），建模没数据要判定哪里不足。随后问：**状态机（卯时→辰时→…直日时刻表）数据支持吗？**

- 结论（写进 `新官轨范_知识体系设计.md`）：**"点不是线"**——现有标注与规则是散点，直日时刻表是"状态机素材"而非"显式时序"，跨步顺序靠共现推断、缺少显式顺序/条件/迁移边，不足以直接推理 → 需新开流程/事件抽取轮
- 用户命反思整套流程 10 问 → 给出改进意见
- 用户命"新开 AI 流程/事件抽取轮"（kg-proc-ai-v1）

### 阶段 4：流程/事件层（kg-proc-ai-v1）
- 产出 `新官轨范_流程_ai\`：**274 流程 / 744 步（XGF-P-001..274）**

## 2. 两次反思的结论

### 反思一（阶段 3 后：重复调用 / 可合并 / 执行时间过长）
核心结论：
- **重复调用**：多轮"读 XHTML 条目 → 判定 → 写源数据 → 打包 → 验证"在同一文本上重复了 5 遍（实体/规则/流程/结构/事件），每条链路各自加载章节、指纹库、规则映射——加载与源数据骨架可合并
- **可合并**：指纹库加载/规则映射/卷解析/注入逻辑四层重复；枚举定义散落各打包器
- **执行时间过长**：AI 逐条判定是全流程瓶颈（不可省，但可通过条粒度并行与一次读取全文减少重读）；验证环节因 stdout 截断重复跑
- **改进**：共享基座、枚举集中、源数据一次读取、验证脚本文件化

### 反思二（阶段 7 后：ID 对齐 / 重复 / 可合并 / 执行时间）
核心结论：
- **ID 对齐审计**：条锚点（item_id）与 derived_rule 映射四层对齐良好；5 处断裂见阶段 7
- **命名空间**：XGF-E 必须唯一归属事件层，流程层只引用
- **改进落地**：P0（主键/引用/item_id）+ P1（枚举集中/打包基座/跨层索引）全量执行，四层重跑 0 issue

## 3. 根因分析：为什么"重复很多次无用读取"

诚实复盘，重复读取有四类根因，其中两类是我的工程失误、两类是环境与方向成本：

1. **上下文压缩后的 schema 重读（半可控）**
   会话极长，窗口压缩后每轮靠 summary + artifact_reload 恢复，但产物 schema（字段名/文件结构）仍需重新读文件确认。改进：把"关键 schema 样例"固化进 summary/报告，减少重读。

2. **探查-执行边界没守住（我的失误）**
   有时探查蔓延成多次小步读取（读注释→读样例→读统计→再读），没有在开工前一次性读完输入 + schema 样例 + 频次统计。改进：**开工前一次探查，定死交付 schema 再写数据**。

3. **产物覆盖回归导致的重复验证（我的失误）**
   P1 重跑打包器曾覆盖 P0 修复（结构层 item_id 丢失）——同一件事验证两遍。主键脚本用 `_p0_*.py` 一次性脚本，清理后重建又要重读。改进：**修复并入打包器、脚本转正式 `build_` 前缀可重跑**（P0 教训已根治，重跑不再丢）。

4. **环境噪声导致的重复跑（半可控）**
   PowerShell 5.1：stdout 30000 字符截断、jieba 日志被当 NativeCommandError、前台 15s 自动转后台——命令结果读不全要重跑。改进：**验证写 .py 脚本并重定向到文件再读**，不依赖 stdout。

5. **用户多轮纠偏（方向成本，不是无用读取）**
   规则层两纠（代码版 204 条 → AI 版）、段粒度→条粒度、事件轮试点→继续。这些是需求收敛成本，但可减少：**方向性假设（粒度/判定方式/交付形态）开工前先跟用户确认**。

## 4. 下次遇到任务的处理原则（方法论沉淀）

1. **一次探查**：开工前读完全部输入 + schema 样例 + 统计；连续两次读取不再改变计划即停止探查。
2. **先锁 schema 再写数据**：交付 JSON 的字段口径、枚举、ID 规则一次性定死，源数据按 schema 编写；打包器负责注入指纹/关联/校验。
3. **AI 判定与代码验证严格分工**：判定逐条人工（AI）完成；代码只验缺漏（覆盖/格式/引用/枚举）。
4. **所有生成器正式化**：`build_` 前缀 + 可重跑 + 幂等；修复并入生成器，不落一次性散文件。
5. **验证一次到位**：校验脚本写文件输出，重跑前先确认不会覆盖已修复字段。
6. **枚举单点治理**：新增枚举值必须版本+1 并回溯存量（registerVersion 模式）。
7. **方向假设先确认**：粒度（卷/条/段）、判定方式（AI/规则）、交付形态（JSON/CSV/文档）在开工前问清。
8. **交付按层聚合**：不是每层每卷逐件 present，而是按层一组（归一汇总 + 验证清单 + 卷示例 + 跨层索引）。
9. **每轮任务建 task 清单**：阶段可见、完成可核。
10. **如实报告缺口**：数据不足的地方写"哪里缺、缺什么、补什么方案"，不静默降级。
