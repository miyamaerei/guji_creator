## 〇、一句话结论（先读）

**现在能建的是「骨架」：本体 schema、E↔规则回填关系、01 卷内 8 条流程草模、事件类型枚举。**
**现在缺的是「血肉」：E–E 关系三元组、事件实例、02–11 卷规则、义项消歧、42 条低置信复核、缺字补录、外部词典回填。**
不是"建模没有数据"，而是**数据是分层齐备的：实体层有、规则层半有（34%）、关系层无、事件层无、流程层可推断**。下文逐层判定。

### 2.1 类（9 个核心类，对齐 ming-officials-kg 的 7 类 + 本项目域扩展）

| `规则 Rule` | AI 逐条抽取的规范句（禁止/义务/允许/程序/时限/处罚/优先级） | 规则层 | ⚠️ 94/274 |

| `流程 Process` | 到任、公文、放告审理、催办勾摄、狱政、赋役、支应、迎送（8 条草模） | 程序型规则链 | ⚠️ 01 卷内可草模 |
| `制裁 Punishment` | 打三十、责罚、痛加责治、加罚、革去（刑罚 30 + 规则槽位） | 实体层+规则层 | ✅ 实例充足 |
| `文献源 Source` | `{XHTML}#条N`（书证锚点，规则 original + 实体 source） | 双侧 | ✅ 全部挂源 |
| `词典条目 Lexicon` | 文本内生 v1，527 词条 | 词典 | ⚠️ v2 外部回填 |

### 2.2 关键属性（第一版必带，防返工）

- `senseId`：同名异义义项键（**监**＝监狱／监督；**簿**＝泛称文书；**里**＝行政区／距离——总报告 §9 已点名）
- `registerVersion`：枚举或词典变更 +1，回溯重标（entity-type-enum-v1 / rule-ai-v1 已挂）
- `confidence`：实体 0–1（词典 0.8–0.92／正则 0.7–0.8／泛称 0.7）；规则 AI 主观 0.72–0.96——**两套口径需统一校准表**
- `source`：`文件#条N`（实体）／`文件#条N`（规则 original 逐字锚定）
- 规则专属槽位：condition / subject / action / object / modal / purpose / deadline / punishment / prohibited_effect（版本化，rule_id 全局唯一 `XGF-R-NNN`）

### 2.3 枚举治理（沿用既有约定）

- 实体类型 11 类封闭 + 兜底「类型待定」；新增子类型必须 registerVersion+1 并回溯存量。
- 规则类型 7 类（禁止/义务/允许/程序/时限/处罚/优先级）可组合（如「禁止+允许」「时限+处罚」），组合不是矛盾而是互补（示例：止许差里长 ⇔ 不可差皂隶）。

## 三、关系设计（kg-rel-v1，按确定性排序）

### 3.1 关系清单与优先级

| 优先级 | 关系 | 定义 | 示例 | 可自动回填？ |
|---|---|---|---|---|
| 高 | `subject_of_rule` | 实体充当规则主体 | 皂隶 → subject_of → XGF-R-031 | ✅ 规则槽位直接回填 |
| 高 | `prohibits / obliges / allows` | 规则模态作用到行为 | R-031 →prohibits→ 差皂隶下乡；R-013 →obliges→ 经心听分付 | ✅ 规则槽位直接回填 |
| 高 | `punished_by` | 规则→制裁 | R-030 →punished_by→ 打三十/加罚公用之物 | ✅ 规则槽位直接回填 |
| 高 | `deadline_of` | 规则→时限参数 | R-030 →deadline_of→ 三十里限一日 | ✅ 规则槽位直接回填 |
| 高 | `composes_with` | 组合规则（禁止+允许等） | R-031 禁止↔允许互补 | ✅ 规则层已有 45 组合 |
| 高 | `exempts` | 例外条款 | R-040 重情不在限次（例外） | ✅ 规则槽位（condition 内） |
| 高 | `belongs_to`（编制于） | 人→机构 | 吏典→六房；禁子→监；库吏→库 | ⚠️ 需从文本抽任职句，半自动 |
| 高 | `keeps / handles`（经手守掌） | 文书→人 | 囚簿→刑房吏守掌；勘合簿→承发吏 | ✅ 规则 obligation_action 回填 |
| 中 | `records`（记录对象） | 文书→被记录对象 | 受理词状簿→词状；囚簿→囚犯 | ✅ 规则槽位回填 |
| 中 | `performs`（施动） | 主体→行为 | 知县→亲看门户；书手→开写手本 | ⚠️ 需事件抽取轮 |
| 中 | `located_in`（处所） | 地点→机构 | 后堂/公廨→县衙；监→狱房 | ⚠️ 实体共现启发，需人工 |
| 低 | `causes`（因果/负面后果） | 行为→prohibited_effect | 差皂隶下乡→致生不虞 | ✅ 规则槽位已有，直接入库 |
| 低 | `conflicts_with`（规则冲突） | 规则间冲突检测 | （示例：出票泛滥 vs 言语分付） | ⚠️ 需冲突检测规则，后置 |

### 3.2 关系数据现状判定

- **E–Rule 关系（高优先级 7 项）**：**数据已隐含在规则槽位里，可程序化回填**（主体/行为/对象/模态/制裁/时限/例外 → 三元组），这是当前唯一"零新标注成本"可落地的关系层。
- **E–E 关系（任职/隶属/经手/处所）**：**当前完全没有关系标注**。实体标注只有点（NER），无边。需一轮关系标注（可从规则槽位半自动 + 句法模式：`X分付Y`、`X守掌Z`、`置立…簿令X守掌` 提取候选，人工复核）。
- 结论：**关系层是第二大缺口**（仅次于规则未完成）。

### 6.2 结论

- **不是"没有数据"**：实体层、规则层（01 卷）、文本层足够支撑**本体 schema、E–Rule 关系回填、01 卷 8 条流程草模、事件类型枚举**的设计与先行入库。
- **是"分层未齐"**：关系实例、事件实例、02–11 卷规则是三个硬缺口；义项消歧、低置信复核、缺字是三个质量缺口。它们按依赖排序，决定建模只能逐层推进。
- **建议实施顺序**：① 规则层 AI 分析已全部完成（273 条，每卷 JSON + 全局归一 XGF-R-001..273）→ ② E–Rule 关系回填（程序化，验缺漏）→ ③ 事件抽取轮（AI 逐条）→ ④ E–E 关系标注轮（半自动候选+人工）→ ⑤ 低置信复核 + 缺字补录 + 泛称消解 → ⑥ 外部词典 v2 回填 + senseId → ⑦ 落库 kg_ming（entity/rule/relation/event/process 五表）+ kg_wf 流程注册（P1–P8 先行，P9–P16 据新规则补全）。
