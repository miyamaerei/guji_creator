## 1. 一个关键澄清：库里只有「一个节点类型」

动手前先厘清层库的一个事实：**GEO（地理）、REG（典章）不是「层」**，它们只是枚举分类组；
真正承载数据的是 `ent`——地名在 ent（`type=place`）、典章散落在 rule/struct 里。

更进一步：层库里所有「人 / 书名 / 名物 / 地点 / 机构 / 概念」都归一进 **ent 这一个节点**，
只靠 `type` 区分。这意味着跨书对齐的「统一对象」只有 **ent**，关系层和引用层都是指向 ent 的边。

**这反而让「所有的层」好设计了**：

| 层扮演的角色 | 落到的表 | 说明 |
|---|---|---|
| 节点（可被跨书对齐的对象） | `nodes` | 当前仅 `ent`；未来新 node 层自动落入 |
| 边（关系 / 引用，指向 ent） | `edges` | REL/APPT/EVT/CIT/LIT/OBJ/CUS/NAM/MING/MEM/CHR |
| 注释（挂在条目上的知识，不跨书对齐） | `records`（JSON） | rule/proc/struct/trl/opn，靠 JSON 查询 |
| 卷级档案（不占 ID 命名空间） | `volumes` | V1 卷阅读模式 |
| 目录（不存数据） | `books`/`layer_catalog`/`layer_fields` | V2/V3 治理组件驱动管线，不入库 |

**铁律延续**：`records` 是「所有的层」的统一落点——新增任何层都不会改它的结构（payload 存 JSON）。
真正会随层变化的，是 `layer_catalog` / `layer_fields` 这两张**目录表**里的行，不是 DDL。

### 1.1 实库校正（2026-10-14）

上面这段「GEO/REG 不是层」的澄清，**只有后半句还成立**，实测要改三处：

1. **`geo` 已是一张真正的目录行**：`layer_catalog` 里 `(kzz, geo)`、`(ysz, geo)` 两行，
   `kind='node'`，共 666 条 `records`（地名/古迹，带 `category`、坐标、隶属链）。
   它**没有**进 `nodes` 表——`transform.build_nodes()` 只把 `layer_key='ent'` 抽成节点
   （见 `transform.py:56-91`），所以 `nodes` 里 100% 是 ent。`geo` 与 ent 的挂钩靠
   payload 里的 `name.location_ent_ids`，已物化进 `record_refs`（126 条）。
   → 结论仍是「跨书对齐的统一对象只有 ent」，但**理由从「GEO 不是层」变成了
   「transform 只认 ent」**；若要让地名自成节点命名空间，改的是 `build_nodes` 的
   层白名单，不是 DDL（这与 §4 的目录驱动设想仍有差距，见 §4.4）。
2. **`reg`（典章）确实不是独立对齐对象**：实测 6 书 463 行，`kind='annotation'`，落 `records`，与设计一致。
3. **`nodes.type` 比设计列举的多得多**：设计写 `person|place|book|object|institution|concept`，
   实测 **21 种**——person 9785 / place 4959 / official 2196 / institution 1684 / work 1538 /
   era 1183 / system 1102 / object 1012 / unknown 421 / behavior 359 / doc 325 / animal 187 /
   quantity 151 / time 76 / plant 66 / document 53 / org 42 / punishment 33 / food 14 / event 13 /
   posthumous 6。其中 `unknown`(421) 与 `doc`/`document`、`org`/`institution`、`work`/`book`
   这几组**同义异写**是枚举治理的活口（对应 §6 与偏差 A7）。
4. **「边层 11 个」不成立**：`edges` 表实际只有 `rel`(939) + `appt`(1156) = 2095 行；
   `event/evt/lit/nam/obj/cus/ming/mem/chr` **一行都没进 edges**（它们在目录里 kind 分别标着
   edge/annotation，本身只躺 `records`）。这些层里 `*_ent_ids` 那部分结构化引用，
   改由 F4 的 `record_refs`（5969 行）承载——**引用边与语义边分家**是实库与本文最大的一处形态差异。

## 2. 三层存储架构

```
┌──────────────────────────────────────────────────────────────┐
│ Tier 0  联邦目录（扩展点）                                      │
│   books · layer_catalog · layer_fields                         │
│   + book_meta（书目元数据：朝代/作者/体裁；⚠ 不在 schema.sql）  │
│   → 新书 / 新层只插这里，不改 schema                          │
└───────────────┬──────────────────────────────────────────────┘
                │ 声明「有哪些层、各层字段语义」
┌───────────────▼──────────────────────────────────────────────┐
│ Tier 1  忠实装载（无损真源）                                    │
│   items（指针，不抄正文）· records（所有层记录的 JSON）         │
│   → 复合主键 (book_id, layer_key, local_id) 隔离，撞号自然消解  │
└───────────────┬──────────────────────────────────────────────┘
                │ T 阶段按目录抽取（实测按代码字典，见 §4.4）
┌───────────────▼──────────────────────────────────────────────┐
│ Tier 2  派生图谱（可重建，不入 git）                            │
│   nodes（ent 等节点）· edges（解析后的关系边）                  │
│   canonical · members（去歧义合并结果）                         │
│   candidate_links · pending_refs（待决引用）                    │
│   record_refs（F4 物化引用边，payload 内 *_ent_ids 展开）       │
│   member_overrides · override_log（F4 人工裁决，重放不覆盖）    │
│   ent_slots（CBDB 富化槽位；⚠ 不在 schema.sql）                 │
│   enum_registry · enum_values · enum_drift（枚举校验）          │
│   volumes · load_runs · federation_meta · fts_nodes(已建/空)    │
└──────────────────────────────────────────────────────────────┘
```

设计原则（五条）与实测兑现度：

1. **不重写 ID**：全部表主键带 `book_id`，复合主键隔离，撞号（设计期实测 2847 个；
   13 书现状 **3199** 个）无需改源数据。✅ 已兑现，`federation.py collision` 为装载前置断言。
2. **原文只存指针**：`items.fingerprint_ref` 指向 `_item_registry`，正文绝不进总库。
   ⚠ 半兑现：`fingerprint_ref` 实测就等于 `item_id` 本身（`load.py:136`），
   `items.title` 存的是**前 50 字摘要**（`load.py:135`）——不是大段正文，但也不是纯指针。
3. **零依赖 SQLite**：纯标准库 `sqlite3`，单文件，守项目铁律。✅ 已兑现。
4. **目录驱动扩展**：schema 固定；新书/新层只插目录表，T 阶段自动识别 node/edge/enum。
   ⚠ **只兑现「新书」，未兑现「新层」**：见 §4.4——`layer_fields.role` 全库 1144 行
   都是 `attr`，边解析与枚举映射实际由 `transform.py:EDGE_SPEC` / `enum_import.py:LAYER_ENUM_FIELDS`
   两个 Python 字典驱动。
5. **一切可重跑**：Tier 1 先删后插幂等；Tier 2 全部可重建（丢了对账重跑即可，不入 git）。
   ✅ 已兑现，且**加了一条必要机制**：人工裁决存 `member_overrides`，`transform` 之后由
   `replay_overrides()` 重放，保证「重跑不覆盖专家结论」（§8）。

## 4. 扩展性机制：新书 / 新层零 DDL

这是用户「还要考虑以后新书的层」诉求的直接回答。

### 4.1 接入一本新书（第 7 本起）—— ✅ 已验证 13 本

```
1. INSERT INTO books(book_id, name, source_root, ...)          -- 新书级命名空间
2. 跑该书 loader：
     - 遍历各层 → 填 layer_catalog(book_id, layer_key, kind, id_prefix, ...)
     - 遍历各层字段 → 填 layer_fields(role=node_ref|enum|attr, ref_layer, enum_group)
     - 逐条 → records(book_id, layer_key, local_id, payload)
     - 条目 → items(指针)
3. 跑 T 阶段：据 layer_catalog.kind 自动抽 nodes/edges，无需任何新代码
```

**全程不碰 `CREATE TABLE`**。书级命名空间由契约线 C2 强制带前缀（`book_id:`），天然无撞号。

> 实测兑现：第 7–13 本（`lgs / xzl / ysz / fqh / ppy / shz / zgz`）全部零 DDL 接入，
> `books` 现有 13 行、`layer_catalog` 100 行、`records` 49885 行，`load_runs` 13 条全 `done`。
> 但**新书的适配器仍然要写**（`adapters/` 下一书一份），「零新代码」只对标准层形状成立；
> 非标准形状（如 `shz` 的 appt 只有 person+office 没有 institution）要在
> `transform.py:EDGE_SPEC_BOOK` 里加一条 per-book 覆盖——这是设计里没预留的硬编码点。

### 4.2 接入一个新层（比如未来的 C13「职官迁转轨迹层」）—— ⚠ 只能走一半

```
1. 在 layer_catalog 插一行：kind='edge', id_prefix='TRANSFER-'
2. 在 layer_fields 插若干行：
     ('book','transfer','person',  'node_ref','ent')   -- 指向人物节点
     ('book','transfer','from_office','node_ref','ent')-- 指向机构节点
     ('book','transfer','type',    'enum', 'TRANSFER_TYPE')
3. 该层记录照常进 records；T 阶段自动按 node_ref 字段抽出 edges
```

> 实测：第 1、3 步成立（`geo/org/doc/actor/fraud/ledger/tme/time` 八个新层就是这么进来的，
> 记录照常落 `records`）；**第 2 步的空头支票已确认**——插了 `layer_fields` 也**不会**
> 让 T 阶段自动抽边或自动做枚举校验。见 §4.4。

### 4.3 为什么 edges 不按层拆表

有人会想把 `rel_edges` / `appt_edges` 拆开。不这么做，原因：
- 边是高度同构的（subject→predicate→object），差异只在 `predicate` 取值与字段名；
- 拆表会让「跨层关系查询」（如「这个人出现在哪些关系里」）变成 UNION；
- 字段差异由 `layer_fields` + `payload`（JSON 留全量）兜底，查询时按需取。

如果将来某层确实需要专属索引（如时间范围查询），那是**可选的派生表**，且可重建、不破坏统一模型。

### 4.4 目录驱动的实际实现状态（与设计的偏差，务必知悉）

设计说「schema 描述数据，目录描述结构」。**实库里「目录描述结构」这层没生效**，
三处硬编码替代了它：

| 设计期望的目录 | 实库状态 | 真正在跑的驱动源 |
|---|---|---|
| `layer_fields.role='node_ref'` → 自动抽边 | 1144 行**全部** `role='attr'`，`ref_layer`/`enum_group` **100% NULL** | `transform.py:31 EDGE_SPEC`（只登记 `rel`/`appt`）+ `EDGE_SPEC_BOOK`（只登记 `shz`） |
| `layer_fields.role='enum'` → 自动漂移校验 | 同上，无一行 `role='enum'` | `enum_import.py:LAYER_ENUM_FIELDS`（25 层 × 19 组的 Python 字典） |
| `layer_catalog.layer_code` 记层库编号 | 100 行**全 NULL** | 无（层名 `layer_name` 也只等于 `layer_key`，中文层名未落库） |
| `layer_catalog.kind` 决定 node/edge | 值存在但 `transform` 不读它 | `build_nodes` 写死 `layer_key='ent'`；`build_edges` 写死 `EDGE_SPEC` 的键 |

**结论**：`layer_fields` 目前是一张**写了但没人读**的登记表；`id_prefix` 有 96/100 行有值（可用）。
要让 §4.2 的承诺成真，缺的不是 DDL 而是**改造 T 阶段去读目录**——这条已记入 §11 偏差台账 A2，
配套建议见 `schema-drift-note.md` §5 R4（`enum_fields` 注册表）。

## 5. 去歧义合并如何落到各表（T0–T3 → 表）

呼应《ELT设计》的算法，明确每张表的职责：

| 步骤 | 做什么 | 落到的表 |
|---|---|---|
| T0 层 key 归一 | events→evt、ents→ent（映射表）；未登记层报 WARN（反制 #27） | 读 `layer_catalog`（映射在 loader 里） |
| T1 名字→ID | REL/APPT 里的「名字」经 ent_keys 解析成本书 ENT id | 写 `edges.subject_uid/object_uid`；解析不到写 `pending_refs` + `edges.*_pending` |
| T2 候选生成 | 精确（normalized+type 一致）+ 别名（alias_index 交叉） | 写 `candidate_links`（method=exact/alias, conf） |
| T3 关系消歧 | 并查集 + 关系一致性迭代传播 + 约束剪枝 | 写 `canonical` + `members`（method/conf/status）；冲突的标 `conflict` |
| 人工确认 | 专家锁定高置信合并、解除误并 | `canonical.status='locked'`、`members.status='locked'` |

> ⚠ **T0 行按设计没有实现**：`events→evt` 的归一在实库里没发生——`event`(6 书) 与 `evt`(2 书)、
> `time`(1 书) 与 `tme`(2 书) 至今作为**四个独立层**并存于 `layer_catalog`（详见 §3.1、§11 A4）。
> 「未登记层报 WARN」这条实现了：`records` 里 27 个层 key 100% 有目录登记，零脱管。
> 另外「人工确认」一行的实现超出设计——不是就地改 `members.status`，
> 而是独立 `member_overrides` + 重放（见 §5.1 要点三）。

**「去歧义」的硬闸门 = `members.status`**：auto 是机器并、locked 是人工锁、conflict 是约束违背待核、
pending 是引用都没解析出来。物理上**任何层的源数据一行不动**，合并只产生链接。

**跨书对齐的查询**（呼应「用关系识别同实体」）：
```
cross_search("王守仁")
  → members 找到 canonical_id
  → 列出所有 member uid（各书 ent 记录）+ 各自出处/置信
  → 沿 edges 找该 canonical 下节点的关系网（需经两次对齐：人对齐 + 关系另一端对齐）
```

### 5.1 实测的 method / status 取值（与设计命名不同）

设计里 `candidate_links.method` 写 `exact|alias`、`members.method` 写 `exact|alias|relation`。
实库跑出来的取值是另一套，记此为准：

| 表.列 | 设计值 | 实测值（行数） |
|---|---|---|
| `members.method` | exact / alias / relation | `exact_normalized` 5164 · `surface_alias` 1282 · `normalized_stripped` 123 · `manual_lock` 203 |
| `members.status` | auto / conflict / pending / locked | `auto` 5640 · `conflict` 929 · `locked` 203 ·（`pending` 0） |
| `canonical.status` | open / locked | `open` 1439 · `locked` 141（共 1580） |
| `candidate_links.method` | exact / alias | 六路：`place_name_match` 2212 · `kinship_relation` 1842 · `place_hierarchy_match` 1413 · `office_name_match` 661 · `office_dynasty_match` 420 · `exact_name` 75 · `context_similarity` 15 · `place_admin_match` 52 |
| `pending_refs.reason` | — | 只有一种：`no_ent_match`（1149 行；按书层集中在 `appt` 725 / `rel` 424） |
| `record_refs.target_ambiguous` | — | 5969 行中 **2500** 为 1（跨卷裸 ID 未唯一解析），5346 行有 `target_uid` |

**要点一：T2 早已不是「精确名 + 别名」两路**。`candidate_links` 的主体来自
`four_step_matching.py / layered_matching.py / place_office_matching.py`，
它们读 `ent_slots`（CBDB 富化的 65843 条槽位：主职/籍贯/生卒/科举/亲属…）做
地名层级、职官朝代、亲属链三类佐证匹配。这正是设计 §5 说的「关系一致性迭代传播」，
只是实现落成了**独立脚本 + 一张 `ent_slots` 支撑表**，而 `ent_slots` 不在 `schema.sql` 里。

**要点二：置信度已按方法分层**（`candidate_links.confidence` 均值）：
`place_hierarchy_match` 0.95 > `exact_name` 0.85 > `context_similarity` 0.76 >
`office_*_match` 0.6 ≈ `place_name_match` 0.6 > `kinship_relation` 0.30。
kinship 一路靠**关系传播**才被救过 0.35 下限（其余 0.6 档根本不需要佐证）；
`conflict` 929 行留人工。**闸门实际有多松、与设计注释的出入，见 §11.4——那是本库最该先拍板的一件事。**

**要点三：F4 人工裁决闭环已落地**（设计 §5「人工确认」行只写了 status，没预料到要独立表）：
`member_overrides`(204：lock 203 / reject 1) + `override_log`(208，只增审计)，
`federation.py lock/unlock/conflicts` 驱动，`transform` 重跑后 `replay_overrides()` 重放，
故裁决**不被 T3 覆盖**——这是「一切可重跑」原则的必要补充。

**要点四：跨书对齐的实际规模**——1580 个 canonical 中 **1340 个跨 ≥2 书**（4780→6772 成员链接）。

## 10. 边界与未决

- **`opn.topic`** 若未来频繁跨书对齐，可把该字段在 `layer_fields` 标 `role='node_ref'`，自动升级为边——示例目录驱动的灵活性。
  ⚠ 但**当前标了也不生效**（§4.4：`role` 无消费者），实际做法是往 `EDGE_SPEC` 加一条。
- **机构（institution）** 目前靠 `ent(type=institution)` 承载（实测 1684 个）；
  `zgz` 另建了 `org` 层（1786 行，kind=annotation）**没有**成为独立命名空间——
  即「建 `kind='node'` 的层就自动进 nodes」这条**尚不成立**（`build_nodes` 只认 `ent`）。
- **`event`/`evt`、`time`/`tme` 同义异写并存**：T0「层 key 归一」在设计里是映射表，
  实库两对都各自登记、各自进 `layer_catalog`，跨层聚合查询必须自己 `IN ('evt','event')`。
  归一与否是**治理决策**（合并会丢失「志书层 vs 笔记层」的来源差异），本档不定论，只登记（§11 A4）。
- **neo4j** 仍只作导出目标（图遍历性能需求时），主库保持 SQLite。
- **总库是否入 git**：维持原建议——`tools/kb-federation/kb.sqlite` **不入库**
  （Tier 1/2 全可重建，撞号脚本 + schema + loader 入 git 即可）；
  `kb_dw.sqlite` 同理不入库。⚠ 但 `ent_slots`（CBDB 富化产物）**目前只能靠重跑
  `cbdb_enrichment.py` 重建**，而它依赖外部 `E:\git\cbdb_sqlite`，重建路径比 loader 脆——
  这是「一切可重跑」原则的一个真实例外，要么固化富化脚本链，要么破例备份该表。

### 11.4 消歧闸门的实测口径（与设计意图有一处出入）

`transform.disambiguate()` 的真实三段式（参数在 `name_rules.json`）：
锚阈值 `secure ≈ 0.83`（`exact_normalized` 0.98 × 0.85）→ 关系传播提升
（`relation_boost_per_edge=0.08`，上限 +0.20，提升后至少 `relation_propagated=0.55`）→
并入下限 `confidence_floor=0.35`。

实测 `candidate_links` 6690 对的落点：

| 置信区间 | 候选数 | 已并进同一 canonical |
|---|---|---|
| ≥0.83（锚） | 2114 | **2114（100%）** |
| 0.35–0.83 | 3384 | **3352（99.1%）** |
| <0.35 | 1192 | 749（应 0——见下） |

两点必须写进设计账：

1. **`transform.py:13` 的注释说「低于关系佐证的只进 `candidate_links` 不并入 canonical，留待人工」，
   代码实际是「`conf ≥ floor(0.35)` 就并」**——0.35~0.83 这一整段（3384 对，占合并候选的一半）
   **不需要任何关系佐证即被并入**。`place_name_match`(0.60) / `office_name_match`(0.60) /
   `office_dynasty_match`(0.60) / `place_admin_match`(0.80) 都落在这一档。
   文档、注释、代码三者口径不一致，**以代码为准**，并建议要么把 floor 提到 0.55
   （强制关系佐证），要么把注释与设计改称「0.35 即并」。**这是治理决策，等你拍板。**
2. **`<0.35` 一档本应全部不并，却有 749 对成了同 canonical 成员**——原因是这两行
   按「原始 `candidate_links.confidence`」分组，而 T3 提升后的置信只存在内存里、
   **未回写 `candidate_links`**。749 对即「被关系传播救活」的对。
   → 顺带暴露一个可观测性缺口：`candidate_links.confidence/method` 是 T2 的原值，
   不含传播结果，`members.confidence` 才是终值；查「为什么并了」必须回看 `members`。

**对齐质量画像**（供判断闸门松紧）：成员 6772 / canonical 1580；
规模分布 2 人 575 · 3–5 人 551 · 6–10 人 152 · **>10 人 85**； singleton canonical 23 个；
`conflict` 成员涉及 282 个 canonical（929 行，等人工）。

宋 36 / 明太祖 35 / 钟山 35 / 唐 31 / 赵孟頫 26 / 王安石 26 / 万历 23），
**但地名与朝代类的大组含「同名的不同所指」**（如 `闽` 在唐/明行政级别不同、
`南京` 在明初与明中期建制不同）——按本项目的跨书对齐意图，
`place`/`era` 是否需要再切一级，是下一个该决定的事（§10 未决）。
