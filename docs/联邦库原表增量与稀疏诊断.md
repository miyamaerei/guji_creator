## 1. 增量更新：原表该加哪些字段

### 1.1 先说结论：结构上已经「可增量」，缺的是「内容水印」

联邦库的**每一个**业务表都以 `book_id` 为前缀键（`records`/`nodes`/`edges`/`members`/`record_refs` 全带），
`build_dw.py` 也早已实现 `DELETE WHERE book_id=?` 的按书重建。
所以「按书增量重跑数仓」在结构上是免费的——**唯一缺的是判断「哪本书变了」的水印**。

而现状：
- `books.checksum` 列**存在但全 NULL**（8 行全空）→ 内容指纹形同虚设。
- `load_runs` 已记录每书 `finished_at` 与 `record_counts`，是现成的「装载时间戳」。

### 1.2 推荐的水印方案（由轻到重）

**方案 A（最小改动，零新字段）**：
- 不碰联邦库，只在数仓 `kb_dw.sqlite` 加一张 `dw_watermark(book_id, last_loaded_at)`。
- ETL 逻辑：取 `load_runs` 每书最新 `finished_at`，与 `dw_watermark` 比对，变化的书才 `DELETE+重抽`。
- 缺点：只能感知「装载时间变了」，感知不到「源书改了但还没重跑」。

**方案 B（推荐，加 1 个字段）**：
- 联邦库 `books` 表加 `source_rev TEXT`（源工程目录的 git commit / 快照 id），装载时写入。
- 数仓侧加 `dw_watermark(book_id, last_source_rev)`。
- ETL 逻辑：比较 `books.source_rev` 与上次摄入的 `last_source_rev`，不一致即该书的源数据变了，重建。
- 优点：源书改了哪怕还没重跑也能被 ETL 捕获，真正「增量正确」。

**方案 C（最稳，加 2 个字段）**：在 B 基础上，给 `records` 也补 `content_hash`
（或复用现有但填空的 `checksum`），支持比「整书」更细的行级增量——但 loader 是整书重抽的，
行级增量收益有限，**不优先**。

> 一句话：联邦库原表只需给 `books` 补一个 `source_rev`（或把现有 `checksum` 真正算出来）；
> 数仓侧加一张 `dw_watermark` 记住上次摄入的 rev。其余 `book_id` 键已就位，无需大改。

### 1.3 增量 ETL 伪流程（接上面的水印）

```
for book in books where source_rev != dw_watermark.last_source_rev:
    DELETE FROM 所有 DW 表 WHERE book_id = book          # 已有
    从 kb.sqlite 重抽该书所有行 → 维度/事实/桥表重插       # 已有
    UPDATE dw_watermark SET last_source_rev = book.source_rev
```

## 2. 原表结构不足（deficiencies）

### 2.1 🔴 schema.sql 与真实库严重漂移（最该修）
文档声明但库里**不存在**的：
- `nodes.normalized` / `nodes.text` —— 实际只有 `label`/`type`/`payload`。
- `canonicals`（复数）—— 实际表名是 `canonical`（单数）。
- `enum_groups` —— 实际是 `enum_registry`；`enum_fields` 表**根本不存在**。
- `name_rules` —— 不是表，是 loader 读的外部 `name_rules.json`。
- `books.title` / `books.author` / `books.dynasty` / `books.abbr` / `books.total_volumes`
  —— `books` 实际只有 `book_id/code/name/source_root/status/schema_version/loaded_at/checksum`。

> 后果：任何照着 `schema.sql` 写的工具都会字段报错（本次体检脚本就一连撞了 4 处）。
> 建议：以真实库为准**重写 schema.sql**，或反向补齐缺失表/列，二选一，杜绝双份真相。
>
> 反向漂移（真库有、`schema.sql` 无）10-16 复测：`book_meta` 已补进建表语句（列与真库逐一对齐）；
> 仍缺 `ent_slots`（官职槽位，assoc 线在用）；`fts_nodes*` 是代码动态建的 FTS 影子表，按注释「可选」处理。
> 现 `schema.sql` 建表 22 张，真库 29 张 = 这 22 张 + `ent_slots` + `fts_nodes` 的 6 张影子表，双向差集只剩 `ent_slots`。

### 2.2 🔴 枚举体系完全空置（项目核心铁律没落地）
`enum_registry`(0) / `enum_values`(0) / `enum_drift`(0)。
guji 项目铁律是「枚举封闭、单点 `_kg_enums.py`」，但联邦库从未把 `Skills/00-…/references/` 的
enum-library 导进来。
> 后果：数仓 `Dim_Enum_*` 全空、`f_drift` 全空、records 里的枚举值无法校验/归一。
> 建议：写一次性导入脚本把 enum-library 灌进 `enum_values`，并跑漂移检测填充 `enum_drift`。

### 2.3 🟠 books 元数据过薄
只有书名和工程目录，缺 `author`(作者) / `dynasty`(朝代) / `category`(笔记·实录·政书) / `full_title`。
> 后果：`Dim_Book` 维度几乎不可用，无法做「明代笔记 vs 政书」这种最有价值的切片。
> 建议：给 `books` 补 `author/dynasty/category/full_title` 等。

### 2.4 🟠 canonical.note 100% 空
1071 个 canonical 的 `note` 全空。人工裁决（lock/reject）的理由没沉淀下来，
下次重跑 `transform` 虽然靠 `member_overrides` 不丢结果，但**为什么这么判**的上下文丢了。
> 建议：裁决时把 `reason` 同步进 `canonical.note`，或让 `override_log` 成为唯一上下文源并在查询时 JOIN。

### 2.5 🟠 edges 缺 volume 列 + predicate 空率高
- `edges` 没有 `volume` 列；1498 条边里 **1235 条 payload 含卷文本**却没抽出成列 → 关系事实无法按卷切片，只能现解 JSON。
- `predicate` 空 **278/1498**（主要是 `appt` 任职层：官职在 payload 不在谓词列）。
> 后果：关系层里混入了「非关系记录」（任职事件本就是 node/事件性质）。
> 建议：edges 加 `volume TEXT`（loader 从 payload 抽）；appt 这类考虑归到 nodes 或单独事实，而非强行塞 edge。

### 2.6 🟠 volumes 目录表空置
`volumes` 是 schema 声明的「扩展点」，但 **0 行**；卷信息散在 `records.volume`/`items.volume`
自由文本（`'01'..'12'` 裸数字，无「卷X」归一）。
> 建议：要么填充 `volumes`（dominant_type/reading_mode），要么承认冗余删掉；
> 数仓现从 records 派生 `Dim_Volume`，能用但不规范。

### 2.7 🟠 pending_refs 无治理闭环
666 条悬空引用（名字在 ent_keys 查不到、边解析失败），目前只有堆积，没有
「已补实体 / 已忽略」的状态机。
> 建议：`pending_refs` 加 `status`(open/resolved/ignored) + `resolved_uid`。

### 2.8 🟡 checksum 全 NULL
见 §1 —— 增量检测形同虚设，必须补 `source_rev` 或真正计算 checksum。

现状：时间只在 `when` 文本（"万历十年"、"正德庚午"），极少落结构化年份。
> 意见：新增一个**时间归一步骤**，用年号表把 `when` 文本换算成公元年份，
> 落到独立 `date_spans(book_id, layer_key, local_id, year_start, year_end, era_text)` 表
> （或 records 加 `year_start/year_end` 列）。
> 这是让「仕履时间线 / 事件年表」真正成为分析轴的前提。做之前先确认是不是项目主轴——
> 若时间不是重点，保持 best-effort 即可，不必强求（数仓 `Dim_Time_Year` 现标注为稀疏/近似）。

### 3.2 健康信号（不用动）

## 5. 2026-10-16 增量入账与一条硬警告

**做了什么**：`adapters/__init__.py` 给 `fqh`/`ppy`/`lgs`/`xzl` 声明 `trl` 层（`BOOK_LAYERS` +
`LAYER_DECL` + 各 adapter 的 `trl_id` 主键），随后 `load --book <id> --no-wipe` 四本，
`refs`/`volumes` 复跑。选 `--no-wipe` 而非默认重装，是因为默认路径的 `wipe_book` 会连带删掉
这四本在 `members`/`candidate_links` 里的 834 行身份数据，而本轮只加 annotation 层记录，
身份层本不该动。灌完后 nodes/edges/canonical/members/candidate_links 与备份逐表相等。

**硬警告：现在的 `transform.py` 与库内身份层不是同一套算法，直接重跑会重写身份。**
在同一份库的副本上实测（只多这 860 条 trl）：

| | 库内现值 | 重跑 transform 后 |
|---|---|---|
| canonical | 1580 | 643 |
| members | 6772 | 2979 |
| members 状态 | auto 5640 / conflict 929 | auto 943 / **conflict 1833** |
| members method 词表 | exact_normalized 5164、surface_alias 1282、normalized_stripped 123、manual_lock 203 | place_name_match 1110、place_hierarchy_match 476、office_name_match 447、kinship_relation 436、office_dynasty_match 196、exact_name 60、context_similarity 18、manual_lock 203 |

差异与这 860 条无关（`nodes` 只从 `ent` 层抽取，`trl` 是 annotation；候选对 6690 一字未变）——
是**身份判定线换过算法**（CBDB 富化 + 分层匹配）之后库没再重跑过。所以重跑等于一次身份重建：
`canon-xxxxx` 按组序重编，`_fqh_conflicts.json`、文档里引用的旧编号会集体错位；
`member_overrides` 204 行会由 `replay_overrides` 重放（`manual_lock` 203 行确实留下了），
但合并下限（0.35）还没拍板，conflict 从 929 涨到 1833 意味着约九成裁决要重看。
**先定合并下限，再挑一个独立窗口跑身份重建**，不要挂在任何「补层」动作后面顺手跑。
