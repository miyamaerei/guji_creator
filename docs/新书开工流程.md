# 新书开工流程 —— 从第 7 本起该怎么起步

> 适用：**第 7 本及以后的新书**。已交付的六本不归这份文档管（它们走 `docs/mcp-规划.md` 的存量线）。
> 本文把三件散落的事串成一条动线：**工厂五阶段**（怎么设计）→ **四段式管线**（怎么执行）→ **格式契约**（怎么保证不走歪）。
> 写这份文档的原因：前六本每一步的做法都在，但「一本新书从零到交付该按什么顺序走」没有一处写全。

---

## 1. 先分清三样东西（最容易混）

| | 是什么 | 产物 | 什么时候用 |
|---|---|---|---|
| **工厂 A** `Skills/00-book-knowledge-factory/` | meta-skill，**定语义层** | 一个「书实例 skill」 | 要系统研读、固化成可复用规范 |
| **工厂 B** `Skills/book-skill-factory/` | 六组启发式问询，**定四级结构**（目录/卷/标题/段落） | `structure.json` + 薄壳 `extract.py` | 书太乱、看不清结构时先探底 |
| **工程目录** `<book>-kb/` | 真正跑管线、放数据的地方 | 层产物 + 交付物 | 实例化之后执行用 |

**两者的关系（真实走过的路）**：《先进遗风》是 **B 探底 → A 定案**——B 版先做结构提取，
发现 `heading_kind: none`（无条目标题、纯段落连排）建不了库，于是在 `xianjinyifeng-kb/` 下
用 A 重做 6 层 KG，切条方案改成「空行段落 = 条」。**结构不明的新书建议先跑 B**，别上来就设计层。

**两套目录组织，开工前就要选定**（现存两种，别混着来）：

| 组织 | 形态 | 例 |
|---|---|---|
| 分离式 | skill 在 `Skills/<NN>-<slug>-knowledge/`，工程在 `<slug>-kb/` | 水东、五杂俎、蘧编、客座 |
| 内含式 | skill 在工程目录内 `<book>-kb/<NN>-<slug>-knowledge/` | 先进遗风（最新做法） |

内含式的好处是 skill 与数据同仓同版本，推荐新书用它。

## 2. 全景图

```
拿到一本新书
     │
     ├─ 结构不明？ ── 是 ─→ 工厂 B：六级问询 → structure.json → 分卷/全本 txt
     │                        （拿准了「怎么切条」再往下走）
     │
     ▼
 Step 0  查契约            ← tools/book-mcp/（本文 §3）
     │   contract_list / layer_list / enum_get
     ▼
 Step 1  定向探查          ← 工厂 A ①（本文 §4）
 Step 2  反思定层          ← 工厂 A ②（本文 §5）  ← layer_get 在这里用
 Step 3  实例化（建 skill + 工程骨架）  ← 工厂 A ③（本文 §6）
 Step 4  试点 3~5 条       ← 工厂 A ④（本文 §7）
 Step 5  全量执行（四段式）  ← 实例管线（本文 §8）
 Step 6  交付 + 回写        ← 工厂 A ⑤（本文 §9）
     │
     ▼
 交付后：移交存量线 tools/kb-mcp/ 接管体检
```

七个步骤里，**Step 0 是这次新加的**——前六本没有这一步，所以格式是事后才被发现的。

## 3. Step 0：开工前先问契约（新增，必做）

```bash
cd tools/book-mcp
python server.py list                  # C1–C9 九条契约：目录/ID/底座/层/枚举/产物/登记/著录/结构
python server.py layers                # 层库候选
python server.py enums                 # 基准枚举组
```

产出**「本书契约台账」**——一张表，后面每一步都照它执行：

| 契约 | 本书的决定 | 何时定 |
|---|---|---|
| C1 目录 | 内含式还是分离式 | Step 0 |
| C2 ID | 每个层的前缀（`ent→ENT-`、`evt→EVT-`…），登记互不相撞 | Step 2 锁层时 |
| C3 底座 | `_item_registry.json` 只读；`_src/` 不手抄原文 | 开工即生效 |
| C4 层 | 启用哪些层，每层 `layer_key` = 目录名 | Step 2 |
| C5 枚举 | 单点 `_kg_enums.py` 在哪、种子值从哪几组继承 | Step 3 |
| C6 产物 | 每层必填字段、`_kg_join` 必建 | Step 2 写 schema 时 |
| C7 登记 | 实例目录名 = frontmatter `name`（管 skill 命名，不管书目著录） | Step 3 |
| **C8 著录** | `book.meta.json`：书名/作者/版本/藏地/著录卷数/叶数/梗概 + 逐字段可得性 A/B/C/D | **Step 1 探查即建最小集，Step 6 补齐** |
| **C9 结构** | `spine.json`：`declared_depth` 拍板这本书切到 卷/篇/章/段/句 哪一级 | **Step 2 与锁层同时拍板** |

> `python server.py layers` 输出里，**前缀列带 `*` 的**（如 `L2 rule → RULE*`）是**按 layer_key 推导的建议值**，
> 不是层库写死的。真实前缀在 Step 2 自己登记——《新官轨范》规则层实际用的是 `XGF-R-`。

## 4. Step 1：定向探查（工厂 A ①）

做三件事，**禁止全文载入**（工厂阶段只读样例，全文精读留给实例执行）：

1. 读目录 / 序跋 / 凡例 → 章节数、篇幅、组织方式
2. 首卷 + 中卷 + 尾卷各抽 ≥3 条 → 内容形态（规范句 / 叙事 / 辞书 / 操作步骤）
3. 密度信号统计（可选）→ 该不该建某层的证据

**终止条件**：必做项做完即停；连续两次读取不再改变设计结论就立即收手（`pitfalls.md` #1 防过度探查）。

这一步同时要澄清四件事**（一次问完，≤4 问）**：研读目标、切条粒度、判定方式、交付形态。

契约关联：**C3**（底座形态在这步就知道要不要特殊处理，如无条目标题时怎么定「条」）；
**C8**（本步即建 `book.meta.json` 的 14 项最小集——书名/作者/朝代/体裁/标点形态/底本类型/源文件等，
全部 A 级机采可得，不许拖到交付）。

## 5. Step 2：反思定层（工厂 A ②）——`layer_get` 在这里用

顺序是**先问用户想结构化什么 → 再给层库参考 → 再让用户自己想 → AI 补证据 → 确认**。
最多两轮收敛，不要链式多轮。

展示候选层时直接查：

```bash
python server.py layer --key appt     # key / code / 前缀 / 名称片段 四种查法都行
python server.py layer --key 名物
```

每条候选层要能回答三件事：**建的理由**（本书哪种内容成体系，给密度证据）、
**不建的理由**（内容不支持就明确不建）、**数据支持检验**（素材不足判「点不是线」，不强行建模）。

**锁层输出**（这步的产物，后面全靠它）：

| layer_key | 目录 | 前缀 | 必填字段 schema_fields | 受枚举护栏字段 enum_fields |
|---|---|---|---|---|
| ent | `_layers/ent/` | `ENT-` | ent_id, item_id, text, type, … | type |
| evt | `_layers/evt/` | `EVT-` | event_id, item_id, type, who, … | type |
| appt | `_layers/appt/` | `APPT-` | appointment_id, item_id, person, … | status |

这张表就是 **C4 的注册内容**，前缀同时登记给 **C2**。

**同一轮还要拍板 C9 的 `declared_depth`**——这本书的结构切到哪一级（卷/篇/章/段/句）。
判据是内容形态不是整齐：名录型（明会典）到 `node_kind` 即够，表格型（食货志）到段有意义，
无句读的刻本**不得声明句级**（C9 硬约束：`expression.punctuation='原本无'` ⇒ `ju=false`，
否则现代人的断句会被下游当成古人的结构）。段/句一律由派生器按规则切，**不占 AI 判定额度**。

## 6. Step 3：实例化（工厂 A ③）——契约落地的重头

按 Step 0 选定的组织方式建骨架，逐个对 C1–C9：

**① 目录（C1）**

```
<book>-kb/                     # 或内含式：内含 /05-<slug>-knowledge/
├── book.meta.json             # 著录五块 + 可得性分级（C8，入库；Step 1 建最小集）
├── structure.json             # 结构识别规则（工厂 B 六组问询的产物，C9 的 recipe 出处）
├── _source/                   # 源书 txt（不入库）
├── _extract/                  # 切条原文：NN_卷名.txt，行格式 `条N|正文`
├── _item_registry.json        # 指纹库（只读，Step 4 之前必须建好）
├── spine.json                 # 结构脊柱：节点树 + 条内偏移（C9，派生物不入库）
├── spine.source.json          # 仅 origin=source 的节点及其 evidence（C9，入库）
├── _src/                      # AI 源数据：只写条号 + 解读字段
├── _layers/<layer_key>/       # 层产物
├── _build/                    # 打包结果
├── _validate/                 # 校验报告
├── _deliver/                  # 交付物（不许用「交付物」这个别名）
├── _kg_enums.py               # 枚举单点（C5）
└── run_all.py / build_*.py    # 四段式管线脚本
```

**①b 著录与结构（C8/C9）**：`book.meta.json` 五块缺一即报，D 级字段（如 txt 转录本的叶数）
必须 `null` + `ye_basis`，**禁止为凑齐而造值**；`spine.json` 由 `build_spine.py` 在底座切完后生成，
`recipe.registry_hash` 必须与当时的 `_item_registry.json` 一致——指纹库一旦被改，spine 立即作废重算。

**② 枚举单点（C5）——最贵的一条教训，别省**

```bash
python server.py enum --group EVENT     # 拉种子值：顶层 27 + 子类 40 + 别名 29
python server.py enum --group ENTITY
```

规则：继承基准值 + 按本书归纳增量；**值必须落在 `_kg_enums.py` 里，禁止写死在打包器**
（前六本里客座、蘧编没建单点，枚举值内嵌打包器，执行期被就地吸收，
EVT 跑到 111 种、LIT 114 种——`pitfalls.md` #27）。
归类型枚举必须带兜底值（`unknown` / `其他` / `未明`）；打包器对未注册值记 **ERR**，不许静默放行。

**③ 实例登记（C7）**：frontmatter `name` 必须**等于**目录名（客座曾写成
`kezuo-zhuiyu-knowledge` 而目录是 `04-kezuozhuiyu-knowledge`，遗留未改）。

## 7. Step 4：试点 3~5 条（工厂 A ④）

按实例 schema 跑一轮：判定 → 注入 → 校验。

因为 `book_check` 还没做（契约线 C1 阶段），这一步**手工按契约逐条对**：

- [ ] `_src/` 里有没有手抄的 `original` 字段？（C3）
- [ ] item_id 是不是 `NN-NNN`？（C2）
- [ ] 层产物的目录名 == layer_key？（C4）
- [ ] 枚举值是不是都从 `_kg_enums.py` 来？有没有打包器里的字面量？（C5）
- [ ] 未注册枚举值有没有报 ERR 而不是静默通过？（C5）
- [ ] 每条必填字段都在吗？（C6）
- [ ] `book.meta.json` 五块齐、14 项最小集非 null、每个 null 都能在 `availability` 里对上 C/D 级？（C8）
- [ ] `spine.json` 的 `recipe.registry_hash` 与当前指纹库一致？`origin=source` 的节点都有 `evidence`？（C9）
- [ ] `declared_depth.ju=true` 时 `expression.punctuation` 不是「原本无」？（C9 跨契约闸）

失败回路要说清：**schema/字段缺陷**回改实例再试；**层设计本身错了**回 Step 2 与用户重新确认，
AI 不得自行改层；连试两轮不成功上浮用户裁决。

## 8. Step 5：全量执行（四段式管线）

```
① build_base.py        切卷切条 → _extract/ + _item_registry.json（原文唯一源）
①b build_spine.py      依 structure.json 派生段/句 → spine.json（纯确定性，不占 AI 额度；C9）
② _src/ 装填           AI 逐条：只写条号 + 解读字段，绝不手抄原文
③ build_<layer>.py     打包：ID 分配 / 归一 / 枚举硬校验 / 从指纹库注入 original
④ build_kg_join.py     跨层索引 → validate → _deliver/
```

实际命令（照抄现有实例，两边都一样）：

```bash
python build_base.py                     # 底座
python annotate.py --expect "01:58,02:42"  # 底座自校验（可选）
python build_ent_keys.py --volumes 01    # L1 实体
python build_appt.py --volumes 01        # 各层逐个跑
python build_kg_join.py --volumes 01     # 跨层整合
python validate_layers.py                # 校验
python run_all.py                        # 或：一次性全量重跑
python run_all.py --volumes 01           # 单卷幂等重算
```

三条铁律：**原文只在指纹库存一份**（`_src/` 不手抄、`spine.json` 不存 `text`）、**枚举封闭**（ `_kg_enums.py`）、
**单卷重跑幂等**（`--volumes NN` 不破坏其他卷）。

契约关联：**C6**——`_kg_join` 必建，层 JSON 按 Step 2 注册的 `schema_fields` 逐项校验完整性。
**C9**——指纹库一旦变动，`spine.json` 的 `registry_hash` 校验会失败，必须重跑 `build_spine.py`（S5 重算闸），
不许留下"改了原文但偏移还指旧位置"的隐性错。

## 9. Step 6：交付 + 回写（工厂 A ⑤）

| 动作 | 对应契约 / 位置 |
|---|---|
| 交付物统一进 `_deliver/` | C1（不许用「交付物」别名） |
| 实例登记 | C7 → `Skills/00-…/references/registry.md` |
| **著录补齐** | **C8**：把 `base_edition` / `abstract`(+出处) 补到能补，D 级字段保持 `null` + 理由；`governance.updated_by` 记谁改的 |
| **结构交付** | **C9**：`spine.json` 过 S1–S11；`declared_depth` 与实际产出一致（WARN 项要写进交付报告，不许默默少切一级） |
| 反思过程存档 | `references/case-feedback-<slug>.md`（实例只固化结论） |
| 新层 / 新坑 / 新枚举提案 | `references/pending-review.md`（待评审区，不是直接入库） |
| **枚举改值** | **C5：version+1 且双写 `enum-changelog.md`**，缺一即野分支 |
| 学习回路合并 | 满足「跨书复用 + 归并优先 + 用户确认」才升入正式库，版本行 +1 |

**交付即交接**：这本书从「契约线」转入「存量线」，此后由 `tools/kb-mcp/` 接管体检
（`enum_drift` / `enum_sync` / `enum_checklist`）。

## 10. 契约自检清单（可打印，逐步打勾）

**开工时（Step 0–3）**

- [ ] C1 目录齐了，`_deliver/` 没写成「交付物」
- [ ] C2 item_id 是 `NN-NNN`；每层一个前缀，全局不撞
- [ ] C3 `_item_registry.json` 已建，`_src/` 没手抄原文
- [ ] C4 每层登记了 key / 目录 / 前缀 / schema / 枚举字段，且 **key == 目录名**
- [ ] C5 `_kg_enums.py` 单点已建，打包器从它读，封闭集有兜底，未注册值报 ERR
- [ ] C7 目录名 == frontmatter `name`，已登记 `registry.md`
- [ ] C8 `book.meta.json` 五块齐、14 项最小集非 null；`availability` 逐级标了 A/B/C/D，每个 null 都对得上 C/D
- [ ] C8 D 级字段有 `<字段>_basis` 理由（如 txt 转录本无叶数），**没有为凑数编造的叶数/藏地**
- [ ] C9 `structure.json` 已定（卷/标题/段落识别规则），`declared_depth` 已由用户拍板
- [ ] C9 `expression.punctuation='原本无'` ⇒ `declared_depth.ju=false`（无句读本不得声明句级）

**执行中（Step 5）**

- [ ] 每层产物字段完整（对照 Step 2 的 `schema_fields`）
- [ ] 没有值跑到枚举定义集之外（这就是存量线事后才报的漂移，本该这里拦住）
- [ ] 单卷重跑幂等：`python run_all.py --volumes 01` 跑两遍结果一致
- [ ] `spine.json` 的 `registry_hash` 与当前 `_item_registry.json` 一致；S5 重算能逐字符复现偏移

**交付前（Step 6）**

- [ ] `_kg_join` 覆盖全部 item_id
- [ ] `_validate/` 里 ERR = 0、GAP = 0
- [ ] 枚举若有变更：`version+1` + `enum-changelog.md` 已追加
- [ ] 交付物在 `_deliver/`
- [ ] C8 补齐 `base_edition` / `abstract`（带出处）；C 级留空要在报告里说明「需书目人工登记」
- [ ] C9 `declared_depth` 与实际产出一致；少切一级的 WARN 已写进交付报告

## 11. 最小命令序列（复制即用）

命令行都从**仓库根**出发，每条 `cd` 独立可用。

```bash
# 0) 查格式：九条契约 + 层库候选
cd tools/book-mcp
python server.py list
python server.py get --id C9             # 结构脊柱怎么定（C8 = 著录元数据）
python server.py layers

# 1) 结构不清先探底（工厂 B，可选）
cd ../../Skills/book-skill-factory
python generate.py --book <书>.txt --answers a.json
# 产出 book-<slug>/（SKILL.md + structure.json + scripts/extract.py）

# 2) 定层时查某一层（工厂 A ②）
cd ../../tools/book-mcp
python server.py layer --key appt
python server.py enum --group EVENT      # 拉该层枚举的种子值

# 3) 建实例 + 工程骨架（按 §6 的目录树手工搭，重 A 轻 B）

# 4) 跑管线：先单卷试点，再全量
cd ../../<book>-kb
python build_base.py                     # ① 底座：切卷切条 + _item_registry.json
python annotate.py --expect "01:58"      #   底座自校验（先进遗风的做法，可选）
python run_all.py --volumes 01           # ② ②③ 单卷试点
python run_all.py                        #   全量：各层 + _kg_join + validate
python validate_layers.py                # ④ 校验（部分装填阶段加 --skip-baseline）
```

单卷重跑幂等，随时可用：`python run_all.py --volumes 01`。
