# 古籍联邦库 · 数据仓库维度建模设计

> 承接 `docs/跨书合并方案.md` / `跨书合并-数据库设计.md` / `tools/kb-federation/schema.sql`。
> 目标：在已建成的联邦库（`kb.sqlite`，18 张表，零依赖 SQLite）之上，建立一套**维度模型（Data Warehouse）**，
> 支撑「跨书覆盖度统计 / 实体对齐分析 / 关系网络度量 / 数据质量（枚举漂移）」等 OLAP 分析。
> 状态：设计稿（待拍板）。

---

## 0. 起点：联邦库 → 数仓 的角色分工

联邦库本身是一套**集成/操作层**（联邦图谱），不是为分析优化的。它已经替数仓做好了两件最难的事：

1. **复合主键隔离**（`book_id, layer_key, local_id`）——天然就是「书级」维度的最细粒度，撞号（实测 2847）已消解，**不重不漏**。
2. **跨书实体对齐已完成**（`canonical` + `members`，F3 落地，`nodes=18152 / canonicals=824 / members=3804`）——这正是数仓要的**一致性维度脊柱**，可直接用。

所以数仓不是重新洗数据，而是把联邦库的三层表**重新按「业务过程」切成事实表 + 围绕一致性维度组织**。联邦库是源，数仓是面向分析的重述。

| 联邦库表 | 在数仓里的角色 |
|---|---|
| `books` | 维度 `Dim_Book`（一致性维度） |
| `layer_catalog` / `layer_fields` | 维度 `Dim_Layer`（一致性维度，含 kind 路由） |
| `volumes` | 维度 `Dim_Volume`（一致性维度，含 reading_mode） |
| `items` | 维度 `Dim_Item`（退化维度，可直接进事实） |
| `records`（JSON） | 事实 `F_Annotation` 的源 + 多数的度量抽取源 |
| `nodes` / `canonical` / `members` | 维度 `Dim_Entity`（解析后，跨书一致） + 桥表 `Bridge_EntityMember` |
| `edges` | 事实 `F_Relationship` 的源 |
| `record_refs` | 事实 `F_Citation` 的源 |
| `enum_registry` / `enum_values` / `enum_drift` | 维度 `Dim_Enum` + 事实 `F_Drift` |
| `load_runs` / `federation_meta` | 装载血缘 / 版本（元数据，不入分析事实） |

## 1. 整体架构结论：**星座模型（Fact Constellation / Galaxy）**

### 先回答你的问题：星型 / 雪花 / 星座，选哪个？

**选星座（Galaxy）作为整体架构；每个事实周围用扁平星型维度；雪花只用于枚举层级这一个 outrigger。**

理由（贴合本项目数据特征，不是泛泛而谈）：

- **为什么不是单一星型**：本项目有 **5 个彼此独立、粒度不同的业务过程**（抽取覆盖 / 关系断言 / 实体解析 / 引用物化 / 枚举漂移）。单一星型只能服务一个过程。这些过程共享同一批维度（书、层、卷、实体、时间、枚举），但各有各的事实表和度量——这正是 Kimball 星座模型的定义。
- **为什么不是全面雪花**：数据量级很小（~14k ID / ~32k 记录 / 6 本书），雪花带来的存储节省和范式化收益可以忽略，反而让查询多 JOIN、拖慢分析。维度应当**扁平（star）**，除了下面说的枚举层级。
- **为什么枚举用雪花（唯一例外）**：`enum_values` 自带真树（`enum_group → value → parent → alias`，如 EVENT 顶层 27 个 → 子类 → 别名）。这个层级是被频繁按「顶层 / 子类」聚合的，单独拆出 `Dim_Enum_Group` / `Dim_Enum_Value`（带 `parent`）作为 `Dim_Enum` 的 outrigger，是雪花的正当用法。
- **星座的「总线」就是一致性维度**：`Dim_Book` / `Dim_Layer` / `Dim_Volume` / `Dim_Entity`(解析后) / `Dim_Time` / `Dim_Enum` 是跨所有事实共享的脊柱。任何一个事实都能和其他事实在这些维度上 **drill-across**（交叉钻取）。

```
                    ┌──────────────── 一致性维度（总线脊柱）────────────────┐
                    │  Dim_Book  Dim_Layer  Dim_Volume  Dim_Entity(canon)  │
                    │  Dim_Time(角色扮演)  Dim_Enum(+雪花 outrigger)        │
                    └───────────┬──────────┬──────────┬──────────┬─────────┘
        ┌──────────────────────┼──────────┼──────────┼──────────┼──────────┐
        ▼                      ▼          ▼          ▼          ▼          ▼
   F_Annotation          F_Relationship  F_Resolution  F_Citation  F_Drift
   (抽取覆盖)            (关系断言)       (实体解析)     (引用物化)   (枚举漂移)
        │                      │               │            │           │
        └──────── 各自星型，共享上面那排维度 ────────┴────────────┴───────────┘
```

## 2. 一致性总线矩阵（Bus Matrix）

行 = 业务过程（事实），列 = 一致性维度。`●` = 该事实关联此维度。

| 业务过程（事实表） | Dim_Book | Dim_Layer | Dim_Volume | Dim_Entity<br>(解析后跨书) | Dim_Entity<br>(书内原始) | Dim_Time | Dim_Enum | Dim_Item |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| **F_Annotation** 抽取覆盖 | ● | ● | ● | | ●(被标注对象) | | ●(枚举字段) | ● |
| **F_Relationship** 关系断言 | ● | ● | ● | ●(主/宾解析) | | ●(事件/任职时间) | ●(predicate 枚举) | ● |
| **F_Resolution** 实体解析 | ● | | | ●(canonical) | ●(member) | | | |
| **F_Citation** 引用物化 | ● | ● | ● | ●(target) | ●(source) | | ●(field/role) | ● |
| **F_Drift** 枚举漂移 | ● | ● | | | | | ● | |

**矩阵的读法**：`Dim_Book` / `Dim_Layer` / `Dim_Entity`(解析后) 出现在最多过程里——它们是**核心一致性维度**，优先设计、优先治理。凡是能在这三列上对齐的查询，都能跨过程钻取（例如「苏轼在哪些书、哪些层被提及、被对齐到哪个 canonical」）。

## 3. 一致性维度（Conformed Dimensions）

### 3.1 Dim_Book（书）—— 最简单的一致性维度
来源 `books`。属性：`book_id`(PK) / `code` / `name` / `author` / `dynasty` / `status` / `schema_version`。
所有事实都挂它，是总线第一柱。

### 3.2 Dim_Layer（层）—— 含 kind 路由的一致性维度
来源 `layer_catalog`（必要时 JOIN `layer_fields` 出字段语义）。属性：`book_id`+`layer_key`(PK) / `layer_name` / `kind`(node|edge|annotation|profile) / `container_kind` / `id_prefix`。
**关键**：`kind` 是数仓区分「这条记录该进哪个事实」的总开关（node→实体维，edge→关系事实，annotation→抽取覆盖事实）。这是联邦库「目录驱动」原则在数仓侧的延续。

### 3.3 Dim_Volume（卷）—— 角色扮演友好的维度
来源 `volumes`。属性：`book_id`+`volume`(PK) / `dominant_type` / `secondary_type` / `reading_mode`。
卷在多个事实里既是「产生地」也是「时间粗略锚点」（古籍卷次≈时间顺序），可作为 `Dim_Time` 的粗粒度替身。

### 3.4 Dim_Entity —— **总线脊柱，必须分两级**
这是整个数仓最有价值、也最该谨慎的维度。联邦库把「跨书对齐」做成了 `canonical`(代表) + `members`(成员链接)，**物理不合并，只建链接**。数仓据此设计两个层次：

- **Dim_Entity_Resolved（解析后 / 跨书一致）**：以 `canonical` 为粒度。`canonical_id`(PK) / `repr_label` / `repr_type`(person|place|book|object|institution|concept) / `status`(open|locked) / `member_count` / `book_span`(出现在几本书)。
  → 这是真正的**一致性维度**，所有跨书分析都对齐到它。
- **Dim_Entity_Raw（书内原始 ent）**：以 `nodes` 为粒度。`uid`(PK=`book_id:local_id`) / `book_id` / `label` / `type` / `payload`。
  → 书内粒度，挂在「被标注对象」「source」等角色上。

两者通过 **桥表 `Bridge_EntityMember`**（`canonical_id`, `uid`, `method`, `confidence`, `status`）连接——这是经典的**多值桥维度**（一个 canonical 可能含多个 raw 节点；冲突期一个 raw 节点甚至短暂属于多 canonical，`status='conflict'`）。查询时要按 `status` 过滤掉 conflict/pending，避免重复计数。

> ⚠️ 设计铁律延续：数仓的 Dim_Entity **绝不回写**联邦库 `nodes`；它只是联邦库 `canonical/members` 的「分析视图」。

### 3.5 Dim_Time —— 角色扮演维度（Role-playing）
古籍时间稀疏且多维（事件起止、任职起止、年谱纪年）。不做单一时间维，而是**角色扮演**：同一张 `Dim_Time`（年 / 朝代 / 世纪）在不同事实里扮演 `event_start` / `event_end` / `appt_start` / `appt_end`。
属性（以年粒度的事实表 `dim_time_year`）：`year`(PK) / `dynasty` / `century` / `is_ming`(是否明代)。来源：从 `edges`/`records` 的 `payload` 抽取 `year_start/year_end`（chr 层最规整）。

### 3.6 Dim_Enum —— 唯一雪花点
来源 `enum_registry` + `enum_values`。
- `Dim_Enum_Group`(outrigger)：`enum_group`(PK) / `name` / `version` / `section`。
- `Dim_Enum_Value`：`enum_group`+`value`(PK) / `is_top` / `parent` / `alias`。
雪花理由：枚举是真树，按「顶层 vs 子类」聚合是高频操作，层级拆开比塞进一个大宽表更清晰。其余维度一律扁平。

### 3.7 Dim_Item（条目）—— 退化维度
`items` 本就是锚点（指针），粒度 = `(book_id, item_id)`。多数情况**直接作为退化维度进事实表**（事实表带上 `book_id, item_id` 即可），不必单独建维表；仅当需要对条目做属性分析（如按 `layer_count` 分桶）时再物化。

## 4. 事实表（Fact Tables）—— 五个业务过程

每个事实表都带 `book_id`（外键到 Dim_Book）作为**最小一致性键**，确保能跨事实 drill-across。

### F_Annotation（抽取覆盖事实）
- **业务过程**：每本书每层抽取出了多少条知识记录。
- **粒度**：`(book_id, layer_key, local_id)` —— 即联邦库 `records` 的一行。
- **维度**：Book ● / Layer ● / Volume ● / Entity_Raw(被标注对象,可空) ● / Enum(枚举字段) ● / Item ●。
- **度量（可加）**：`record_count`(=1，行级) / `payload_size` / `has_enum_drift`(标志)；**从 payload JSON 派生**的覆盖指标（如该记录含几个实体引用）。
- **用途**：「某书某层覆盖率」「哪些卷/层是空壳」。

### F_Relationship（关系断言事实）
- **业务过程**：知识图谱的边（谁—谓词—谁）。
- **粒度**：`(book_id, layer_key, local_id)` —— 联邦库 `edges` 一行。
- **维度**：Book ● / Layer ● / Volume ● / **Entity_Resolved(主/宾，经解析)** ● / Time(角色扮演) ● / Enum(predicate 枚举) ● / Item ●。
- **度量**：`edge_count`(=1) / `is_resolved`(subject&object 都解析到节点) / `confidence`(若关系消歧带入)。
- **用途**：「苏轼（canonical）的关系网跨哪些书」「某谓词（如『师友』）的总边数」。

### F_Resolution（实体解析事实）
- **业务过程**：跨书实体对齐的结果与置信。
- **粒度**：`(canonical_id, uid)` —— 联邦库 `members` 一行（含桥语义）。
- **维度**：Book ● / **Entity_Resolved(canonical)** ● / **Entity_Raw(member)** ●。
- **度量**：`confidence` / `method`(exact|alias|relation) / `status`(auto|conflict|locked|pending) / `evidence_count`。
- **用途**：「对齐质量」「待人工复核的 conflict 有多少（接 `conflicts` 命令）」「同一实体跨几本书」。

### F_Citation（引用物化事实）
- **业务过程**：记录 → 实体的结构化引用（payload 内 `*_ent_ids` 展开）。
- **粒度**：`(book_id, layer_key, local_id, field#n)` —— 联邦库 `record_refs` 一行。
- **维度**：Book ● / Layer ● / Volume ● / **Entity_Resolved(target)** ● / Entity_Raw(source) ● / Enum(field/role) ● / Item ●。
- **度量**：`ref_count`(=1) / `is_ambiguous`(裸 ID 跨卷重名)。
- **用途**：「某书被引最多的实体」「引书网络（citation_network 查询的仓库版）」。

### F_Drift（枚举漂移事实）—— 数据质量过程
- **业务过程**：数据里用到但枚举库没有的值（治理用，对应坑 #27）。
- **粒度**：`(book_id, layer_key, field, enum_group, value)` —— 联邦库 `enum_drift` 一行。
- **维度**：Book ● / Layer ● / Enum(枚举组) ●。
- **度量**：`drift_count` / `in_library`(0/1)。
- **用途**：「哪本书哪层漂移最严重」「治理优先级」。

## 5. 一致性事实（Conformed Facts）

「一致性事实」在 Kimball 里指**跨多个事实表、定义完全相同、可直接相加/比较的度量**，是 drill-across 的另一半（维度是脊柱，一致性事实是可比的刻度）。本项目可确立三条：

1. **`mention_count`（实体被提及次数）**：在 `F_Annotation` 与 `F_Relationship` 中定义一致——都按「对齐到同一 `Dim_Entity_Resolved` 的出现次数」计。于是可以问「苏轼在『关系』里出现 12 次、在『标注』里出现 30 次」，两列直接可比。
2. **`book_span`（实体横跨书本数）**：由 `Dim_Entity_Resolved.book_span` 提供，是跨 `F_Resolution` / `F_Relationship` / `F_Citation` 都一致的「实体活跃度」指标。
3. **`record_count`（层记录数）**：在 `F_Annotation` 与 `F_Drift` 里同为「该层落到该维度的记录条数」，用于「覆盖率 vs 漂移率」同屏对比。

> 注意区分：**一致性事实 ≠ 同一张表**。它是「同名同义、可跨过程相加」的度量约定。上面的 `confidence` 在 `F_Resolution` 有明确语义，但**不应**在 `F_Relationship` 里假装有同义 confidence——那会破坏一致性，必须分别命名。

## 6. 关键建模技巧清单

- **实体解析桥表**（`Bridge_EntityMember`）：多值桥，查询时按 `status IN ('auto','locked')` 过滤，杜绝 conflict/pending 重复计数。
- **角色扮演时间维**：同一 `Dim_Time` 在 F_Relationship 里同时扮演 `event_start`/`event_end`，不复制维表。
- **退化维度 Item**：`item_id` 直接进事实，省一张维表。
- **雪花仅枚举**：其余维度扁平；枚举层级拆 outrigger。
- **JSON 抽取进度量**：`records.payload` / `edges.payload` 是 JSON，仓库的度量（引用数、枚举字段命中）在 ETL 阶段从 JSON 解析后落数值列，**不让分析查询现解 JSON**。
- **绝不回写**：数仓所有表都是联邦库的**派生物**，可重建；`kb_dw.sqlite` 同 `kb.sqlite` 一样**不入库**。

## 7. 物理落地建议

- **独立库 `tools/kb-federation/kb_dw.sqlite`**（或并入同一库另起 schema 前缀），仍用**纯 SQLite、零第三方依赖**，守项目铁律。
- ETL 顺序：先建一致性维度（Dim_Book/Layer/Volume/Entity/Time/Enum）→ 再建 5 个事实表 → 最后建桥表。全部 `DELETE WHERE book_id=?` 幂等重跑。
- 视图层可预建：
  - `v_entity_mentions`（canonical × 各过程 mention_count，供一致性事实直接查）
  - `v_cross_book_alignment`（实体跨书对齐总览，接 `search` / `assoc` 命令的仓库版）

---

## 8. 一句话总结

> **星座架构 + 扁平星型维度 + 枚举单点雪花 + 以「解析后实体（canonical）」为一致性脊柱的桥表**。
> 联邦库已经把最难的「跨书对齐」做完，数仓的本职是把这 18 张表重新按 5 个业务过程切成事实表，
> 让「苏轼在六本书里被提及/关联/引用多少次、对齐到哪个实体、质量如何」变成一条 SQL 就能答的问题。
