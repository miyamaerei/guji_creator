# 《明史》志书（食货志 × 职官志）接入联邦库方案

> 提出：2026-10-13
> 状态：**待拍板**（承接 docs 内「跨书合并」系列文档；其中三份核心文档本身亦为待拍板状态）
> 定位一句话：**志书联动不另起炉灶，作为两本"新书"接入 `tools/kb-federation/`，全套复用既有装载/对齐/查询/校验机制。**

---

## 1. 结论先行

《明史》食货志与职官志是两个独立修复完成的工程（`mingshi-shihuozhi` / `mingshi-zhiguanzhi`），各自维护完整的 `_layers/` 体系。此前曾讨论过在志书侧自建 `_kb/entity_links.json` + `bridge_org/salary/evo` 三座桥 + SHZ:/ZGZ: 命名空间前缀的联动方案。

**本方案推翻该设计，改为接入 docs 已实证的联邦库（`tools/kb-federation/`）**：

- 上一轮 7 个新构件 → **只有 3 件真正新增**（两个 adapter、name_rules 增补、3 个关联查询），其余全部落在既有机制上；
- **SHZ:/ZGZ: 前缀方案作废**——docs 复合主键 `(book_id, local_id)` 天然解决 item_id 撞号（两志均从 `01-001` 起）与 ENT- 前缀撞名；
- 三座桥表语义不新增 schema，降级为 `edges` + `record_refs` 上的既有边/引用 + L3 查询；
- **职官志树形结构（机构树/官职上下级）同样不加表**——靠既有 `records`（无损 JSON）+ `nodes`（单 ent）+ `edges`（有向边）+ `layer_fields`（字段语义声明）落地，adapter 只需新增"树展平 + ID 归一"两个函数（见阶段 A 补充）。

## 3. 为什么判定走联邦线（而非自建联动层）

1. **撞号问题已被复合主键解决**：两志 item_id 都从 `01-001` 起、层前缀都叫 `ENT-`——这在 docs 联邦库面前不是新问题，`(book_id, local_id)` 复合主键天然隔离，**不需要自造 SHZ:/ZGZ: 前缀**（上一轮设计里最重的一步直接删除）。
2. **"物理不合并、逻辑建链接"就是为这种场景设计的**：docs 铁律——「宁可漏不可错」「canonical + member 逻辑链接」「curate.py 人工核验」，正好对应"同书强对齐但不武断"。
3. **铁律继续生效**：原文只在各书 `_item_registry`（志书 `_extract`/原文层），adapter 只读 `_layers` 直载，不重抄原文；一切可重跑（幂等 `BEGIN; DELETE; INSERT; COMMIT`）。
4. **避免平行体系**：若志书自建 `_kb/` 联动层，会产生与联邦库语义重复的第四套数据（节点/边/引用/对齐各一套），未来无法与其它书（兵志、刑志、地志等 14 志原文已在 `ming-history/合并/`）互通。接入联邦库则一次投入、全员受益。

## 5. 实施阶段（新增工作量）

### 阶段 A：接入（对应 F2 直载）
- 新增 `tools/kb-federation/adapters/adapt_shz.py`、`adapt_zgz.py`
  - 读各自 `_layers/*.json` 映射到 L2：节点统一进 `ent`、关系进 `edges`、原文注释进 `records`（JSON 存）
  - 幂等装载：`BEGIN; DELETE; INSERT; COMMIT`，可控回滚
  - 零第三方依赖，风格对齐六旧书 adapter
- 跑通后预期：`books` 13 本、records/nodes 相应增长、load_runs 增量

### 阶段 A 补充：职官志树形结构如何落（不加表）

联邦库是"单 `ent` 节点 + 通用有向边"模型，树只是有向图的特例，**不需要新增表**。schema.sql 头注释已声明扩展原则——schema 固定不变，新层只往 `layer_catalog` / `layer_fields` 插行、T 阶段按目录自动抽取，无需 ALTER TABLE。职官志树形数据有两种形态：

**形态 A：机构树 `structs_NN.json`（parent + 嵌套 children）**

| 树元素 | 联邦库落点 | 说明 |
|---|---|---|
| 机构整条记录 | `records`（payload 整条 JSON 无损） | Tier1 忠实装载，不丢 children 嵌套 |
| 机构节点 | `nodes`（type='institution'，uid=`zgz:ORG-501#1`） | 树节点即 ent 节点，无独立节点表 |
| 父子层级 | `edges`（subject=子, object=父, predicate='parent_of'） | T 阶段把嵌套 children **递归展开**成多条边 |
| 同级/上下级职官 | `edges`（predicate='peer_of' / 'subordinate_of'） | officials 的 peers/subordinates 数组同样展开 |
| 机构 → 所属官职 | `edges`（org_id → OFF-*，predicate='holds_office'） | 树到官职的桥 |

**形态 B：官职表 `officials.json`**——`org_path` 路径数组 + peers/subordinates 引用，本身已为铺平设计，展开成边即可，无新结构。

查询侧：`idx_edges_subject/object` 索引已建，SQLite 原生 `WITH RECURSIVE` 递归 CTE 可直查子树/祖链，不依赖新表。

**adapter 需新增的两个函数（代码新增，非 schema 变更）**：

- `flatten_tree(records)` —— 递归展开嵌套 children → 逐条生成 parent_of 边；不展平则最深层机构（如"经历司"）成孤儿节点；
- `normalize_local_id(rec)` —— ID 归一，**必须保留 `#n` 后缀**（实测 `ORG-501#1`），否则 `ORG-501` 与 `ORG-501#1` 会被复合主键误判为两条 record、或被折叠丢实体。

**三个注意点**：

1. `#n` 后缀去重不能丢——docs F2 已记录此坑（水东/新官按实体复用 id 需 `#n` 去重），志书同样存在；
2. `officials.json` 双 ID（`official_id` 与 `id` 并存，均 `OFF-001`），须在 `layer_fields` 声明为 `node_ref`（ref_layer='ent'），否则 T 阶段不会把 `peers:["OFF-002"]` 自动解析成边；
3. `flatten_tree` 必须先于 T 阶段执行，防止最深层机构成孤儿节点。
- `name_rules.json` 增两志条目（史志别称：户部 ↔ 明初民部、都察院 ↔ 御史台等）
- 跑 T 阶段候选（T1 精确 → T2 alias → T3 关系传播）
- `curate.py` 核验冲突，别名裁决写入 `member_overrides` + `override_log`

### 阶段 C：查询（对应 F4）
- `assoc.py` 新增 3 个关联查询：
  - `joint_timeline` —— 跨志联合时间线
  - `salary_bridge` —— 职官俸禄 ↔ 食货税额对照
  - `org_career_chain` —— 食货 PROCS 与职官 officials 任职链贯通

### 阶段 D：收尾
- `layer_catalog` 登记志书独有层（opns/regs/ledger/structs——六旧书没有的层，需确认 schema 不缺字段）
- 可选：`kb_dw.sqlite` 数仓纳入两书（漂移检查覆盖、维度表扩展）
- 志书侧 `_views/cross/` 由 L3 查询结果渲染，只做呈现

## 6. 边界、风险与铁律

- **物理不合并**：两志数据仍在各自 `_layers/`，联邦库只建逻辑链接；
- **原文只在指纹库**：全链不重抄原文，adapter 只读层产物；
- **一切可重跑**：任何阶段可删除重建，幂等装载保证；
- **宁可漏不可错**：同名异实（南北两京官司、泛称"尚书"）强制进 curate 人工核验，宁缺勿链；
- **不新建 C17/C18/C19 补充层**（食货志已有硬约束），缺口只登记不编造；
- 志书内 `validate_layers` 全绿基线不可破坏——联邦线是只读消费方，不回写志书层。

**风险清单**：
| 风险 | 缓解 |
|---|---|
| 泛称实体误链（"尚书""御史"） | T2 alias 收敛 + curate 强制核验 |
| layer_catalog 对志书独有层支持不足 | 阶段 D 先确认 schema，缺则仅登记不扩展表 |
| docs 联邦库方案本身待拍板 | 本方案按「已落地代码」口径，docs 改动时映射随动 |
| 数仓维度模型对史书体例不适配 | 阶段 D 可选，先只做漂移覆盖 |
